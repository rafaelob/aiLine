Guia Gemini Interactions API — Referência completa

Documentação técnica da Gemini Interactions API (GA desde junho/2026 — a interface padrão do Gemini para projetos novos). Cobre a anatomia da Interaction (timeline de steps), texto, streaming SSE, multimodal (imagem/áudio/vídeo/PDF), function calling, structured output, thinking, cache implícito, Deep Research e Antigravity, ferramentas server-side (Google Search, Maps, Code Execution, URL Context, File Search, Computer Use, MCP), background, webhooks e a referência REST, além de quando ainda usar generateContent (Batch API, AFC em Python e cache explícito).

Use este guia quando

Padrões vigentes

  • SDK google-genai, versão >=2.3.0 para Interactions e pin <3.0.0; chamada base client.interactions.create(model=..., input=...); texto da resposta em interaction.output_text, timeline em interaction.steps.
  • Interactions é GA na Gemini API desde junho de 2026; generateContent é legado e segue suportado. Lacunas restantes da Interactions: Batch API, AFC (Python) e cache explícito. safety_settings são aceitos em interactions.create.
  • Estado no servidor: store (retenção 55 dias no pago, 1 dia no gratuito) e previous_interaction_id; store=false não combina com background=true nem com previous_interaction_id.
  • tools, system_instruction e generation_config valem por interação: reenvie a cada turno.
  • Saída estruturada e modalidades por response_format; raciocínio por generation_config.thinking_level; níveis e padrão variam por modelo (minimal dá erro no gemini-3.8-flash). gemini-4-argon ignora temperature, top_p e top_k.
  • Responda todo step function_call com function_result (call_id = step.id) e previous_interaction_id; no streaming, acumule arguments_delta até step.stop e trate eventos SSE desconhecidos com log + skip.
  • Agentes gerenciados (Deep Research, Antigravity) rodam em segundo plano: use background=true e webhooks.
  • MCP remoto com Gemini 3: as páginas oficiais divergem — UNVERIFIED; valide por teste funcional (1.5).
  • No Vertex / Gemini Enterprise Agent Platform a Interactions API é Preview (v1beta1).
  • Docs oficiais legíveis por agente: espelho .md.txt de cada página, https://ai.google.dev/gemini-api/docs/llms.txt e Gemini Docs MCP (https://gemini-api-docs-mcp.dev).

Os exemplos REST deste guia usam a Gemini Developer API (AI Studio): endpoint generativelanguage.googleapis.com/v1beta/interactions e header x-goog-api-key. Parte A — Conceitos & Guias

Capítulos 1–23 cobrindo todos os conceitos públicos da Gemini Interactions API, em ordem de leitura recomendada da documentação oficial. Exemplos em Python (google-genai), JavaScript (@google/genai) e REST/cURL.

1. Visão geral da Interactions API

A API Interactions é a interface padrão do Gemini para fluxos agênticos, conversas multiturno com estado server-side e operações longas. É GA (desde junho/2026) e a documentação oficial a recomenda para todo projeto novo; novos modelos, capacidades multimodais, ferramentas e recursos agênticos são lançados nela. O método generateContent é descrito como legado, mas segue totalmente suportado — ver quando ainda usar generateContent.

1.1 Por que usar a Interactions API

  • Gerenciamento de histórico server-side: conversa multiturno via previous_interaction_id. O servidor ativa estado por padrão (store=true); para modo stateless, defina store=false.
  • Etapas de execução observáveis: a resposta é uma timeline tipada de steps (thought, function_call, function_result, model_output, google_search_call, etc.), facilitando depuração e renderização de UI para eventos intermediários.
  • Criado para fluxos agênticos: orquestração nativa multi-turno com ferramentas e agentes gerenciados.
  • Tarefas longas em background: background=true habilita operações assíncronas (Deep Research, Antigravity) com integração a webhooks.
  • Acesso a novos modelos e agentes: Deep Research, Antigravity, Omni e os modelos Gemini 3.x saem direto na Interactions.

1.5 Lacunas conhecidas da Interactions API

Segundo a visão geral, continuam ausentes (presentes só em generateContent — ver quando ainda usar generateContent):

  • Batch API.
  • Chamada automática de função (Python).
  • Cache explícito — o cache implícito via previous_interaction_id funciona (§16).
  • MCP remoto com Gemini 3 — conflito oficial: a overview diz que Gemini 3 não suporta MCP remoto ("coming soon"), enquanto a página de Function Calling documenta a tool mcp_server (Streamable HTTP). UNVERIFIED: valide modelo, endpoint e SDK com uma chamada real antes de depender dele.
  • Compatibilidade multi-turn entre modelos: ao misturar modelos na mesma conversa (com ou sem estado), o modelo seguinte precisa aceitar como entrada as modalidades de saída dos anteriores (por exemplo, não continue com um modelo só de texto uma conversa que gerou imagem).

safety_settings são aceitos em interactions.create (§22.1).

2.3 Primeira interação (Hello world)

Python

from google import genai

client = genai.Client()

interaction = client.interactions.create(
    model="gemini-3.8-flash",
    input="How does AI work?"
)
print(interaction.output_text)

JavaScript

import { GoogleGenAI } from "@google/genai";

const ai = new GoogleGenAI({});

const interaction = await ai.interactions.create({
  model: "gemini-3.8-flash",

  -H "x-goog-api-key: $GEMINI_API_KEY" \
  -H 'Content-Type: application/json' \
  -d '{
    "model": "gemini-3.8-flash",
    "input": "How does AI work?"
  }'

3. Anatomia de uma Interaction

O recurso central da API é o objeto Interaction. Ele encapsula uma rodada completa de execução: as entradas do usuário, qualquer raciocínio (thoughts), chamadas de ferramentas, resultados e a resposta final do modelo — tudo organizado em uma timeline ordenada chamada steps.

Forma da resposta: a criação síncrona/streaming entrega o resultado final e eventos dos steps; não presuma que o objeto de resposta inicial contenha a timeline completa. Para auditar/reidratar uma interação armazenada, use GET /interactions/{id} (com include_input=true quando necessário). Essa distinção é importante para state/chaining.

5.2 Modo sem estado (store=false)

Para conformidade ou casos onde você não quer armazenamento server-side, defina store=false. Nesse modo você é responsável por reenviar TODOS os steps gerados (incluindo thought com signature) em cada turno — caso contrário a continuidade de raciocínio quebra.

history = [
    {"type": "user_input", "content": [{"type": "text", "text": "I have 2 dogs."}]}
]

interaction1 = client.interactions.create(
    model="gemini-3.8-flash", store=False, input=history
)

for step in interaction1.steps:
    history.append(step.model_dump())

history.append({
    "type": "user_input",
    "content": [{"type": "text", "text": "How many paws are in my house?"}]
})

interaction2 = client.interactions.create(
    model="gemini-3.8-flash", store=False, input=history
)
print(interaction2.steps[-1].content[0].text)
Restrições de store=false:
  • Incompatível com background=true (Deep Research exige store=true).
  • Impede usar a interação como previous_interaction_id em chamadas subsequentes.
  • Você precisa preservar e reenviar todas as etapas geradas pelo modelo — incluindo assinaturas de thought.

6. Streaming (SSE)

O streaming usa o mesmo endpoint POST /v1beta/interactions, apenas adicionando "stream": true no body. A resposta é um fluxo Server-Sent Events com eventos tipados por step.

Transporte: a Interactions API é HTTP request-response (com estado no servidor via previous_interaction_id) e o streaming é SSE sobre HTTP — não há WebSocket nesse caminho. Interação bidirecional em tempo real (voz/vídeo, áudio-para-áudio) é a Live API sobre WebSocket (WSS; modelos gemini-3.8-live e gemini-3.8-live-extended-thinking) — uma superfície separada da Interactions API.

6.1 Streaming básico

Python

stream = client.interactions.create(
    model="gemini-3.8-flash",
    input="Count from 1 to 25.",
    stream=True,
)
for event in stream:
    if event.event_type == "step.delta":
        if event.delta.type == "text":
            print(event.delta.text, end="", flush=True)

6.5 Streaming com function calling

Em streaming, function calls chegam em partes: step.start entrega name e id, e cada step.delta com delta.type == "arguments_delta" traz um fragmento em delta.arguments (string JSON) que você precisa acumular até o step.stop.

stream = client.interactions.create(
    model="gemini-3.8-flash",
    input="What is the weather in Paris?",
    tools=[weather_tool],
    stream=True
)

current_calls = {}
for event in stream:
    if event.event_type == "step.start" and event.step.type == "function_call":
        current_calls[event.index] = {
            "id": event.step.id,
            "name": event.step.name,
            "arguments": ""
        }
    elif event.event_type == "step.delta" and event.delta.type == "arguments_delta":
        if event.index in current_calls:
            current_calls[event.index]["arguments"] += event.delta.arguments

# Após interaction.completed, parse final
import json
for index, call in current_calls.items():
    call["arguments"] = json.loads(call["arguments"]) if call["arguments"] else {}
print(current_calls)

8. Compreensão de imagens

8.1 Métodos de envio

  • Files API (recomendado para reuso e arquivos grandes; 2 GB por arquivo, 48 h).
  • Inline Base64 — limite divergente entre páginas oficiais: a página de métodos de entrada diz 100 MB por request (desde 2026-01-08; PDF 50 MB), enquanto a página de compreensão de imagens ainda diz 20 MB no total. Para imagens, fique abaixo de 20 MB ou valide com uma chamada real.
  • URI público / URL externa (até 100 MB por request, conforme a página de métodos de entrada).

8.2 Formatos suportados

  • image/png, image/jpeg, image/webp, image/heic, image/heif.

8.3 Limites e tokenização

  • Máximo: 3.600 imagens por requisição.
  • Tokens (página de tokens / image-understanding): imagens com ambas dimensões ≤ 384 px = 258 tokens; maiores são divididas em blocos de 768×768 px com 258 tokens cada (tile_size = floor(min(width, height) / 1.5)).
  • Divergência: a página de media resolution dá, para Gemini 3, 1120 tokens por imagem no default (280/560/1120/2240 em low/medium/high/ultra_high). Não há página que concilie as duas; para cobrança real use interaction.usage e para pré-estimativa use count_tokens.
  • Resolução: o campo resolution por item controla o detalhe (custos mais altos) — ver §11.6.

9.7 Geração de áudio (TTS)

A Interactions API também gera áudio a partir de texto. Use response_format={"type": "audio"} e generation_config.speech_config; os modelos TTS atuais são gemini-3.8-flash-tts e gemini-3.8-flash-lite-tts (GA desde 2026-09-22). Estilo, emoção e ritmo vão em uma anotação speech_metadata do turno. No modo unário o áudio sai em interaction.output_audio.data (base64; WAV com cabeçalho RIFF, PCM 24 kHz, 16-bit, mono por padrão).

Single-speaker — Python

Streaming — Python

9.9 Vozes, idiomas & limites

  • 30 vozes pré-construídas no campo voice — ex.: Zephyr (bright), Puck (upbeat), Charon (informative), Kore (firm), Fenrir (excitable), Leda (youthful), Aoede (breezy), Achird (friendly), Sulafat (warm)… (lista completa na doc oficial). Vozes customizadas (Voices API: voice design e replicação) persistem até 200 por projeto, com TTL de 1 ano (stateful) ou 7 dias (chaves stateless).
  • Idioma automático: o modelo detecta o idioma do texto de entrada (cobertura varia por modelo — ver a seção de idiomas da doc).
Limitações do TTS: entrada somente texto, saída somente áudio; multi-speaker limitado a 2 vozes pré-construídas (para vozes customizadas, sintetize cada turno separadamente e concatene removendo os cabeçalhos WAV). Divida transcrições longas e implemente retry em falhas do servidor.

13. Function calling

Function calling conecta o modelo a ferramentas/APIs externas. Em vez de produzir só texto, o modelo decide quando emitir uma step function_call com id, name e arguments. Seu app executa a função e devolve o resultado num step function_result.

13.1 Esquema da declaração de função

CampoTipoObrigatórioDescrição
typestringSimSempre "function" (no nível superior de tools).
namestringSimsnake_case ou camelCase.
descriptionstringSimExplicação clara da finalidade.
parametersobjectSimJSON Schema (subset OpenAPI).
parameters.requiredstring[]NãoLista de parâmetros obrigatórios.

13.2 Fluxo completo (4 etapas)

  1. Definir a declaração
  2. Chamar o modelo com tools=[...]
  3. Executar a função no cliente (lendo step.name e step.arguments)
  4. Enviar function_result referenciando call_id

13.3 Exemplo — set_light_values

Python

set_light_values_declaration = {
    "type": "function",
    "name": "set_light_values",
    "description": "Sets the brightness and color temperature of a light.",
    "parameters": {
        "type": "object",
        "properties": {
            "brightness": {"type": "integer", "description": "0–100"},
            "color_temp": {"type": "string",
                           "enum": ["daylight", "cool", "warm"]},
        },
        "required": ["brightness", "color_temp"],
    },
}

def set_light_values(brightness, color_temp):
    return {"brightness": brightness, "colorTemperature": color_temp}

interaction = client.interactions.create(
    model="gemini-3.8-flash",
    input="Turn the lights down to a romantic level",
    tools=[set_light_values_declaration],
)

fc_step = next(s for s in interaction.steps if s.type == "function_call")
result = set_light_values(**fc_step.arguments)

final = client.interactions.create(
    model="gemini-3.8-flash",
    input=[{
        "type": "function_result",
        "name": fc_step.name,
        "call_id": fc_step.id,
        "result": [{"type": "text", "text": str(result)}],
    }],
    tools=[set_light_values_declaration],
    previous_interaction_id=interaction.id,
)
print(final.output_text)

15.5 Assinaturas de pensamento (signature)

16. Caching (implícito)

A Interactions API suporta apenas cache implícito. Cache explícito (criação manual de objetos de cache) não está disponível na Interactions; esse é um dos usos que ainda exigem generateContent (client.caches.create(...)).

16.1 Como funciona

  • Ativado por padrão nos modelos Gemini 3.x.
  • Economia de custo aplicada automaticamente em cache hits.
  • Reutilização via previous_interaction_id dispara o cache.

17.9 Agentic Vision (Code Execution + imagem)

O modelo escreve e executa Python sobre a própria imagem (crop, zoom, threshold, contagem, anotação) em vez de "chutar olhando o thumbnail". A documentação oficial de Code Execution chama isso de Code Execution with images e lista três usos: zoom & inspect, visual math e image annotation; ativa-se com Code Execution + Thinking. [doc]

Escopo e evidência. É um recurso da família Flash, não dos modelos Pro. Na documentação oficial, o suporte a Code Execution with images cita a linha Gemini Flash; a confirmação explícita para gemini-3.8-flash não consta na página oficial consultada (UNVERIFIED; teste no seu ambiente antes de depender em produção).

A ideia central: Code Execution é o instrumento de medição do modelo, e a Interactions API dá memória multi-turn (raciocínio, traços de tool e thought_signature) por previous_interaction_id.

O loop, em uma figura

Orquestrador                                   gemini-3.8-flash
   │  turn 1: payload + imagem + prompt            │
   ├───────────────────────────────────────────────►│ THINK  (planeja a hipótese e a região)
   │                                                 │ ACT    ──► code_execution (crop/zoom/threshold/medir)
   │                                                 │ OBSERVE ◄── lê o crop transformado; itera se preciso
   │                                                 │ FINAL: plt.show(imagem anotada)
   │  {analysis, findings, measurements, boxes[]}    │
   │  + annotated_png (emitido pelo modelo)          │
   │  + interaction_id (para o próximo turno)        │
   │◄───────────────────────────────────────────────┤
   │  turn 2 (opcional): MESMOS bytes (audita SHA256!)│
   │            + previous_interaction_id + nova pergunta
   ├───────────────────────────────────────────────►│ retoma com thinking_signature + contexto de code_execution

Invariantes obrigatórias (todo turno, sem exceção)

  1. A imagem vai em TODO turno. previous_interaction_id carrega raciocínio + assinatura + traços de tool, não os bytes da imagem. Reenvie os bytes e audite por sha256(png)[:16].
  2. Assinatura de pensamento preservada verbatim. Ela é opaca e vive dentro dos step/content blocks da interaction — não há acessor top-level resp.thinking_signature no SDK google-genai atual. O SDK reidrata sozinho quando você define previous_interaction_id = resp.id; nunca reconstrua nem injete a assinatura à mão.
  3. Schema fixo = AGENTIC_SCHEMA (abaixo), com additionalProperties: false e os quatro campos sempre exigidos.
  4. Tool list = exatamente [{"type":"code_execution"}] no turno de vision. Quer multi-tool? Embrulhe o flash dentro de um agente maior que roda seu próprio loop e delega só a visão.
  5. Trust framing no system prompt (o modelo é a fonte de verdade; o código é o instrumento). Autonomy framing ("decida se usa a tool") degradou calibração ~8,9 pp nos experimentos.

System prompt (trust framing — núcleo)

Você é o especialista de AGENTIC-VISION. Você É a fonte de verdade sobre esta
imagem — o orquestrador confia na sua leitura. O code execution é o SEU
INSTRUMENTO para fundamentar essa leitura; use-o liberalmente em vez de chutar
a partir de um thumbnail.

Opere em um loop explícito THINK → ACT → OBSERVE:
  • THINK   — em 1–3 frases, planeje qual região e qual medida resolvem a questão.
  • ACT     — carregue a imagem e rode código: crop/zoom; realce de contraste
              (CLAHE/equalização); threshold (HSV costuma ser mais estável que RGB);
              edge detection (Canny/Sobel) ou blob analysis. DESCARREGUE qualquer
              contagem/área/distância para o Python. NÃO meça "no olho".
  • OBSERVE — leia o crop transformado; se não for decisivo, itere outro passo.

PASSO FINAL — OBRIGATÓRIO: como última chamada de código, DESENHE sua(s) caixa(s)
e rótulo(s) sobre a imagem (cv2.rectangle / patches.Rectangle) e exiba com
plt.imshow(...); plt.show() para capturar a imagem anotada — é a sua trilha de auditoria.

DISCIPLINA DE SAÍDA: preencha apenas analysis, findings_summary, measurements e
boxes (coordenadas em pixels da imagem ORIGINAL). Não emita diagnóstico final fora
do schema — o diagnóstico é responsabilidade do agente principal.

Chamada (Interactions API)

import hashlib, base64, json
from google import genai
client = genai.Client()

def sha16(b): return hashlib.sha256(b).hexdigest()[:16]

def consult_flash(*, png_bytes, expected_hash, prompt, prior_id=None,
                  thinking_level="medium"):
    assert sha16(png_bytes) == expected_hash, "image drift antes do envio"
    payload = dict(
        model="gemini-3.8-flash",
        generation_config={"thinking_level": thinking_level},  # low|medium|high (3.8 Flash não aceita minimal)
        input=[
            {"type": "text",  "text": "Fonte da modalidade / caption"},
            {"type": "image", "data": base64.b64encode(png_bytes).decode(),
                              "mime_type": "image/png",
                              "resolution": "ultra_high"},     # crítico p/ lesão pequena
            {"type": "text",  "text": prompt},
        ],
        tools=[{"type": "code_execution"}],                    # SÓ isto no turno de vision
        response_format={"type": "text", "mime_type": "application/json",
                         "schema": AGENTIC_SCHEMA},
    )
    if prior_id:
        payload["previous_interaction_id"] = prior_id          # única diferença no multi-turn
    resp = client.interactions.create(**payload)
    parsed  = json.loads(resp.output_text) if resp.output_text else {}
    steps   = [type(s).__name__ for s in (resp.steps or [])]
    code_n  = sum(1 for s in steps if "CodeExecutionCall" in s)
    out_img = getattr(getattr(resp, "output_image", None), "data", None)
    return {
        "interaction_id": resp.id,
        "analysis": parsed.get("analysis", ""),
        "findings_summary": parsed.get("findings_summary", ""),
        "measurements": parsed.get("measurements", "none"),
        "boxes": parsed.get("boxes", []),
        "n_code_calls": code_n,
        "used_agentic": code_n > 0,        # 0 chamadas = modelo "fugiu" da tool
        "annotated_b64": out_img,          # PNG anotado emitido pelo próprio modelo
        "image_hash": expected_hash,
    }

boxes em pixels da imagem original (nunca normalizados). measurements é string (conjunto aberto: área px², razão de assimetria, diâmetro mm…). additionalProperties: false em todo lugar — sem isso o flash inventa campos que o orquestrador descarta em silêncio.

Multi-turn: o que você NÃO faz numa continuação

  1. Não remova a imagem do novo turno — mesmo com previous_interaction_id, os bytes precisam estar no payload.
  2. Não reconstrua o system prompt inteiro num mega-prompt; envie só a instrução incremental — o contexto anterior vem pelo id.
  3. Não levante/re-injete a "thinking signature" manualmente; setar previous_interaction_id = resp.id é o mecanismo suportado.

Encadeie (previous_interaction_id) para aprofundar na MESMA imagem; comece do zero para outra imagem ou quando a pergunta muda de eixo (continuação serve para deepening, não para redirecionar). Se sha256 diverge entre turnos, aborte — é bug de drift de ground-truth.

Tuning

thinking_levelQuando
low (minimal nos modelos que o aceitam)Triagem em volume, passes de sanidade, consultas de rotina.
mediumDefault para vision diagnóstico. medium → high tem custo ~80% maior e só se justifica em casos de alta complexidade.
highCasos difíceis (lesão pequena, camadas OCT ambíguas); raramente necessário.

resolution: "ultra_high" é não-negociável para imagens diagnósticas ≤ 512 px (dermoscopia etc.); o default subamostra e perde o gradiente que dirige a decisão. Distribuição empírica: mediana de 3 passos de código por caso; se o flash emite < 2 chamadas de rotina, suba o thinking_level ou torne o THINK obrigatório no prompt.

Campo na Interactions API: a resolução vai no próprio bloco de imagem do input, no campo resolution (string). Valores validados em produção:

resolutionQuando usar
standardImagens macroscópicas grandes (ex.: raio-X de tórax).
highOCT, ultrassom.
ultra_highDermoscopia e qualquer imagem ≤ 512 px (preserva o gradiente de pigmentação que o default subamostra).

ultra_high custa ~2240 tokens por imagem segundo a página de media-resolution; a documentação recomenda high para a maioria dos casos e ultra_high só quando o teste mostra ganho claro (ex.: Computer Use ou detalhe diagnóstico minúsculo). [doc]

Anti-padrões (não faça)

  • Adicionar google_search ao turno de vision. Misturar busca introduz ruído. Mantenha o turno de visão só visão; busca é outra tool, orquestrada à parte.
  • Re-renderizar as boxes quando output_image existe — o PNG anotado pelo próprio modelo é melhor que o render por coordenadas (ele "viu" as medidas do código).
  • Pedir veredito diagnóstico final ao flash. Ele é instrumento de visão; o diagnóstico é do agente principal. Misturar os papéis infla a confiança dele nas próprias caixas.
  • Usar gemini-nano-banana-2.1 para isto — é um modelo de geração de imagem, não de raciocínio vision-grounded. Use um Flash de raciocínio (ex.: gemini-3.8-flash).
  • Reaproveitar previous_interaction_id entre imagens diferentes "para economizar tokens" — o flash conflaciona os casos. Imagem nova = interaction nova.

Explicabilidade e auditoria. Trate agentic vision como instrumento de explicabilidade e auditoria (caixas + medidas que mostram por que o modelo tomou a decisão), não como alavanca automática de acurácia. Detecte "tool-dodge": n_code_calls == 0 + boxes == [] + measurements == "none" ⇒ rebaixe a confiança da leitura, não trate como negativo confiante.

Fontes: ai.google.dev/gemini-api/docs/code-execution (Code Execution with images) · ai.google.dev/gemini-api/docs/media-resolution.

18.9 Antigravity agent (preview) — agente gerenciado de propósito geral

O Antigravity (antigravity-preview-09-2026, Preview) é um agente gerenciado de propósito geral: uma única chamada dispara um loop autônomo de raciocínio, execução de código, gestão de arquivos e navegação web dentro de um sandbox Linux hospedado (§18.10). O modelo padrão é gemini-3.8-flash (vale quando agent_config é omitido). Disponível via Interactions API e Google AI Studio. Aceita também gemini-4-argon em agent_config.model. As ações internas de ferramentas usam nomes em snake_case com parâmetros em PascalCase (ex.: write_to_file, replace_file_content(TargetFile, StartLine, EndLine, TargetContent, ReplacementContent), view_file). Fonte: antigravity-agent · changelog.

interaction = client.interactions.create(
    agent="antigravity-preview-09-2026",
    input="Analyze this CSV and produce a summary report.",
    environment="remote",   # sandbox novo com defaults
)
print(interaction.output_text)
print(interaction.environment_id)  # reutilize para continuar com os mesmos arquivos/estado

O parâmetro environment aceita três formas:

FormaComportamento
"remote"Cria um sandbox novo com configurações padrão.
"env_abc123"Reutiliza um environment existente pelo ID — arquivos e estado preservados.
{...} (EnvironmentConfig)Configuração completa: fontes Git/GCS/inline e regras de rede (allowlist).

Capacidades: execução de código (Bash, Python, Node.js; instala pacotes, roda testes), arquivos persistentes entre interações, acesso web (Google Search + URL Context) e compactação automática de contexto (~135k tokens). code_execution, google_search e url_context vêm ativas por padrão (restrinja passando só o necessário em tools); o filesystem é habilitado pelo environment. Também aceita funções customizadas ({"type":"function", ...}, só em modo stateful via previous_interaction_id) e servidores mcp_server remotos (Streamable HTTP; name minúsculo/alfanumérico).

Customização: passe um AGENTS.md com instruções, monte skills em .agents/skills/ no sandbox ou configure inline; o resultado pode ser salvo como agente gerenciado (custom agent).

Limitações (preview): entrada apenas text e image (base64 inline; sem áudio, vídeo ou PDFs); sem saída estruturada; file_search, computer_use e google_maps não suportados; background=true exige store=true. Parâmetros de sampling (temperature, top_p, top_k), stop_sequences e max_output_tokens retornam erro 400 se enviados. Servidores MCP remotos apenas via Streamable HTTP (sem SSE) e com name alfanumérico minúsculo. Function calling customizado apenas em modo stateful (com previous_interaction_id).
Custo: pay-as-you-go pelos tokens do modelo subjacente e pelas ferramentas usadas; o projeto free tem cota gratuita. Para limitar o gasto do loop use max_total_tokens dentro de agent_config.

18.10 Environments (sandboxes de agente)

Cada agente gerenciado roda em uma VM Linux isolada (Ubuntu, Python 3.12, Node.js 22) onde raciocina, executa código, gerencia arquivos e navega na web. Rede de saída liberada por padrão (configurável via allowlist). A VM hiberna por inatividade e restaura o estado na próxima requisição (cold start); é deletada permanentemente após 7 dias de inatividade. Limite: 1.000 agentes gerenciados. import time
def call_with_retry(max_retries=3, base_delay=5):
    for attempt in range(max_retries):
        try:
            return client.interactions.create(
                model="gemini-3.8-flash", input="...", service_tier="flex")
        except Exception as e:
            if attempt < max_retries - 1:
                time.sleep(base_delay * (2 ** attempt))
            else:
                return client.interactions.create(
                    model="gemini-3.8-flash", input="...")  # fallback

22. Limitações

Limites da Interactions API:

  • Só em generateContent: Batch API, cache de contexto explícito e chamada automática de função em Python (AFC) — ver generateContent: quando ainda usar.
  • MCP remoto com Gemini 3.x — há conflito entre páginas oficiais: a visão geral diz que Gemini 3 não o suporta, enquanto Function Calling o documenta por Streamable HTTP (não SSE). Exija teste funcional do modelo, endpoint e SDK-alvo.
  • File Search: sem áudio/vídeo; não disponível na Live API; não combina com Search/URL Context.
  • Computer Use: Preview; modelos em §17.5.
  • Antigravity: entrada só texto/imagem; sem saída estruturada (§18.9).

22.1 Configurações de segurança

Configurações de segurança customizadas (safety_settings, com HarmCategory e HarmBlockThreshold) são suportadas diretamente em interactions.create. Para fluxos agênticos com ferramentas arriscadas (como Computer Use), a Interactions API expõe também o campo safety_decision (ex.: require_confirmation) — implemente HITL conforme a §17.5.

23. Práticas recomendadas

  • Use previous_interaction_id em vez de reenviar histórico — ativa cache implícito e reduz custo.
  • Para Deep Research, combine com modelo padrão depois: faça polling até completed e use previous_interaction_id num Gemini Flash para resumir.
  • Coloque conteúdos grandes (PDF, documento) no início do prompt para maximizar cache hits.
  • Para multimodal de uma imagem ou PDF curto, posicione o prompt de texto depois da mídia.
  • Em streaming de function calling, acumule arguments_delta e só faça JSON.parse após step.stop.
  • Em modo store=false, NUNCA modifique blocos thought ou suas signature — reenvie exatamente como recebido.
  • Implemente retry com backoff em service_tier: flex; monitore o tier efetivo de Priority via header x-gemini-service-tier.
  • Em webhooks, valide webhook-timestamp (≤5 min) e use webhook-id para deduplicação.
  • Trate eventos SSE desconhecidos com log + skip, não como erro.

23.1 Prompt design para Gemini 3.x e 4 (recomendações oficiais)

A lista abaixo resume o guia oficial de prompt design na parte específica para as famílias Gemini 3.x e 4 — que é a que este guia usa (gemini-3.8-flash, gemini-4-argon). Ele complementa, não substitui, as práticas de API acima.

  • Seja preciso e direto; evite linguagem persuasiva. Gemini 3.x/4 responde melhor a instrução objetiva do que a apelos retóricos ("é crucial que você...").
  • Escolha um único estilo de delimitador estrutural por prompt — tags XML (<role>, <constraints>, <context>, <task>) ou headings Markdown (\# Identity, \# Constraints, \# Output format) — e não misture os dois no mesmo prompt.
  • Persona, formato de saída e restrições críticas vão na system_instruction ou no início do prompt, nunca soltos no meio da entrada.
  • Contexto longo: coloque todo o material de referência (documentos, PDFs) primeiro e a pergunta/instrução por último, com uma frase-ponte como "Com base nas informações acima...". Isso também maximiza o cache hit rate implícito descrito acima.
  • Verbosidade é baixa por padrão. Tom conversacional precisa ser pedido explicitamente via system_instruction.
  • Raramente é preciso pedir chain-of-thought explícito. Como o modelo já gera thought steps internamente (ver §15), um simples "pense bem antes de responder" já ajuda em problemas difíceis, ao custo de mais tokens de pensamento — não escreva um roteiro de raciocínio passo a passo manual.
  • Multimodal: trate texto, imagem, áudio e vídeo como entradas de mesma classe e referencie cada uma explicitamente no prompt (ex.: "na imagem acima" / "no trecho de áudio entre 0:10 e 0:20").
  • Sampling: a doc recomenda manter temperature/top_p/top_k nos valores padrão para modelos Gemini 3.x — alterá-los pode causar looping ou degradação em tarefas de raciocínio. Para gemini-4-argon, esses parâmetros são ignorados se fornecidos; no Antigravity, retornam erro 400. A recomendação oficial é não os enviar e controlar o esforço por thinking_level.
  • Agentes: para prompts agênticos (Deep Research, Antigravity, custom agents), a doc recomenda configurar explicitamente três eixos no system_instruction: raciocínio/estratégia (decomposição, profundidade de diagnóstico), execução/confiabilidade (persistência, avaliação de risco — diferenciar leitura de baixo risco vs. escrita de alto risco) e interação/saída (como tratar ambiguidade, verbosidade, quando pedir confirmação humana).

Fonte: ai.google.dev/gemini-api/docs/prompting-strategies.

generateContent: quando ainda usar

A Interactions API é a interface padrão da Gemini API (GA desde junho/2026). A API generateContent original permanece suportada como alternativa legada para os três casos de uso que a Interactions ainda não cobre. Fontes: migrate-to-interactions e deprecations.

Lacunas que ainda exigem generateContent

Três recursos específicos só existem atualmente na API generateContent:

  • Batch API assíncrona (client.batches / :batchGenerateContent; desconto de 50% nos preços de inferência).
  • Cache de contexto explícito (client.caches.create + cached_content). Na Interactions API o cache é implícito via previous_interaction_id.
  • Chamada automática de função em Python (passar funções Python diretamente em tools para execução automática pelo SDK). Na Interactions API o desenvolvedor gerencia o loop de function_call e function_result (§13.3).

Nota sobre segurança: safety_settings personalizados são suportados diretamente na Interactions API. É permitido misturar as duas APIs no mesmo projeto. O SDK google-genai versão 3.0 removerá a AFC via chamadas diretas legadas e Live.send, por isso mantenha o pin < 3.0.0 (§2.2).
