Arquitetura & Orquestração de Agentes

O capítulo de fundação do núcleo agnóstico: como projetar o runtime que decide, a cada ciclo, qual contexto projetar, qual modelo chamar, quais capabilities expor, como validar chamadas, como reduzir resultados e como registrar evidência. Vale para qualquer provider (OpenAI, Anthropic, Google) e qualquer framework de agentes. Os outros capítulos do núcleo — estado, ferramentas, providers e operação — usam o vocabulário definido aqui.

Faça / Não faça

  • Não trate Agents SDK, Agents API e uma conversa Responses com previous_response_id como sinônimos → três routes distintas (§8).
  • Não use o provider como banco de estado → ledger canônico externo; o payload do provider é projeção.
  • Não use handoff quando basta delegar → agent-as-tool (o parent continua no comando); handoff só para mudança de ownership.
  • Não deixe o subagente devolver transcript bruto → output_schema, provenance, status e lacunas.
  • Não abra fan-out sem limite → max_fanout, timeout, join, cancelamento e budget por escopo.
  • Não repita mutação após timeout sem idempotency key.
  • Não envie segredos, tokens de tenant ou autorização pelo prompt; MCP e A2A não autorizam por si.
  • Não use Assistants API (encerrada 2026-08-26) → Responses + Conversations; Agent Builder (shutdown 2026-11-30) → Agents SDK + servidor próprio.
  • Não use langgraph.prebuilt.create_react_agent nem langgraph-supervisor (repo arquivado) → langchain.agents.create_agent (prompt= vira system_prompt=).
  • Não comece trabalho novo em ADK 1.x nem em vertexai.agent_engines → ADK 2.x e agentplatform.Client().runtimes (Agent Runtime).
  • Não use Gemini generateContent/google-generativeai como rota agentic → Interactions API via google-genai.
  • Não use A2A 0.3 (kind, /v1 no REST) → a2a-sdk>=1.0; não use o handshake MCP initialize/Mcp-Session-Id (Legacy) → spec 2026-07-28.
  • Não conclua que uma rota gerenciada (Agents API, multi-agente hospedado, Managed Agents) é portátil → declare o que o runtime deixa de controlar e mantenha fallback testado.
  • Para runs ZDR estritos não use a Agents API → Agents SDK auto-hospedado ou Responses direta.
  • Não misture built-ins, funções externas com side effects e síntese no mesmo boundary (paralelismo sem fase).

Sobre este guia

Este é um guia para IA e humanos: combina decisões de arquitetura ("quando usar o quê") com contratos tipados prontos para copiar (capability registry, active plan, delegation packet, skeleton de loop). Toda a prosa é em PT-BR; nomes de classes, parâmetros e código permanecem em inglês, como nas APIs oficiais.

Regra de desenho que atravessa todo o núcleo: o modelo pode planejar e solicitar ações, mas o runtime governa autorização, execução, limites, persistência, redaction e replay. O payload enviado ao provider é sempre uma projeção reconstruída do seu estado durável — nunca a fonte única da verdade.
Princípio agnóstico: nada neste capítulo depende de um provider específico. As decisões valem se você orquestra com a Responses API da OpenAI, a Messages API da Anthropic, o google-genai ou um framework como OpenAI Agents SDK, LangGraph ou Google ADK. A camada de adapter (capítulo de providers) traduz estes contratos para cada API.
O que este capítulo não faz: ele não reescreve a referência de cada framework nem repete contagem de tokens, compaction detalhada ou parâmetros de provider. Quando o assunto já tem guia dedicado, há um cross-link. Veja o mapa do núcleo.

Parte 1 — Fundamentos

O vocabulário e os mapas de decisão que sustentam todo o restante: o que é um sistema agentic, quais são as peças que você combina e como escolher entre elas.

1. Escopo universal de orquestração

Um sistema agentic universal não é "um chatbot com ferramentas". É um runtime que decide, em cada ciclo, qual contexto projetar, qual modelo chamar, quais capabilities expor, como validar chamadas, como reduzir resultados e como registrar evidência. A unidade de projeto não é a mensagem isolada; é o turn bundle: instruções, histórico projetado, assets, tools, planos ativos, políticas, budgets, traces e estado de execução.

Decisão do modelo × decisão do código × política da organização. Um runtime SOTA separa explicitamente os três. O modelo decide o conteúdo da resposta e quais ações pedir; o código decide se, quando e como executar; a política define retenção, aprovação, quotas e fronteiras. Misturar os três no prompt é a origem da maioria das falhas de segurança e custo.

O OpenAI Agents SDK documenta dois estilos centrais de orquestração: deixar o LLM orquestrar com tools e handoffs, ou orquestrar por código para mais determinismo. A arquitetura universal deve permitir misturar os dois, com fronteiras explícitas — e é exatamente isso que os primitivos abaixo viabilizam.

Fonte oficial: openai.github.io/openai-agents-python/multi_agent (orquestração via LLM vs via código).

3. Arquitetura de referênciaAtualizado · 2026-09-30

A figura abaixo separa as quatro camadas que nunca devem ser confundidas. Trocar de provider, reduzir contexto, auditar tools e manter invariantes só é possível quando o estado real vive no runtime, e o payload do provider é tratado como projeção.

Detalhe de cada camada: o ledger canônico tem capítulo próprio (Estado, contexto & memória); o capability registry e os adapters também (Ferramentas, MCP & RAG e Providers & adapters). Aqui interessa apenas a relação entre elas.

4. Matriz de escolha: agent, workflow, agent-as-tool ou handoff

A primeira decisão de arquitetura é a topologia. Use a situação concreta — não a preferência por "ser agêntico" — para escolher.

SituaçãoEscolha recomendadaCritério operacional
Etapas conhecidas, dados sensíveis, pouca ambiguidadeWorkflow determinístico com chamadas LLM pontuaisMinimiza variabilidade e simplifica auditoria.
Tarefa exploratória, baixo risco e tools segurasAgent com loop controladoLimitar max turns, allowed tools, budgets e final reserve.
Especialista precisa analisar um subproblema e devolver sínteseAgent-as-toolO parent mantém a conversa; o child recebe pacote mínimo e retorna envelope reduzido.
O usuário deve passar para outro especialista/fluxo ativoHandoffA nova entidade assume o controle com contexto mínimo e consentimento quando necessário.
Integração reusável por muitos hostsMCP server/tool/resourceSchemas, auth, rate limits e escopo explicitados fora do prompt.
Consulta de conhecimento com provenanceRAG como capability/toolA tool retorna trechos, citações, score, freshness e limites de confiança.
Operação com side effect financeiro/legal/externoTool com HITL ou workflow aprovadoO modelo nunca autoriza sozinho; o runtime valida e pede aprovação.
Agent-as-tool ≠ handoff. A confusão entre os dois é tão comum que tem seção própria (§8). Em resumo: agent-as-tool é delegação subordinada; handoff é transferência de ownership.

4A. Catálogo de padrões de workflow (Anthropic)

A matriz acima escolhe entre famílias de topologia. Quando a escolha recai sobre um workflow (caminho orquestrado por código, não pelo próprio LLM), o ensaio "Building Effective Agents" da Anthropic cataloga um conjunto de padrões de composição, do bloco básico (augmented LLM) até a fronteira com agentes autônomos. Vale conhecê-los explicitamente para não transformar todo problema em "um agente".

#PadrãoO que faz
4A.1Prompt chainingDecompõe a tarefa em passos sequenciais fixos; cada chamada de LLM processa a saída da anterior, com gates opcionais entre elas.
4A.2RoutingClassifica a entrada e a direciona para o fluxo ou prompt especializado adequado.
4A.3ParallelizationExecuta subtarefas pré-definidas em paralelo — por sectioning (partes independentes) ou voting (várias tentativas agregadas). Detalhado em §4A.3.1.
4A.4Orchestrator-workersUm orquestrador decompõe dinamicamente a tarefa, delega a workers e sintetiza os resultados. A diferença-chave para parallelization é a flexibilidade — as subtarefas não são pré-definidas, mas determinadas pelo orquestrador com base na entrada específica.
4A.5Evaluator-optimizerLoop de refinamento entre um LLM gerador e um LLM avaliador (detalhado abaixo).

Além desses workflows compostos está o padrão agente: sistemas em que os LLMs "dynamically direct their own processes and tool usage, maintaining control over how they accomplish tasks" — em vez de seguir um caminho de workflow pré-definido.

4A.5 Evaluator-optimizer

No evaluator-optimizer, nas palavras da Anthropic, "one LLM call generates a response while another provides evaluation and feedback in a loop": uma chamada de LLM gera a resposta, uma segunda chamada avalia essa resposta e devolve feedback, e o ciclo se repete até a saída ser aceita. A Anthropic descreve o padrão como análogo ao processo iterativo de escrita pelo qual um autor humano passa ao produzir um documento polido: um papel gera, outro critica, e o gerador refina a partir da crítica.

ElementoPapel no loop
LLM geradorProduz a resposta inicial e cada refinamento subsequente, incorporando o feedback recebido na rodada anterior.
LLM avaliadorExamina a resposta contra critérios de aceite explícitos e retorna aceite ou crítica específica e acionável.
Critério de paradaAceite do avaliador — o runtime deve impor também um teto de iterações para evitar loop sem convergência.
Quando usar. A Anthropic aponta que o padrão é particularmente eficaz quando há critérios de avaliação claros e quando o refinamento iterativo agrega valor mensurável. O bom encaixe aparece quando as respostas do LLM melhoram de forma demonstrável com feedback articulado e o próprio LLM consegue gerar esse feedback. Exemplos citados: tradução literária, em que "there are nuances that the translator LLM might not capture initially, but where an evaluator LLM can provide useful critiques"; e tarefas de busca complexa que exigem múltiplas rodadas de pesquisa e análise, em que o avaliador decide se novas buscas são necessárias.
Onde não vale a pena. Sem critério de aceite objetivo, o avaliador apenas introduz latência e custo (duas chamadas por rodada) sem convergência garantida. Trate o evaluator-optimizer como caso especial de separação generator-verifier: mantenha os dois papéis com prompts/instruções distintos (idealmente modelos ou temperaturas diferentes) para reduzir o viés de um único LLM validar o próprio output, e imponha o mesmo teto de iterações e budget que qualquer outro loop do runtime (ver §7 e §10).

4A.3.1 Parallelization: sectioning versus voting/consensus

Parallelization é o padrão de workflow em que múltiplas chamadas de LLM trabalham simultaneamente sobre uma tarefa e têm suas saídas agregadas de forma programática (não por "mais uma chamada de LLM" solta). Ele tem duas variações com propósitos distintos — confundi-las é o erro mais comum ao desenhar o padrão: sectioning quebra a tarefa em subtarefas independentes executadas em paralelo; voting (consenso) roda a mesma tarefa várias vezes para obter saídas diversas e agregá-las.

Não confundir com paralelismo de tool-calls. Esta seção trata do padrão arquitetural de workflow (fan-out de chamadas de LLM + fan-in programático). O paralelismo de ferramentas dentro de um único turno — protocolo por provider, scheduler, quais tools são paralelas ou seriais — é assunto do guia Paralelismo & tools.
VarianteDefinição (Anthropic)Quando usarExemplos oficiais
Sectioning Quebrar uma tarefa em subtarefas independentes, cada uma rodando em paralelo numa chamada de LLM separada ("Breaking a task into independent subtasks run in parallel"). A tarefa tem considerações distintas que ganham foco quando isoladas — LLMs geralmente performam melhor quando cada consideração é tratada por uma chamada de LLM separada — ou quando velocidade é o objetivo e as subtarefas podem rodar simultaneamente. Guardrails: uma instância de modelo processa a consulta do usuário enquanto outra, em paralelo, faz a triagem de conteúdo inadequado — separar as duas funções tende a performar melhor do que uma única chamada acumulando guardrail e resposta principal. Automatizar evals: cada chamada de LLM avalia um aspecto diferente do desempenho do modelo para um dado prompt.
Voting / consensus Rodar a mesma tarefa múltiplas vezes para obter saídas diversas ("Running the same task multiple times to get diverse outputs"), depois agregar por maioria, threshold ou síntese. A tarefa se beneficia de múltiplas perspectivas independentes para aumentar a confiança no resultado, ou quando é preciso equilibrar falsos positivos e negativos ajustando o threshold de votos. Revisão de código em busca de vulnerabilidades: vários prompts diferentes revisam e sinalizam o código quando encontram um problema. Moderação de conteúdo: avaliar se um conteúdo é inadequado usando múltiplos prompts que checam aspectos distintos ou exigem thresholds de votação diferentes, equilibrando falsos positivos e negativos.

A escolha entre as duas não é estética: sectioning otimiza cobertura e latência (subtarefas diferentes, sem redundância de trabalho); voting otimiza confiança e robustez (mesma tarefa repetida, com redundância deliberada para reduzir variância e capturar divergências entre execuções). Ambas exigem um passo de agregação determinístico e auditável no orquestrador — nunca delegado a "mais uma chamada de LLM" sem critério explícito de combinação (maioria simples, threshold configurável, união de achados, ou síntese com política definida).

Antipadrão relacionado — "Paralelismo sem fase" (§10): misturar sectioning e voting no mesmo boundary, ou paralelizar sem separar claramente a fase de fan-out (disparo das chamadas) da fase de fan-in (agregação), gera resultados inconsistentes e dificulta a auditoria — especialmente em voting, onde o critério de combinação dos votos precisa ser registrado no ledger para permitir replay.
Fontes oficiais: anthropic.com/engineering/building-effective-agents (seções "Parallelization" & "Evaluator-optimizer") · docs.langchain.com/oss/python/langgraph/workflows-agents.

Parte 2 — Contratos do runtime

Os artefatos tipados que tornam a orquestração auditável e portável: o registry de capabilities, o estado de plano, o loop e os modos de delegação.

5. Contrato de capability registry

Toda ferramenta, subagente, handoff ou endpoint MCP deve ser registrado como uma capability com metadados suficientes para roteamento, segurança e avaliação. O registro não deve depender de nomes naturais no prompt — depende de um contrato. 

{
  "capability_id": "retrieve_domain_evidence.v1",
  "kind": "mcp_tool | a2a_task | function_tool | agent_as_tool | handoff | provider_builtin",
  "route": "provider_route_or_protocol_version",
  "description_for_model": "Recupera evidências com proveniência e limites de confiança.",
  "input_schema":  { "type": "object", "properties": {} },
  "output_schema": { "type": "object", "required": ["summary", "citations", "confidence"] },
  "capabilities_required": ["structured_output", "citations"],
  "loss_declaration": { "status": "preserved | transformed | unavailable", "notes": [] },
  "side_effect_level": "none | read | write_low | write_high",
  "authorization": { "scope": "derived_from_runtime_not_model", "approval": "policy_or_human" },
  "tenant_boundary": "required",
  "concurrency": { "class": "parallel_read | serial | serial_by_resource", "max_fanout": 4 },
  "retry": { "transient_only": true, "max_attempts": 2, "backoff": "bounded" },
  "idempotency": { "required_for_write": true, "key_source": "runtime" },
  "max_input_tokens": 2000,
  "max_output_tokens": 1200,
  "timeout_ms": 15000,
  "approval_policy": "auto | human_required | forbidden",
  "observability": ["trace_span", "cost", "source_hashes", "tool_args_redacted"]
}

O mesmo contrato suporta ferramentas locais, MCP, A2A, RAG, agentes especializados e built-ins; o adapter converte para o formato aceito por cada rota e registra capacidades preservadas, transformadas ou indisponíveis. O scheduler continua sendo a autoridade sobre autorização, fan-out, locks, retries e idempotência. As regras de design do schema de tool (nomes, descrições, caps de output) e o envelope de resultado estão no capítulo de ferramentas.

Por que auth_scope deriva do runtime: se o escopo de autorização viesse do modelo, um prompt injection em um documento poderia escalar privilégio. O runtime resolve tenant e scope a partir de claims autenticados, nunca a partir do texto.

6. Microcontextos & active plan

Dois padrões evitam que o contexto do parent vire um depósito e que o raciocínio fique implícito:

PadrãoO que éPor que importa
MicrocontextoSubexecução isolada com input mínimo, policy, budget, tools permitidas e envelope de retorno.Evita que subagentes herdem todo o histórico — só entram fatos necessários, assets autorizados e schema de saída.
Active planEstado explícito do que está em andamento: objetivo, etapas, pendências, constraints, decisões e condição de finalização.Substitui raciocínio implícito por estado auditável, com budgets e gates.
Delegation packetPacote tipado para agent-as-tool/handoff/MCP: tarefa, contexto reduzido, constraints, capabilities, output contract e trace do parent.Torna a delegação verificável e impede vazamento de contexto.

O active plan vive no ledger e é reprojetado a cada turno:

{
  "active_plan": {
    "goal": "produzir resposta verificável",
    "stage": "collect_evidence | analyze | synthesize | finalize",
    "open_questions": [],
    "constraints": ["não vazar dados sensíveis", "citar fontes"],
    "budgets": { "turns_remaining": 3, "tool_calls_remaining": 8, "tokens_remaining": 24000, "max_fanout": 4 },
    "context_health": { "source_hashes": [], "critical_facts": [], "compaction_count": 0, "retention_check": "required" },
    "finalization_policy": { "reserve_tokens": 4000, "reserve_seconds": 20 }
  }
}
Budgets aparecem aqui e no ledger. A fórmula de orçamento de contexto (entrada projetada + reasoning + saída final + margem) e a contagem de tokens em si pertencem ao capítulo de estado e ao guia de token counting. Aqui o budget é apenas uma propriedade do plano que o loop respeita.

7. Skeleton de orquestrador

O loop é intencionalmente provider-neutral: registrar, validar, executar, reduzir e reprojetar. Um framework de agentes pode gerenciar boa parte deste loop; quando o projeto exige controle fino, implemente-o sobre a API direta do provider e adapters próprios. 

from dataclasses import dataclass
from typing import Any

@dataclass
class TurnPolicy:
    allowed_capabilities: list[str]
    max_agent_turns: int
    max_tool_calls: int
    max_fanout: int
    final_reserve_tokens: int
    require_human_for: list[str]
    retry_budget: int = 2

async def run_agent_turn(user_input: str, ledger, policy: TurnPolicy, adapter) -> dict[str, Any]:
    ledger.record_user_input(user_input)
    projected = ledger.project_for_route(
        route=adapter.route_id,                # rota explícita; não inferir pelo nome do modelo
        allowed_capabilities=policy.allowed_capabilities,
        reserve_tokens=policy.final_reserve_tokens,
    )
    for _step in range(policy.max_agent_turns):
        response = await adapter.invoke(projected)
        ledger.ingest_provider_response(response)
        calls = adapter.normalize_tool_calls(response, limit=policy.max_tool_calls)
        if not calls:
            return ledger.final_answer()
        safe_calls = authorize_and_validate(calls, policy, ledger)  # claims do runtime, nunca do modelo
        results = await execute_with_policy(
            safe_calls,
            max_fanout=policy.max_fanout,
            retry_budget=policy.retry_budget,
            retry_only=lambda call: call.is_transient and (
                call.spec.side_effect_level in {"none", "read"} or call.has_idempotency_key
            ),
            idempotency_key=lambda call: ledger.idempotency_key(call),
            fail_closed_on_unknown=True,
        )
        ledger.record_tool_results(adapter.reduce_results(results))
        projected = ledger.project_for_route(route=adapter.route_id)
    return ledger.force_wind_down_summary()                # respeita o final reserve
Mesmo quando o framework gerencia o loop, mantenha registro externo de traces, usage, tool results e decisões críticas se o sistema precisa ser auditável. O mapeamento deste skeleton para cada framework está nos guias de Agents SDK, LangGraph e Google ADK.

8. Handoff versus agent-as-tool em detalheAtualizado · 2026-09-30

Agent-as-tool é delegação subordinada: o parent formula a tarefa, envia um pacote mínimo e consome o retorno. Handoff é transferência de ownership: o agente-alvo vira a entidade ativa e deve receber contexto suficiente para continuar. Confundir os dois aumenta o risco de vazamento de contexto e de loops.

DimensãoAgent-as-toolHandoff
Controle da conversaPermanece com o parent.Passa para o target.
Contexto enviadoMínimo e específico da tarefa.Resumo de continuidade + consentimentos/políticas.
Output esperadoEnvelope tipado e reduzido.Nova interação ou resolução no fluxo alvo.
Uso típicoPesquisa, análise, extração, validação.Especialista ativo, humano, atendimento, workflow setorial.
Risco principalO child retornar demais.Transferir dados/autoridade demais.
Implementações concretas (verificado em 2026-09-30):
  • OpenAI Agents SDK (openai-agents 0.22.3): handoffs, agents-as-tools, filtros de input e collapse de transcript — guia do Agents SDK.
  • LangChain/LangGraph (langchain 1.4.3, langgraph 1.2.12): langchain.agents.create_agent com subagentes expostos como @tool — o padrão supervisor direto, que substitui langgraph-supervisor (repositório arquivado) — e handoffs via tools/Command; ver orquestração em LangGraph e LangGraph.
  • Google ADK (google-adk 2.10.0): workflows em grafo (graph/dynamic/collaborative), coordenador + subagentes e RemoteA2aAgent para A2A; deploy gerenciado no Agent Runtime (multiagente com A2A ainda em preview); ver orquestração no ADK e Google ADK.
Rotas gerenciadas não são uma capacidade portátil. Uma API de execução de modelo, um recurso de conversa e um harness de agentes hospedado podem ter nomes parecidos, mas contratos, retenção, autorização, observabilidade e ciclo de vida diferentes. A Responses API/Conversations da OpenAI, a Interactions API do Google e Messages/Agent SDK ou Managed Agents da Anthropic devem ser registrados como routes distintas; não conclua que um adapter possui multi-agent apenas por existir um SDK ou um recurso beta. Quando a orquestração fica hospedada, declare explicitamente o que o runtime deixa de controlar (fan-out, contexto, retries, aprovação, dados) e mantenha uma saída compatível ou um fallback testado.
A OpenAI tem DUAS rotas chamadas "Agents", e não são o mesmo produto. A Agents SDK (openai-agents, biblioteca open-source) é a rota que os guias de framework documentam: você hospeda o loop — runner, handoffs, guardrails, sessões — na sua arquitetura, sobre chamadas à Responses API. A Agents API é um serviço gerenciado em beta pública desde 2026-09-10 que roda o harness do Codex na infraestrutura da OpenAI: sessão, compactação de contexto, recuperação de falha e delegação a subagentes ficam do lado do servidor. Blocos: agent (modelo/instruções/tools/MCP), environment (none | openai_hosted | self_hosted), session (durável) e events/items; endpoint POST /v1/agents/sessions com o header OpenAI-Beta: agents=v1; computer use hospedado desde 2026-09-29. Uma sessão da Agents API, uma sessão da Agents SDK e uma conversa da Responses com previous_response_id são três recursos diferentes — registre-os como três routes distintas, nunca como sinônimos. Regra prática: Agents API quando o objetivo é operar menos harness; Agents SDK quando possuir e customizar o harness é requisito. A Agents API não suporta ZDR (nem com sandbox self-hosted) e retém dados só nos EUA — para runs ZDR-estritos, use a Agents SDK auto-hospedada ou a Responses direta. Há ainda o multi-agente hospedado da própria Responses (beta; GPT-6.1 Sol e todos os GPT-5.6), em que o modelo raiz coordena subagentes numa chamada. Do lado Anthropic, Managed Agents segue em beta (header managed-agents-2026-04-01; sem data de GA; política de permissão auto desde 2026-09-10; US$0,08 por hora-sessão + tokens), e o Claude Agent SDK é outra biblioteca: roda o binário do Claude Code no seu processo. Fontes: developers.openai.com/api/docs/guides/agents-api/overview e /responses-multi-agent; platform.claude.com/docs/en/managed-agents/overview — todos 2026-09-30.

9. Skill packs e modos de injeção

Skills devem ser versionadas, testadas e injetadas no menor escopo possível. O erro mais comum é carregar tudo sempre — isso degrada o contexto, aumenta o custo e cria conflitos de instrução. Os modos de injeção são uma decisão de arquitetura; a autoria das skills (formato SKILL.md, progressive disclosure, ativação por description) tem guia próprio.

ModoDescriçãoQuando usar
catalog_onlyO modelo vê apenas nomes/descrições de skills.Muitos recursos disponíveis, mas poucos necessários por turno.
hot_dynamicO runtime injeta o corpo completo da skill só quando relevante.Especialização contextual sem poluir o prompt base.
pinned_systemSkill crítica fica sempre nas instruções.Regras de segurança ou formato que nunca podem faltar.
child_frozen_packO subagente recebe um pacote fixo e isolado.Especialista repetível com contrato estável.
specialist_catalogO parent conhece especialistas e delega via agent-as-tool/handoff.Arquiteturas multiagente com fronteiras claras.
Cross-link: a autoria de skills portáveis, os contratos de ativação, o orçamento de skills e a eviction sem perder autoridade estão no Guia de Skills. A teoria de budget/compaction que sustenta o hot_dynamic está no capítulo de estado e no guia de contexto & compactação.

Parte 3 — Operação & escala

Como evitar as armadilhas conhecidas, fazer o sistema crescer sem virar cosmético, rotear modelos e modelar execuções longas — culminando no blueprint SOTA.

10. Antipadrões arquiteturais

Cada antipadrão abaixo corresponde a um invariante violado em algum lugar do núcleo:

  • ☐ Contexto bruto sem fronteira: anexar toda saída de tool/RAG/subagente no histórico do parent.
  • ☐ Provider como banco de estado: depender de previous_response_id, cache ou session como único histórico durável.
  • ☐ Tool schema permissivo: aceitar argumentos arbitrários ou filtros definidos pelo modelo sem sanitização.
  • ☐ Subagente sem envelope: permitir que o child retorne narrativa longa em vez de output tipado e reduzido.
  • ☐ Handoff opaco: transferir controle sem registrar por quê, para quem, com qual contexto e qual consentimento.
  • ☐ Paralelismo sem fase: misturar built-ins, funções externas, side effects e síntese no mesmo boundary.
  • ☐ Fan-out sem orçamento: deixar o modelo ou um subagente abrir tarefas sem limite por request, tenant, provider e recurso.
  • ☐ Contrato de child implícito: delegar sem input_schema, output_schema, deadline, cancelamento e status desconhecido.
  • ☐ Retry de mutação incerta: repetir após timeout sem idempotency key e sem distinguir falha antes da execução de resultado desconhecido.
  • ☐ Context rot ignorado: aumentar o histórico sem medir retenção dos fatos críticos, proveniência e fidelidade da compactação.
  • ☐ Sem wind-down: continuar abrindo tools quando o orçamento da resposta final já acabou.
O antipadrão mais caro costuma ser "provider como banco de estado": quando um incidente exige replay e o histórico só existia no lado do provider (sujeito a retenção, ZDR e expiração de cache), a auditoria fica impossível. O ledger canônico existe para evitar isso — ver Estado, contexto & memória.

13. Long-running jobs e deep research

Execuções longas devem ser modeladas como jobs, não como uma conversa gigante. Um job tem estado persistido, etapas, checkpoints, retries, evidência acumulada, budgets e condição de encerramento.

  • ☑ Persistir o estado do job fora do provider.
  • ☑ Registrar checkpoints e permitir replay parcial.
  • ☑ Definir budget por etapa, não apenas global.
  • ☑ Reduzir evidências antes de cada síntese intermediária.
  • ☑ Encerrar com declaração de cobertura, lacunas e fontes.
  • ☑ Se o usuário acompanha o job por streaming (fecha/volta, reconexão, replay de eventos, timestamps do 1º token), a camada de entrega é o guia Streaming Durável & Resumível — event store com seq, Last-Event-ID, executor durável e failover como nova tentativa.
Implementações de deep research e background jobs (com webhooks, retomada e modo assíncrono) estão nos guias de provider/framework: Deep Agents (receita de deep research), Gemini Interactions API (Deep Research, background & webhooks) e OpenAI (background & webhooks).

Checklist de aceitação arquiteturalAtualizado · 2026-09-30

Use como gate antes de promover qualquer arquitetura de agentes para produção:

  • ☐ Existe um ledger canônico separado dos payloads de provider.
  • ☐ Cada capability tem route, input/output schema, side-effect level, auth scope, budget, retry/idempotency e policy de aprovação.
  • ☐ O adapter expõe uma matriz de capacidades e uma loss declaration; Responses/Conversations, Interactions e Messages/Agent SDK não são intercambiáveis por nome.
  • ☐ MCP (host ↔ tool/resource/prompt) e A2A (agent ↔ agent/task) foram escolhidos para a fronteira correta, com identidade e autorização verificadas.
  • ☐ Agent-as-tool e handoff usam delegation packet, I/O tipado, deadline, cancelamento e envelope de retorno.
  • ☐ O sistema separa as fases de recuperação, ação, análise e síntese.
  • ☐ O modelo nunca recebe segredos, tokens de tenant ou autorização "por prompt".
  • ☐ Há limites explícitos para turns, tool calls, fan-out por escopo, fila/backpressure, tempo, tokens, output e custo.
  • ☐ Retry só ocorre em falhas transitórias e operações idempotentes; mutações têm chave idempotente e circuito aberto/half-open.
  • ☐ Context health mede compactação, proveniência e retenção de fatos críticos; o plano falha fechado quando a retenção é desconhecida.
  • ☐ Evals reportam processo (tool/auth/retry/handoff/contexto) separado do outcome (correção, segurança, latência e custo); planos difíceis têm cenário determinístico ou replay.
  • ☐ Traces e usage ledger permitem replay ou auditoria sem depender do provider.

Notas de verificaçãoAtualizado · 2026-09-30

Afirmações perecíveis deste capítulo, conferidas em 2026-09-30 nas fontes oficiais listadas em Fontes & verificação e em PyPI/npm/GitHub Releases. O capítulo mantém só invariantes de arquitetura; IDs de modelo, limites e parâmetros ficam nos guias de provider.

  • Resolvido Rotas de provider. OpenAI: Responses (execução) e Conversations (estado) são recursos distintos; parallel_tool_calls/max_tool_calls são controles da chamada, não política per-tool do runtime. Google: a Interactions API é GA desde junho de 2026 e é a rota recomendada (a rota antiga está em Legado e migração). Anthropic: Messages é a API direta e stateless; Agent SDK e Managed Agents são outros harnesses.
  • Resolvido Agents SDK × Agents API × Responses. Agents API: beta pública desde 2026-09-10, POST /v1/agents/sessions com OpenAI-Beta: agents=v1, sem ZDR, residência de dados só nos EUA; computer use hospedado desde 2026-09-29. Multi-agente hospedado da Responses: beta, suportado por GPT-6.1 Sol e todos os GPT-5.6. Managed Agents (Anthropic): beta (managed-agents-2026-04-01), sem GA.
  • Resolvido Protocolos. MCP corrente = 2026-07-28; 2025-11-25 é Legacy. A2A: spec 1.0, repositório v1.0.1, a2a-sdk 1.2.1. Uma versão de spec não prova adoção pelo SDK: alguns adapters ainda pinam mcp 1.x (ex.: langchain-mcp-adapters, CrewAI); ADK 2.10.0 e openai-agents 0.22.3 aceitam mcp<3. Matriz em Protocolo MCP §3.
  • Resolvido Frameworks. Versões e APIs correntes em §11; migrações em Legado e migração.
  • Pesquisa Context rot/LOCA-bench, AHE, Memento, APB, ContextBench e OrchBench informam o checklist, não a compatibilidade de provider: meça retenção de fatos críticos, transferências, processo e outcome separadamente, com fan-out, orçamento, circuit breaker e replay determinístico quando possível.
  • UNVERIFIED Suporte de Astra/6 Sol/6 Luna ao multi-agente hospedado da Responses (o guia da API cita só GPT-6.1 Sol e GPT-5.6); política formal de EOL do ADK 1.x; sunset de langgraph-swarm. Nenhum exemplo foi executado neste corte.
