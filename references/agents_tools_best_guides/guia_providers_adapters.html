Faça / Não faça

  • Faça: pisos de segurança no lockfile: mcp>=2.2.0 (ou >=1.30.0), litellm>=1.103.1, claude-agent-sdk>=0.2.121, pydantic-ai>=2.52.0; lista completa em Operação, Segurança & Evals.
  • Faça: fixe google-genai<3.0.0 (o README oficial avisa que a 3.0 tira o AFC de Models.generate_content).
  • Faça: OpenAI stateless/ZDR com store=false e devolva os output items; previous_response_id e conversation são mutuamente exclusivos.
  • Faça: Gemini: reenvie tools, system_instruction e generation_config a cada interação; devolva steps thought/function_call intactos (assinaturas) e responda com function_result + call_id.
  • Faça: Claude: adaptive thinking + output_config.effort (refaça o sweep por modelo); para forçar tool, tool_choice: auto + strict tool use ou structured output.
  • Faça: structured output por provider: OpenAI text.format, Anthropic output_config.format, Gemini response_format; valide localmente sempre (§7).
  • Faça: registre a rota real de cada adapter no provider_switch e declare perdas; bloqueie a conversão de reasoning opaco/assinaturas em texto.
  • Não use Chat Completions em projeto novo: gpt-6-astra e gpt-6.1-sol só a aceitam sem tools. Não use Assistants API (encerrada em 2026-08-26) → Responses + Conversations.
  • Não envie reasoning.effort: "none" a gpt-6-astra ou gpt-6.1-sol (400; o 6.1 Sol também não aceita minimal); com effort ≠ none, remova temperature/top_p.
  • Não use em Fable 5.1, Opus 5.5 ou Sonnet 5.5: thinking disabled ou enabled+budget_tokens (400; no Sonnet 5.5 use {"type":"between_tools"}), temperature/top_p/top_k não-default (400 desde o Opus 4.7), tool_choice any/tool (400), computer_20251124 (→ computer_toolset_20260801), output_config.format com citations (400).
  • Não use response_format (padrão OpenAI) na Anthropic: o campo é output_config.format.
  • Não use generateContent, google-generativeai, outputs[] nem thinking_budget no Gemini 3; thinking_level: "minimal" retorna erro no gemini-3.8-flash; store=false não combina com background=true. Exceções do generateContent em Legado.
  • Não suponha Interactions em Pydantic AI, Vercel, LiteLLM, CrewAI ou Instructor (não documentado); só o ADK documenta (use_interactions_api=True). Prefixo openai: do Pydantic AI 2.x já é Responses.

Sobre este guiaAtualizado · 2026-09-30

Este capítulo do núcleo trata a aplicação como dona de um contrato canônico e cada provider como uma projeção desse contrato. O objetivo não é reexplicar a API de cada provedor — é dar o adapter que converte um modelo canônico (ledger, capabilities, schemas, roles) para rotas explicitamente identificadas: OpenAI Responses e seu recurso Conversations, Anthropic Messages ou Agent SDK/Managed Agents, e Google Interactions. Cada combinação tem capacidades, estado, retenção, tool loop e perdas diferentes; o adapter não pode selecionar uma rota apenas pelo nome do modelo.

Para IA e humanos: use as tabelas como referência de consulta (parâmetros, roles, comportamento por provider) e os contratos JSON como esquema copy-paste. Cada afirmação perecível (IDs de modelo, nomes de parâmetro, versão de spec) é conferida na seção Notas de verificação contra as fontes oficiais ali listadas.
Onde aprofundar cada API: parâmetros completos da Responses API → guia_openai_modelos; Messages API e blocos de tool/thinking → guia_claude_api; Interactions API e google-genai → guia_gemini_interactions_api; runtime do Agents SDK → guia_agents_sdk e guia_agents_sdk_orquestracao.

A tese do adapterAtualizado · 2026-09-30

Trocar de provider deve ser uma operação declarada, nunca transparente. Um sistema que "só troca o nome do modelo" mente para si mesmo: roles não têm equivalência perfeita, carriers de reasoning são opacos e específicos, budgets se comportam de forma distinta e o estado servidor de um provider não existe no outro. O adapter resolve isso projetando o contrato canônico e produzindo uma loss declaration a cada conversão. 

{
  "route": "openai.responses | openai.conversations | google.interactions | anthropic.messages | anthropic.managed_agents",
  "capabilities": { "tool_loop": "client | hosted | mixed", "state": "app | provider | session", "streaming": true },
  "loss_declaration": [
    { "capability": "reasoning_carrier", "status": "preserved | transformed | unavailable", "action": "rehydrate | drop | block" },
    { "capability": "tool_parallelism", "status": "hint_only", "action": "enforce_in_scheduler" }
  ],
  "revalidation": { "contract_probe": true, "held_out_eval": true }
}

A matriz é um contrato de execução, não uma tabela de marketing: se uma capacidade requerida estiver unavailable ou a perda não tiver ação segura, o switch deve parar e pedir rota/fallback. Detalhes perecíveis ficam nos guias específicos e nas fontes oficiais.

O papel de cada camada, os parâmetros da Responses API que importam para a orquestração, e quando o Agents SDK ou o Pydantic AI entram. Detalhe completo de cada API fica nos guias dedicados.

1. Papel de cada SDK/frameworkAtualizado · 2026-09-30

Cada camada tem um papel; o erro comum é confundir um provider adapter com um banco de estado durável, ou um framework de runtime com governança de negócio. A tabela separa uso recomendado de "não confundir com".

CamadaUso recomendadoNão confundir com
OpenAI Agents SDK (openai-agents)Runtime de agentes com tools, handoffs, guardrails, sessions, tracing e MCP. Uma base de orquestração no ecossistema OpenAI.Banco de estado durável universal ou substituto de políticas de negócio; é outra camada sobre a rota do provider.
OpenAI Responses APIInterface direta para controle fino de input, tools, estado projetado, structured outputs e loop próprio.Recurso Conversations, framework de governança ou política per-tool; o cliente ainda valida, executa tools e mantém o ledger.
OpenAI ConversationsRecurso de estado/conversa que pode ser usado pela Responses; o adapter deve registrar quando o histórico vive nele.Uma chamada de inferência ou garantia de retenção/ZDR.
OpenAI Python SDK (openai)Cliente oficial para chamar a API OpenAI.Orquestrador por si só.
Anthropic SDK / Messages API (anthropic)API direta e stateless para Claude: tools (tool_use/tool_result), server tools e thinking conforme a rota/modelo.Agent SDK/Managed Agents, estado durável ou a mesma semântica de roles/tokens/reasoning da OpenAI.
Anthropic Agent SDK / Managed AgentsHarness separado para sessões/agentes gerenciados, com ciclo de vida, eventos e controles próprios.Um alias da Messages API ou um contrato portátil de subagentes.

Google GenAI SDK (google-genai)Cliente oficial; expõe client.interactions (exige 2.3.0+; o schema de steps existe desde 2.0.0).SDKs legados (google-generativeai) ou estado durável automático.
Pydantic AI (pydantic-ai)Camada complementar de agentes tipados, output estruturado, deps, evals, observabilidade e wrappers model-agnostic.Substituto obrigatório do Agents SDK; use onde agrega validação/typing/evals.
Nota transversal — AGENTS.md não é um SDK de provider, mas atravessa todos eles. Desde que a Anthropic doou o MCP à Agentic AI Foundation (ver Ferramentas, MCP & RAG §3), a mesma fundação — sob a Linux Foundation — passou a esteirar o formato de instruções de projeto AGENTS.md: um único arquivo Markdown na raiz do repositório, lido por múltiplos agentes de codificação (Codex, Jules, Aider, goose, Gemini CLI, Cursor, Windsurf e outros listados em agents.md). Claude Code lê AGENTS.md desde a versão 2.1.277 — mas só quando o projeto não tem CLAUDE.md; havendo os dois, CLAUDE.md prevalece e o AGENTS.md é ignorado (ainda não disponível em Bedrock, Vertex ou Foundry). Isso não é uma convenção de SDK ou de API — é um contrato de portabilidade de instruções entre agentes, então o adapter que decide "qual arquivo de instrução o runtime lê" deve tratá-lo como uma camada própria, sem confundir com o system/developer/instructions de cada provider descritos nas seções seguintes. 2. OpenAI Responses API: parâmetros críticosAtualizado · 2026-09-30

Para a orquestração, estes são os campos que mais influenciam controle de fase, estado e budget. A referência completa (anatomia da Responses, function calling, streaming) está em guia_openai_modelos.

Parâmetro/campoUsoCuidado
inputItens de entrada multimodais/projetados do ledger.Não jogar corpus bruto sem caps de budget.
instructionsInstruções da chamada atual.Com previous_response_id, não assuma carry-over de instructions anteriores.
toolsBuilt-ins, MCP e function tools.Exponha apenas as allowed tools da fase.
tool_choiceauto / required / específico / none.Trava fase, não é a única camada de segurança.
parallel_tool_callsPermite que o modelo emita function calls em paralelo quando a rota/modelo o suportar.É um controle de emissão da chamada; a execução, locks e política per-tool continuam no runtime, e hosted tools não viram client tools.
max_tool_callsLimite global de tool calls hospedadas na resposta.Não substitui o max turns, fan-out ou limites por capability do orquestrador.
max_output_tokensLimita tokens visíveis + reasoning conforme o modelo.Reserve orçamento para reasoning e resposta final.
previous_response_idEncadeia a resposta anterior para o próximo turn.Não é ledger; é mutuamente exclusivo com conversation na mesma chamada e não carrega automaticamente instructions anteriores.
conversationRecurso de conversa stateful gerido pelo servidor; seus itens entram na projeção da Responses.Avalie retenção/política de dados; é projeção, não fonte da verdade, e não combine com previous_response_id.
storetrue persiste a resposta (necessário p/ previous_response_id).Para ZDR/stateless, use store=false e devolva os output items; em background com ZDR, a OpenAI ainda mantém a resposta transitoriamente em disco por cerca de 10 minutos.
truncationauto / disabled.Truncation automática pode remover contexto crítico silenciosamente.
backgroundtrue roda em segundo plano: consulte por GET até sair de queued/in_progress; cancel idempotente; com streaming, retomável por starting_after.Com store=false os dados ficam cerca de 10 minutos; durabilidade de ponta a ponta é da camada 2 (Streaming durável).
reasoning.effortValores (none/minimal/low/medium/high/xhigh/max) dependem do modelo.gpt-6-astra e gpt-6.1-sol não aceitam none (400); com effort diferente de none, remova temperature/top_p.
service_tierstandard, flex, batch, fast (antes "priority"; priority segue equivalente) e ultrafast (GA para gpt-6-astra desde 2026-09-29).Disponibilidade e residência variam por modelo; ultrafast recomenda WebSocket.
context_managementCompaction no servidor ({"type":"compaction","compact_threshold":N}) compatível com store=false.Pode reduzir o reuso de cache; não combine com configuration_update nem com truncation automático.
x-request-id/request_idIdentifica a requisição para suporte e correlação.Persistir no trace redigido; não confundir correlação do provider com idempotência da tool.
Reasoning stateless (ZDR): para preservar o reasoning entre turnos sem armazenamento na retenção normal do servidor, combine store=false com include=["reasoning.encrypted_content"] e devolva o conteúdo cifrado a cada turno. Confira o nome exato do campo na doc atual da Responses API.

Família recomendada em 2026-09-30: gpt-6-astra (flagship), gpt-6.1-sol (near-Astra a menor custo, 2026-09-29), gpt-6-sol e gpt-6-luna (volume); tool calling nos GPT-6 exige Responses (ver Legado e migração). A referência atual recomenda separar o ledger da retenção do provider: escolha conversation ou previous_response_id deliberadamente, registre a política de armazenamento e faça o scheduler respeitar limites próprios. O flag de paralelismo é uma dica de emissão, não autorização para side effects.

3. OpenAI Agents SDK: quando usar como baseAtualizado · 2026-09-30

Use o Agents SDK quando o projeto se beneficia de loop de agentes, guardrails, handoffs, agents-as-tools, sessions, tracing e MCP em código Python-first. A doc oficial o posiciona como framework leve e recomenda a Responses API direta quando você quer possuir manualmente o loop, o dispatch de tools e o estado. É uma base recomendada — LangGraph e Google ADK são alternativas legítimas (ver os guias de framework do super-guia).

from agents import Agent, Runner, function_tool

@function_tool
def lookup_policy(topic: str) -> str:
    # Chame sua capability real; reduza o output antes de devolver ao agente.
    return "síntese com provenance"

specialist = Agent(
    name="evidence_specialist",
    instructions="Responda apenas com evidências tipadas e limitações.",
    tools=[lookup_policy],
)

manager = Agent(
    name="orchestrator",
    instructions="Planeje, delegue quando necessário e sintetize com fontes.",
    tools=[specialist.as_tool(
        tool_name="consult_evidence_specialist",
        tool_description="Consulta o especialista de evidências; retorna síntese tipada com limitações.",
    )],
)

result = Runner.run_sync(manager, "Pergunta do usuário")
print(result.final_output)
Detalhe da API e padrões de orquestração: guia_agents_sdk · guia_agents_sdk_orquestracao · doc oficial openai.github.io/openai-agents-python

Em 2026-09-30 o openai-agents está na 0.22.3 (pré-1.0) e seu modelo default é gpt-5.6-luna, não um GPT-6: informe model= e model_settings explicitamente. O transporte da Responses pode ser HTTP ou WebSocket (set_default_openai_responses_transport("websocket")). A Agents API (beta, /v1/agents/sessions) é um produto distinto do Agents SDK. Mesmo quando o SDK gerencia o loop, mantenha registro externo de traces, usage, tool results e decisões críticas se o sistema precisa ser auditável — o ledger canônico é seu, não do framework.

4. Pydantic AI como camada complementarAtualizado · 2026-09-30

O Pydantic AI brilha nas bordas tipadas: dependências, output estruturado, validação de ferramentas, evals, observabilidade (Logfire) e wrappers model-agnostic. Convive com o Agents SDK — use Pydantic para schemas/evals/validadores, o Agents SDK para orquestração/handoffs, e a Responses API direta nos pontos de controle fino. Nenhum outro guia do conjunto cobre o Pydantic AI, então ele mora aqui.

from pydantic import BaseModel, Field

class EvidenceItem(BaseModel):
    source_id: str
    claim: str
    confidence: float = Field(ge=0, le=1)

class SpecialistOutput(BaseModel):
    answerable: bool
    summary: str
    evidence: list[EvidenceItem]
    missing: list[str] = []

# Use este modelo como contrato de saída de subagente/tool/eval,
# independentemente do provider que gerou a resposta.
Versão verificada em 2026-09-30: pydantic-ai 2.52.0 (PyPI). Na série 2.x o prefixo openai: usa a Responses API; Chat Completions só por openai-chat:. A versão, sozinha, não prova compatibilidade de MCPToolset, A2A, durable execution, providers ou integrações: cada capability deve ser conferida na documentação e no lockfile do projeto, com probe de contrato antes de habilitar. Piso de segurança: >=2.52.0 (GHSA-v36g-jcw9-x7cw).
Regra de portabilidade: use Pydantic AI como camada de schemas, validação e evals apenas onde a superfície instalada e o adapter a suportarem. Não deduza nomes de classes, extras, durabilidade ou transporte MCP da série de versão; registre a capability como preservada, transformada ou indisponível.
Fonte oficial: pydantic.dev/docs/ai (overview, agents, tools, output, evals, Logfire, models) · versão confirmada no PyPI 2.52.0 em 2026-09-30. Repositório: github.com/pydantic/pydantic-ai.

Parte 2 — Adapters por provider

O ângulo aqui é de projeção/adapter — o "como o contrato canônico vira chamada deste provider". A API real de cada um está nos guias dedicados.

5. Anthropic adapterAtualizado · 2026-09-30

No adapter Anthropic, trate tool use como blocos estruturados: o modelo emite tool_use, o cliente executa a tool e devolve tool_result (numa mensagem de role user), com stop_reason: tool_use. Tools de servidor são executadas pela Anthropic e podem ter eventos/pausas próprios; não as misture com o executor client-side. Messages é uma rota direta e stateless; Agent SDK/Managed Agents é um harness separado, com sessão e ciclo de vida próprios. Para thinking, preserve os blocos/assinaturas conforme as regras de contexto e tool-use. A API completa está em guia_claude_api.

ThinkingO controle muda por modelo (tabela abaixo). Em claude-opus-5-5, claude-fable-5-1 e claude-sonnet-5-5, tool_choice any/tool retorna 400: adapter que force tool choice troca para auto + strict tool use ou structured outputs. Preserve blocos e assinaturas.

9. Provider switching contractAtualizado · 2026-09-30

Trocar provider deve ser declarado. O adapter produz uma matriz de perdas e uma justificativa de roteamento — assim a troca é auditável e reversível.

{
  "provider_switch": {
    "from": "openai.responses",
    "to": "google.interactions",
    "capabilities_required": ["structured_output", "client_tool_loop", "state_resume"],
    "reason": "latency_or_capability",
    "preserved": ["messages", "assets", "function_schemas", "citations"],
    "loss_declaration": [
      {"capability": "openai_encrypted_reasoning", "status": "unavailable", "action": "drop_and_rehydrate"},
      {"capability": "provider_state", "status": "transformed", "action": "rebuild_from_ledger"},
      {"capability": "developer_role_semantics", "status": "transformed", "action": "revalidate_prompt"}
    ],
    "lost_or_transformed": ["openai_encrypted_reasoning", "developer_role_semantics"],
    "required_rehydration": ["system_instruction", "thought_signature_policy"],
    "revalidation_required": ["schema", "authorization", "tool_order", "context_retention"],
    "risk": "medium",
    "user_visible": false
  }
}
  • ☑ Não migrar carriers privados (reasoning/thinking cifrado, signatures) como texto comum.
  • ☑ Não presumir que roles e budgets têm equivalência perfeita.
  • ☑ Não misturar histórico do provider A com o B sem adapter e loss declaration.
  • ☑ Revalidar capabilities e autorização depois do switch; um route id diferente implica um contrato diferente.
  • ☑ Se o adapter não consegue provar retenção, schema ou idempotência, falhar fechado e manter a rota anterior.
  • ☑ Registrar motivo, modelo, versão, parâmetros e usage estimado/real.
Perda silenciosa: passar o carrier de reasoning de um provider como mensagem de texto para outro não "preserva o raciocínio" — corrompe o estado e pode vazar conteúdo opaco. Sempre descarte ou re-hidrate explicitamente, nunca traduza por engano.
