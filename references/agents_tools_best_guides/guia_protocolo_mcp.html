Protocolo MCP

A revisão 2026-07-28 é a corrente do MCP: o protocolo é stateless, não tem handshake nem sessões de protocolo e descobre capabilities por server/discover. Este guia trata o ciclo de vida do protocolo — o que a revisão define, quem a implementa (SDKs, frameworks, conectores hospedados) e quais recursos têm prazo de remoção.

O conceito de MCP como fronteira de capability continua em Ferramentas, MCP & RAG §3; o hardening operacional de servidor, em §11 do mesmo guia.

Resumo para agentes (verificado 2026-10-24)

Use este guia quando

  • Precisar saber qual revisão do MCP vale hoje, quem a implementa (SDKs, frameworks, conectores hospedados) e quais recursos têm prazo de remoção.
  • Escolher pisos e tetos de dependência MCP (Python mcp, TypeScript, fastmcp) e saber o que um adapter ou conector hospedado ainda limita.
  • Implementar ou revisar estado por handle, MRTR, subscriptions/listen, códigos de erro, extensões (Tasks, Skills, Apps) e autenticação MCP.
  • Operar A2A entre agentes (versão por request, Task, Agent Card).

Não é aqui

  • Contrato de tool, envelope de resultado, RAG e hardening de servidor MCP: Ferramentas, MCP & RAG.
  • Pisos por advisory de todo o ecossistema (mcp, fastmcp, langgraph, SDKs não-Python): Operação, Segurança & Evals.
  • Conector MCP de cada provider em detalhe: guias de provider (Claude API, OpenAI, Gemini Interactions).

Padrões vigentes

  • Revisão corrente: 2026-07-28 (stateless, versão por request em _meta, descoberta por server/discover, estado por handle explícito).
  • Implementação direta: pip install "mcp[cli]>=2.2.0,<3"; servidor com a classe MCPServer. Adapter que limita mcp<2 (langchain-mcp-adapters, crewai, semantic-kernel, mcp-use): fixe mcp>=1.30.0,<2 (piso de segurança).
  • Pacote fastmcp (Prefect): >=4.1.2; é outro projeto que o npm fastmcp.
  • Em cada POST Streamable HTTP, enviar MCP-Protocol-Version igual a _meta.io.modelcontextprotocol/protocolVersion, Mcp-Method sempre e Mcp-Name em tools/call, resources/read, prompts/get; divergência dá 400 HeaderMismatch.
  • Estado entre chamadas é handle explícito, escopado ao principal autenticado; input do usuário no meio da chamada vai por MRTR (resultType: "input_required"); notificações duráveis por subscriptions/listen.
  • OAuth: Protected Resource Metadata (RFC 9728), validação literal de iss, PKCE S256, registro na ordem pré-registrado, CIMD, DCR (deprecado).
  • Compare erros por constante nomeada: -32020 (header), -32021 (capability ausente), -32022 (versão); recurso inexistente é -32602.
  • Providers hospedados: você herda a revisão do provider (OpenAI não declara revisão; Gemini 3 não tem remote MCP).

Sobre este guia

Este guia é dono do ciclo de vida do protocolo: o que a revisão corrente (2026-07-28) define, quem a implementa e quais recursos têm prazo de remoção. Um teto de dependência num adapter limita aquele ambiente; ele não redefine a revisão corrente.

Fronteira com os outros guias. MCP como conceito e o hardening de servidor ficam em Ferramentas, MCP & RAG; prática de segurança e pisos de dependência, em Operação, Segurança & Evals; Agent Skills, em Skills.
Este guia não é um cookbook de SDK. Os exemplos permanecem nas formas de wire normativas: cada framework ou provider precisa de validação própria antes que um exemplo de adapter seja apresentado como caminho executável.

Parte 1 — Estado e bibliotecas

1. Estado e compatibilidade

A revisão 2026-07-28 está publicada e é a corrente (página de versionamento, sem data anunciada para a próxima). Compatibilidade de framework ou provider é evidência de integração, não uma segunda definição do estado do protocolo.

CamadaEstado em 2026-10-24Consequência
Speccorrente normativa, finalProjete contra ela.
SDKs oficiaissete linguagens Python, TypeScript, C#, Go, Rust, Ruby e PHP citam a revisão nas release notes; nenhuma release estável de Java, Kotlin e Swift a declara (§2.1)Dá para implementar servidor e cliente na revisão corrente nessas sete linguagens.
Frameworks e adaptersquase todos aceitam mcp<3; langchain-mcp-adapters, crewai, semantic-kernel e mcp-use (Python) ainda limitam a mcp<2 (§2.2)Nesses ambientes fixe mcp>=1.30.0,<2 (piso de segurança).
Providers hospedadosVocê herda a revisão do provider: OpenAI não declara revisão; Gemini 3 não oferece remote MCP (§2.3)O conector do provider, não o seu código, negocia o protocolo.
Piso e teto resolvem problemas opostos. O teto (<2) preserva um adapter que não aceita a major nova; o piso protege de vulnerabilidade conhecida e é independente da revisão. Uma dependência sem teto resolve para mcp 2.x, o que é correto para implementação direta: adicione <2 somente quando o metadado do adapter exigir, e valide em runtime antes de fixar um teto manual.

Negociação de versão. A revisão corrente é 2026-07-28. Um servidor que implementa só essa revisão não negocia com um cliente que ofereça outra revisão; para atender esse cliente, o servidor precisa aceitar a revisão oferecida no mesmo processo.

Exemplo mínimo (Python mcp 2.x)

Servidor com a classe MCPServer e cliente por URL Streamable HTTP:

from mcp.server import MCPServer
mcp = MCPServer("Demo")

@mcp.tool()
def add(a: int, b: int) -> int:
    """Add two numbers."""
    return a + b
# servir: mcp run server.py --transport streamable-http
from mcp import Client
async with Client("http://localhost:8000/mcp") as client:   # URL = Streamable HTTP
    result = await client.call_tool("add", {"a": 1, "b": 2})
    print(result.structured_content)
Python mcp 2.x. Client é de primeira classe; Resolve(fn) cobre o fluxo MRTR; MCP Apps vem embutido e há OpenTelemetry por padrão. O pacote depende de mcp-types==2.3.0 e de httpx2>=2.10.0 — uma distribuição separada de httpx: código que constrói um httpx.AsyncClient e o entrega ao SDK instala sem erro e falha na chamada. Uma tool com anotação x-mcp-header inválida falha no registro (InvalidSignature; só parâmetros str, int ou bool simples valem como header); redirecionamentos só são seguidos dentro da mesma origem e AuthSettings.validate_token_resource existe. Não implementados no SDK Python 2.3.0: Tasks (SEP-2663), DPoP (SEP-1932) e jwt-bearer. Piso de segurança: mcp>=2.2.0 (GHSA-qx49-fqc8-xw99, high: o cliente OAuth envia credenciais a um authorization server escolhido pelo servidor; GHSA-rwrf-2pqf-9j8j, medium: o cliente busca um $ref escolhido pelo servidor ao validar outputSchema, §7.1; GHSA-84m7-p3x7-pcfv / CVE-2026-59951). Em adapters que limitam mcp<2: mcp>=1.30.0.
TypeScript: família v2. Pacotes server, client, core, codemod, server-legacy e middlewares node, express, fastify, hono (docs v2). A 2.4.0 (23/10) traz Skills (SEP-2640) e passa a rejeitar x-mcp-header com número (release v2.4.0). Um servidor por request: Server.connect() rejeita instância já conectada com SdkError ALREADY_CONNECTED; crie o McpServer e o transporte dentro do handler ou use a factory de createMcpHandler; redirects só na mesma origem (redirectPolicy: 'follow' para seguir outro host); opções opt-in, desligadas por padrão: maxToolInputElements (McpServer) e expectedResource (requireBearerAuth/verifyBearerToken). Piso de segurança: server/client>=2.3.0 (server-legacy>=2.3.1, express>=2.0.2, node>=2.1.0, hono>=2.0.1). Abaixo disso há advisories do repositório: GHSA-6qxp-vccf-f47h (OAuth envia credenciais ao servidor de autorização escolhido pelo servidor MCP), GHSA-22jm-h49p-29qw (tasks sem vínculo de sessão), GHSA-6prh-2h8m-c8cw (redirect cross-origin), GHSA-rvq5-wwqv-78pq (bearer aceita token de outro serviço), GHSA-46jr-4wx8-v453 (uma request esgota memória), GHSA-f897-62hf-6gxq (corpo sem limite) e GHSA-jm63-cq47-j5jp (instância compartilhada entrega mensagens de um cliente a outro) (advisories do repositório).
Dois "FastMCP" são coisas diferentes. O pacote fastmcp (Prefect) é projeto de terceiros: 4.1.3 (20/10), construído sobre mcp 2.x (fastmcp-slim exige mcp>=2.2.0,<3, o que fixa o piso do SDK). O npm fastmcp (4.23.7) é um terceiro projeto homônimo e independente. O que ainda morde na 4.x: ctx.elicit() só existe no protocolo antigo; tasks vivem no pacote fastmcp-tasks; sessões HTTP expiram após 30 min ociosas (o padrão do SDK MCP); a busca de tools por regex usa o motor do Pydantic (sem lookaround nem backreference; rejeita padrões acima de 1.000 caracteres); arquivos de skill precisam resolver dentro dos diretórios configurados. Piso de segurança: fastmcp>=4.1.2 — o repositório publicou 16 advisories entre 2026-10-16 e 2026-10-20, entre eles GHSA-gpgx-58w2-xwwf (crítica: o cliente avalia como código Python o title autorreferente de um outputSchema fornecido pelo servidor), GHSA-cg3c-5x66-h9cc (high: regex controlada pelo atacante no RegexSearchTransform) e GHSA-vqqp-x5qm-5qp4 (medium: wrappers de cliente criam provedores OAuth M2M sem issuer binding; corrigido na 4.1.2) (advisories do repositório). Tratamento completo da armadilha em Ferramentas, MCP & RAG §3.

Parte 2 — A revisão 2026-07-28

3. Core stateless

A decisão estruturante, da qual quase todas as outras decorrem: o protocolo não tem estado. Não existe um momento de abertura de conexão em que cliente e servidor se apresentam e negociam capabilities para o resto da vida da conexão.

AspectoRevisão 2026-07-28
Abertura de conexãoNão há handshake. Cada request é autocontida.
CapabilitiesCada request carrega as suas, em _meta
Versão do protocoloDeclarada em toda request
DescobertaMétodo próprio: server/discover, que o servidor DEVE implementar

3.1 As chaves de _meta

As chaves reservadas usam prefixo reverse-DNS do protocolo. Qualquer prefixo cujo segundo rótulo seja modelcontextprotocol ou mcp é reservado.

ChaveTipoGrauPara quê
io.modelcontextprotocol/protocolVersionstringobrigatóriaVersão desta request, ex.: "2026-07-28"
io.modelcontextprotocol/clientCapabilitiesClientCapabilitiesobrigatóriaCapabilities do cliente relevantes a esta request
io.modelcontextprotocol/clientInfoImplementationDEVERIANome e versão do cliente — não é "opcional": a spec diz que o cliente DEVERIA incluir em toda request, salvo configuração explícita em contrário
io.modelcontextprotocol/logLevelLoggingLevelopcionalNível mínimo de log para esta request
io.modelcontextprotocol/subscriptionIdstring—Correlaciona notificação com a assinatura de origem
io.modelcontextprotocol/serverInfoImplementationDEVERIANo _meta do resultado: identifica o servidor
traceparent, tracestate, baggageW3CopcionalExceção à regra de prefixo — contexto de trace OpenTelemetry
Falta de campo obrigatório é rejeição dura, não degradação. Request sem protocolVersion ou clientCapabilities é malformada: o servidor DEVE rejeitar com -32602 (Invalid params) e, em HTTP, status 400 Bad Request. E o servidor NÃO PODE contar com capability que o cliente não declarou: se precisar de uma, devolve -32021 com data.requiredCapabilities listando o que faltou — também com 400 em HTTP.
clientInfo e serverInfo são autodeclarados e não verificados. A spec é explícita: servem para exibição, log e depuração; implementações NÃO DEVERIAM mudar comportamento com base neles nem usá-los em decisão de segurança. É o mesmo erro de sempre — tratar identificação declarada pelo par como se fosse autenticação.

3.2 Estado explícito não é sugestão — é norma

A spec normatiza o handle explícito. Nas palavras dela: estado que precisa atravessar múltiplas requests DEVE ser referenciado por um identificador explícito que o cliente passa em cada request. E mais: o servidor NÃO PODE inferir contexto de requests anteriores na mesma conexão, nem tratar identidade de conexão ou de processo como se fosse continuidade de conversa. Uma conexão stdio aberta não é uma sessão — o cliente pode intercalar requests sem relação nenhuma no mesmo transporte.
Por que isso é bom, apesar do custo. Um protocolo sem estado é horizontalmente escalável por construção: qualquer réplica atende qualquer request, sem afinidade de sessão, sem replicação de estado entre nós, sem reconexão que precise reconstruir contexto. O custo é verbosidade — cada request repete o que antes era dito uma vez. É a troca clássica, e para servidores MCP atrás de balanceador ela compensa com folga.

4. O fim das sessões

O protocolo não tem sessões: nenhuma request depende de identificador de sessão e a autenticação é por request.

Identificador de estado nunca é credencial. Tratar quem apresenta um identificador como dono da sessão é uma classe de vulnerabilidade: implementações reais do SDK já foram corrigidas por servir requests de estado sem verificar o principal autenticado. Sem sessão no protocolo, o servidor autentica cada request e escopa todo estado ao principal. Quando um padrão gera a mesma falha em várias implementações, o padrão é o defeito.

Se o seu servidor precisa de continuidade entre chamadas — um carrinho, um rascunho, um cursor de paginação —, o estado é explícito: um handle devolvido por uma tool e passado de volta como argumento de outra. É o conselho mais durável deste guia: handle explícito, assinado e escopado ao principal.

Handle explícito é dado que vem de fora — trate como tal. A spec diz o mesmo sobre o estado opaco que ela mesma define para o fluxo de múltiplas rodadas: o servidor DEVE assumir que está sob controle de um atacante. Assine, valide e escope o handle ao principal autenticado; nunca confie que ele voltou intacto só porque você o emitiu.

5. Assinaturas e notificações

NecessidadeMecanismo
Notificações duráveis (mudança de recurso, lista de tools)subscriptions/listen, um stream unificado
Nível de logViaja em _meta por request
LivenessÉ do transporte; o protocolo não tem método para isso
Reconexão após quedaReconecte e re-sincronize pelo estado da aplicação; o protocolo não retoma stream
A ausência de retomada de stream tem consequência de design. Não existe "retomar": quando um stream cai, o cliente emite uma request nova, com id novo — é outra request, não a continuação da anterior. Nada do que passou é reentregue. Quem construiu entrega confiável de eventos apoiado na resumability do transporte precisa mover essa garantia para a camada de aplicação, com cursor ou marca d'água própria.
subscriptions/listen continua sendo request/resposta. Parece conexão persistente, mas não é: a resposta é apenas um stream aberto de notificações, e o estado dela é escopado à request, não à conexão por baixo. Notificações entregues por esse stream carregam io.modelcontextprotocol/subscriptionId no _meta, para o cliente correlacionar com a assinatura de origem.

5.1 Cancelamento e progresso

Sem sessão, cancelar é sempre cancelar uma request específica, correlacionada pelo id JSON-RPC (ou pelo progressToken em _meta, para progresso).

MecanismoComo funciona por transporteRegra do servidor
CancelamentoStreamable HTTP: fechar o stream SSE da request é o sinal de cancelamento — o servidor DEVE tratar a desconexão do cliente como cancelamento daquela request, sem mensagem extra. Stdio: não há stream por request, então o cliente DEVE enviar notifications/cancelled referenciando o id.O servidor NÃO PODE enviar notifications/cancelled para nada além de encerrar um stream de subscriptions/listen que ele mesmo está fechando — cancelamento de request do cliente para o servidor continua existindo, mas o servidor não usa mais essa notificação para avisar o cliente de outras coisas.
ProgressoCliente inclui progressToken (string ou inteiro, único entre requests ativas) no _meta da request. O servidor PODE emitir notifications/progress — o valor progress DEVE crescer a cada notificação, mesmo com total desconhecido.Sem sessão, a notificação de progresso só pode viajar dentro do SSE daquela request (ver §7) — não existe mais canal de servidor para cliente fora do escopo de uma request em aberto.

6. MRTR — requests de múltiplas rodadas

Num protocolo sem estado, o servidor não pode iniciar uma request para o cliente no meio de uma operação — não há canal aberto para isso. Tudo que dependia disso (pedir uma completação ao cliente, pedir input ao usuário, listar raízes de filesystem) foi reformulado sob um mecanismo único: Multi Round-Trip Requests.

O padrão inverte quem dirige a conversa:

  1. O cliente chama uma tool.
  2. Em vez de responder pronto, o servidor devolve um resultado do tipo input requerido, descrevendo o que precisa e carregando um estado opaco.
  3. O cliente obtém o que foi pedido — do usuário, do modelo, de onde for.
  4. O cliente repete a chamada, agora com as respostas e o estado opaco devolvido.
Quem controla o fluxo agora é o cliente. O servidor nunca "espera" — ele responde e sai. Isso é o que torna cada request independente e o servidor replicável. Também significa que o cliente precisa implementar o laço de retry: um cliente que trate input requerido como erro vai simplesmente falhar em toda tool que precise de interação.

6.1 Onde MRTR vale — e onde não vale

MRTR não é exclusivo de chamada de tool. O servidor pode devolver input requerido em exatamente três requests do cliente, e a spec fecha a lista com um NÃO PODE para todo o resto:

Request do clienteAceita input requerido?
prompts/getsim
resources/readsim
tools/callsim
qualquer outraNÃO PODE

6.2 As formas de wire

CampoOndeO que carrega
resultType: "input_required"Resultado do servidorSinaliza que a request está incompleta
inputRequestsResultado do servidorMapa de identificador → request. Valores DEVEM ser ElicitRequest, CreateMessageRequest ou ListRootsRequest
inputResponsesRetry do clienteMapa com as mesmas chaves, contendo o resultado de cada pedido
requestStateAmbosString opaca. O cliente NÃO PODE inspecionar, parsear, modificar ou supor nada sobre o conteúdo — só devolver o valor exato
Detalhes fáceis de errar na implementação do cliente:
  • O id JSON-RPC DEVE ser diferente entre a request original e o retry — são requests independentes, não continuação.
  • Se veio requestState, o cliente DEVE ecoar o valor exato. Se não veio, o cliente NÃO PODE inventar um.
  • Sem inputRequests, o cliente PODE repetir imediatamente.
  • Esses campos valem só para o retry daquela request — nunca para outras chamadas em paralelo.
Do lado do servidor, duas regras que evitam laço quebrado: ele NÃO PODE pedir um tipo de input que o cliente não declarou em capabilities (pedir elicitation a quem não a suporta), e NÃO PODE assumir que o cliente vai atender ou repetir. Ele também DEVE incluir ao menos um entre inputRequests e requestState em toda resposta de input requerido.

6.3 Proteção do requestState

Este é o ponto de segurança da revisão. O estado trafega pelo cliente, então a spec obriga: o servidor DEVE tratá-lo como input controlado por atacante. Se ele influencia autorização, acesso a recurso ou lógica de negócio, o servidor DEVE proteger a integridade (HMAC ou AEAD) e DEVE rejeitar estado que falhe na verificação. A dispensa só vale quando adulterar não causa nada pior que a request falhar.

Contra replay, a spec manda incluir dentro do payload protegido e verificar na volta:

ItemO que impede
Principal autenticado — rejeitar estado apresentado por outroReuso entre usuários
Expiração curta (TTL) — rejeitar estado vencidoJanela de replay longa
Identificador da request de origem (método + digest dos parâmetros) — rejeitar em request que não bateReuso entre requests diferentes
Nada disso garante uso único. A própria spec avisa: essas medidas limitam a janela e impedem reuso entre usuários e entre requests, mas não garantem consumo único. Se o seu requestState representa algo que só pode ser resgatado uma vez — um pagamento, um cupom, uma aprovação —, você DEVE impor essa invariante do lado do servidor, com estado real. É a exceção onde "stateless" não te salva.

7.1 JSON Schema — duas regras de segurança

O dialeto padrão é JSON Schema 2020-12 quando o schema não declara $schema, e implementações DEVEM suportar ao menos esse dialeto. Junto vêm duas restrições que não são detalhe de tipagem — são defesa:

1. Não resolva $ref de rede automaticamente. JSON Schema permite $ref apontando para URI absoluta. A spec agora diz que implementações NÃO PODEM dereferenciar automaticamente $ref que resolva para URI de rede. Um modo opcional que busque PODE existir, mas DEVE vir desligado por padrão e DEVERIA impor allowlist de hosts — ou, no mínimo, rejeitar loopback, link-local e endereços de rede privada, aplicar timeout e limite de tamanho, e logar as URIs resolvidas. É a mesma família de SSRF que já assombra descoberta de metadados: um schema de tool vindo de servidor não confiável vira requisição para dentro da sua rede.

E o comportamento em falha importa: schema que não valida por $ref externo não resolvido DEVERIA ser rejeitado, não tratado como permissivo em silêncio.

Não é teoria: o GHSA-rwrf-2pqf-9j8j (medium, 2026-09-28) é exatamente um cliente do SDK Python que buscava um $ref escolhido pelo servidor ao validar outputSchema; corrigido em mcp 2.2.0 e 1.30.0.
2. Ponha limite nas palavras-chave de composição. anyOf, oneOf, allOf, if/then/else e $defs são expressivos e caros de validar. A spec recomenda limites — profundidade máxima, teto de subschemas, ou orçamento de tempo por validação — porque um schema malicioso vira vetor de negação de serviço contra o seu validador. Quem aceita schema de terceiro (marketplace de servidores MCP, registro público) precisa disso.
O que o dialeto permite: inputSchema e outputSchema aceitam qualquer palavra-chave do 2020-12, e structuredContent aceita qualquer valor JSON — não só objeto. Mais liberdade de modelagem, com as duas travas acima como contrapartida.

9. Deprecações com prazo

A revisão traz uma política formal de ciclo de vida (SEP-2596), com estados ativo → deprecado → removido e janela mínima de 12 meses entre depreciar e remover (90 dias na via expedita, para segurança). Deprecados em 2026-07-28; nada foi removido, e a remoção só é elegível na primeira revisão publicada em ou depois de 2027-07-28.

Parte 3 — Extensões & auth

10. Framework de extensões

Recursos que não são núcleo do protocolo são extensões versionadas independentemente, declaradas nas capabilities e identificadas por um esquema de nome com prefixo de domínio reverso. Isso permite que o núcleo fique pequeno e estável enquanto funcionalidades opcionais evoluem no próprio ritmo.

ExtensãoRepositórioEstadoO que traz

io.modelcontextprotocol/ui		ext-appsoficialElementos de UI interativos (gráficos, formulários, player) embutidos na conversa.
MCP Tasks
io.modelcontextprotocol/tasks		ext-tasksoficialExecução assíncrona de operações longas: polling, input no meio do voo e handles duráveis (resultType: "task"; tasks/get, tasks/update, tasks/cancel). Autorização gerenciada por empresaoficialControle de acesso centralizado para ambientes corporativos. É extensão oficial com requisitos normativos próprios — o que ela não é, é parte do núcleo do protocolo.
MCP Server Cards
io.modelcontextprotocol/server-card		ext-server-cardoficial · FinalSEP-2127 Final (SEP). Formato de descoberta antes da conexão: transportes, versões e orientação de conexão do servidor.
Skills over MCP
io.modelcontextprotocol/skills		ext-skillsoficial · FinalSEP-2640 Final; o TypeScript SDK 2.4.0 a implementa. Suporte de clientes na matriz oficial: parcial em ChatGPT, fast-agent e Inspector; completo em mcpc. Não substitui o formato de diretório SKILL.md, que continua na especificação de Agent Skills — ver Skills.
"Extensão oficial" não quer dizer "núcleo", e é justamente essa a graça. Toda extensão oficial usa linguagem normativa (DEVE/DEVERIA/PODE) e passa por processo de proposta com implementação de referência obrigatória em algum SDK antes da revisão. Mas extensões são sempre desligadas por padrão e exigem opt-in explícito do desenvolvedor, e SDK nenhum é obrigado a implementá-las para estar em conformidade com o protocolo. Antes de depender de uma, confirme que o seu SDK a suporta.
Como a negociação acontece. O cliente anuncia extensões em clientCapabilities.extensions dentro do _meta de cada request; o servidor anuncia as dele na resposta do server/discover. É um mapa de identificador para objeto de configuração — objeto vazio significa "suporto, sem ajuste". Se um lado suporta e o outro não, quem suporta DEVE voltar ao comportamento do núcleo ou rejeitar com erro apropriado.
Extensões evoluem sozinhas — e isso tem um preço. Atualizações não passam por revisão dos mantenedores do núcleo. A orientação é preferir flags de capability ou versionamento dentro do objeto de configuração; quando a quebra é inevitável, cria-se um identificador novo (o padrão sugerido é sufixo -v2). Ou seja: o identificador da extensão é parte do seu contrato — trate mudança dele como quebra.
Não construa sobre proposta não normativa. "Em revisão" significa que a superfície pode mudar por inteiro. Extensão oficial tem contrato; proposta em revisão tem intenção.

11. Auth

Os subconjuntos de spec que a autorização MCP realmente implementa. A página normativa /basic/authorization lista as fontes externas de que é subconjunto: OAuth 2.1 IETF draft (draft-ietf-oauth-v2-1-13), RFC 6750 (Bearer Token), RFC 8414 (Authorization Server Metadata), RFC 7591 (Dynamic Client Registration), RFC 8707 (Resource Indicators), RFC 9728 (Protected Resource Metadata), RFC 9207 (Authorization Server Issuer Identification), o draft de Client ID Metadata Documents e OpenID Connect Discovery/Dynamic Registration. Autorização em si continua OPCIONAL para uma implementação MCP; quando suportada em transporte HTTP, DEVERIA seguir esta spec — stdio NÃO DEVERIA segui-la (credenciais vêm do ambiente).

11.1 Requisitos

RequisitoPor quê

11.2 Seleção e step-up de escopo

Escopo ganhou um fluxo formal de negociação, para o cliente pedir só o necessário e escalar sob demanda em vez de pedir tudo de uma vez.

PassoRegra
Seleção inicialCliente DEVERIA seguir esta prioridade: (1) o parâmetro scope do header WWW-Authenticate na resposta 401, se presente; (2) na ausência dele, todos os escopos de scopes_supported do Protected Resource Metadata.
Escopo insuficiente em runtimeServidor DEVERIA responder 403 Forbidden com WWW-Authenticate: Bearer error="insufficient_scope", scope="...", resource_metadata="...", reunindo todos os escopos daquela operação num único desafio — desafiar um de cada vez força múltiplas idas e voltas de autorização para uma única operação.

Hierarquia de escopoServidor DEVE considerar que um escopo mais amplo implica os mais estreitos (ex.: admin ⊇ read) ao decidir se um token já é suficiente.
Minimização de escopo é princípio operacional, não só protocolo. A orientação prática — modelo de escopo progressivo, nunca escopo wildcard/omnibus, log de eventos de elevação — está tratada junto com o resto do hardening de servidor em Ferramentas, MCP & RAG §11, para não duplicar a mesma tabela nos dois guias.

Sem sessões de protocolo, a ameaça equivalente ao sequestro de sessão é o roubo do handle de estado (State Handle Hijacking) — ver o controle operacional completo em Ferramentas, MCP & RAG §11.

Parte 4 — A2A

12. A2A: ciclo de vida entre agentes

MCP padroniza capabilities expostas a um host; A2A padroniza a interação entre um cliente e um agente remoto. Na fonte oficial atual, a specification wire é 1.0; o release v1.0.1 do repositório (28/05, release estável recente) é um patch — três correções de binding HTTP (prioriza application/a2a+json), erros de transcodificação e valores de TaskStatus — e não muda a versão wire Major.Minor.

Três numerações distintas identificam as camadas: specification wire 1.0, patch do repositório v1.0.1 e pacote a2a-sdk 1.2.3 (PyPI, 2026-10-19).

Contrato ao operar A2AAplicação
Versão por requestEnvie A2A-Version: 1.0 em cada request HTTP; o servidor processa a semântica Major.Minor pedida ou devolve VersionNotSupportedError.
Message → TaskUma Message inicia ou continua uma interação e recebe uma resposta direta ou uma Task. A Task carrega status, artifacts e histórico; resultados vivem em artifacts, não em Messages.
Atualização de TaskObtenha estado por polling, streaming ou push. O fluxo termina em TASK_STATE_COMPLETED, TASK_STATE_FAILED, TASK_STATE_CANCELED ou TASK_STATE_REJECTED; TASK_STATE_INPUT_REQUIRED e TASK_STATE_AUTH_REQUIRED pedem continuidade controlada.
Auth por requestO cliente envia credenciais declaradas pelo Agent Card em cada request; o servidor autentica cada request e autoriza pela identidade e política. taskId e contextId não substituem autorização.
Proteção do Agent CardValide binding, URL e requisitos de segurança antes de usar a descoberta. Quando houver assinatura, verifique JWS antes de confiar no card; detalhes estendidos só são obtidos após autenticação e sob controle de acesso.
Não trate descoberta como confiança. O Agent Card descreve capacidades e schemes de segurança; ele não concede privilégio. Proteja a versão estendida, não coloque segredos no card público e preserve autenticação/autorização em cada operação, inclusive nas etapas internas de uma Task.

Fontes oficiais: A2A Protocol Specification 1.0 · A2A repository release v1.0.1 · PyPI a2a-sdk.
