Protocolo MCP

A revisão 2026-07-28 foi publicada e é a maior ruptura desde o lançamento do MCP: o protocolo virou stateless, o handshake initialize deixou de existir e as sessões saíram do protocolo. Este guia trata o ciclo de vida do protocolo — o que mudou, quem já fala a revisão atual, e como manter compatibilidade legado apenas onde o adapter realmente a exigir.

A mecânica Legacy de 2025-11-25, necessária apenas para clientes ou adapters com teto de dependência, e o conceito de MCP como fronteira de capability continuam em Ferramentas, MCP & RAG §3; o hardening operacional de servidor, em §11 do mesmo guia.

Estado verificado em 2026-09-30. A revisão de fio corrente é 2026-07-28 (página de versionamento; sem data anunciada para a próxima). SDK Python oficial: mcp 2.2.0 (07/09); a linha 1.x (1.30.0) só recebe manutenção de segurança. TypeScript: família v2 (@modelcontextprotocol/server, client, core) em 2.2.0 (28/09); o monólito @modelcontextprotocol/sdk 1.31.0 continua mantido. FastMCP Python (Prefect): 4.0.10, GA desde 31/08, sobre mcp 2.x; o fastmcp do npm é outro projeto. MCP Registry: preview, sem data de GA. A2A: wire 1.0, a2a-sdk 1.2.1. Detalhes em §3 e §16.

Superfície atual

Revisão de fio corrente: 2026-07-28 (stateless, sem initialize). SDK Python oficial: pip install "mcp[cli]>=2.2.0,<3". Servidor (classe MCPServer, não mais FastMCP) e cliente:

from mcp.server import MCPServer
mcp = MCPServer("Demo")

@mcp.tool()
def add(a: int, b: int) -> int:
    """Add two numbers."""
    return a + b
# servir: mcp run server.py --transport streamable-http
from mcp import Client
async with Client("http://localhost:8000/mcp") as client:   # URL = Streamable HTTP
    result = await client.call_tool("add", {"a": 1, "b": 2})
    print(result.structured_content)

Faça / Não faça

  • Faça: implementação direta com mcp>=2.2.0,<3 (piso de segurança: GHSA-qx49-fqc8-xw99 e GHSA-rwrf-2pqf-9j8j; na linha 1.x, mcp>=1.30.0).
  • Faça: com adapter em 1.x, fixe o que ele aceita (mcp>=1.30.0 quando o pin permitir). crewai com mcp~=1.28.1 não alcança a correção: fale só com servidores confiáveis.
  • Faça: envie MCP-Protocol-Version igual a _meta.io.modelcontextprotocol/protocolVersion, Mcp-Method em toda request e Mcp-Name em tools/call, resources/read, prompts/get; divergência dá 400 HeaderMismatch.
  • Faça: use constantes nomeadas para erros. Novos: -32020 (header), -32021 (capability ausente), -32022 (versão); recurso inexistente agora é -32602.
  • Faça: rejeite schema com $ref de rede não resolvido; nunca dereferencie $ref de rede por padrão (§10.1).
  • Faça: OAuth com Protected Resource Metadata (RFC 9728), validação literal de iss, PKCE S256 e recusa se code_challenge_methods_supported faltar. Registro: pré-registrado > CIMD > DCR.
  • Faça: notificações duráveis por subscriptions/listen; input do usuário no meio da chamada por MRTR (resultType: "input_required").
  • Não use initialize, Mcp-Session-Id, Last-Event-ID, resources/subscribe, logging/setLevel, ping (removidos na 2026-07-28) → _meta por request + server/discover.
  • Não use Roots, Sampling, Logging, DCR (deprecados; nada removido ainda) nem HTTP+SSE → Streamable HTTP. Detalhes em Legado e migração.
  • Não passe um httpx.AsyncClient ao mcp 2.x: ele usa httpx2 (instala sem erro, falha na chamada).
  • Não confunda a classe FastMCP (SDK 1.x, hoje MCPServer) com o pacote fastmcp (Prefect) nem com o npm fastmcp.
  • Não compare códigos de erro por literal numérico; não compare número de versão entre SDKs (Java 2.0.x não declara a revisão atual).
  • Não espere Tasks, DPoP ou jwt-bearer no SDK Python 2.2.0; Tasks é a extensão io.modelcontextprotocol/tasks (§13).
  • Não migre só o servidor: cliente Legacy não negocia com servidor só-Modern; use servidor dual-era.

Sobre este guia

Existem duas eras de compatibilidade, mas uma só revisão atual: 2026-07-28. A linha 2025-11-25 é Legacy e continua útil para compatibilidade retroativa ou para o ambiente específico cujo adapter ainda declara mcp<2. Um teto de adapter limita aquele ambiente; ele não redefine a revisão atual do protocolo.

Estado do protocolo ≠ compatibilidade de um adapter. A revisão 2026-07-28 é normativa e atual; o Python mcp 2.2.0 declara suporte a ela. Compatibilidade com clientes de eras anteriores depende do modo/servidor efetivamente configurado. Frameworks, conectores hospedados e bibliotecas intermediárias podem continuar Legacy em ritmos diferentes. Não conclua que o protocolo é antigo só porque um adapter exige mcp<2.

A revisão 2025-11-25 é anterior e Legacy. Não a remova de um stack que ainda depende dela: use-a como alvo de compatibilidade, não como estado canônico do MCP. O que existe só por compatibilidade está reunido em Legado e migração.

Fronteira com os outros guias. Este guia é dono do ciclo de vida do protocolo: o que a revisão nova mudou, quem a implementa, e quando migrar. Ele não reescreve o que já está documentado: MCP como conceito e a mecânica da linha Legacy ficam em Ferramentas, MCP & RAG; prática de segurança e pisos de dependência, em Operação, Segurança & Evals; Agent Skills, em Skills.
Este guia não é um cookbook de SDK. O Python mcp 2.2.0 já implementa a revisão atual, e a v2 TypeScript usa pacotes separados de cliente e servidor. Ainda assim, os exemplos aqui permanecem nas formas de wire normativas: cada framework ou provider precisa de validação própria antes que um exemplo de adapter seja apresentado como caminho executável.

Parte 1 — O regime dual-era

1. Publicada ≠ operanteAtualizado · 2026-09-30

A revisão 2026-07-28 foi publicada como stable release no repositório canônico da spec e é a revisão atual. A distância entre "a spec existe" e "este adapter específico a fala" continua sendo de várias camadas; compatibilidade de framework ou provider é evidência de integração, não uma segunda definição do estado do protocolo.

CamadaEstado em 2026-09-30Consequência

A leitura correta é de baixo para cima: a atualização precisa subir do SDK para as bibliotecas intermediárias e só então para os frameworks. Enquanto uma camada intermediária declarar teto, as camadas acima dela não têm como adotar a linha nova naquele ambiente; o teto não transforma a spec atual em Legacy.

O risco concreto é aplicar a regra errada ao ambiente errado. Uma dependência sem teto resolve para mcp 2.x, o que é correto para implementação direta já pronta para a revisão atual. Adicione <2 somente quando o metadado ou a validação do adapter demonstrar que ele permanece Legacy; nesse caso, o pin evita uma troca acidental no próximo install. Veja Postura para stacks com adapter Legacy.

2. Modern, Legacy e dual-era

A spec define uma terminologia própria para o período de convivência. Vale adotá-la, porque ela deixa explícito o caso que falha:

TermoSignificado
ModernImplementação que fala 2026-07-28 ou posterior: stateless, sem handshake, com server/discover.
LegacyImplementação que fala 2025-11-25 ou anterior: com initialize, sessões e capabilities negociadas uma vez.
Dual-eraImplementação que atende as duas — tipicamente um servidor que serve todas as revisões a partir do mesmo processo.

Note que dual-era não é atributo só de servidor: cliente também pode ser dual-era, e é isso que separa o caso que funciona do que quebra.

2.1 A matriz de compatibilidade

A spec publica o resultado esperado de todas as combinações. Vale ler como tabela de decisão, porque a intuição erra em pelo menos duas linhas:

ClienteServidorResultado
ModernModernfunciona server/discover é opcional; divergência de versão vira erro de versão não suportada e o cliente repete com uma versão comum.
ModernLegacyfalha O servidor pode rejeitar com erro próprio, ficar em silêncio, ou — pior — processar um método ambíguo com semântica antiga. Em stdio, o cliente DEVERIA mandar server/discover primeiro para falhar de forma determinística.
Dual-eraModernfunciona A sonda responde e o cliente permanece em modo Modern.
Dual-eraLegacyfunciona A sonda falha de um jeito não-reconhecível como erro Modern, e o cliente cai para initialize — e, se preciso, até para o transporte HTTP+SSE deprecado.
LegacyModernfalha initialize é método desconhecido e faltam os campos obrigatórios de _meta. Cliente Legacy não tem mecanismo de avanço.

LegacyLegacyfunciona Fora do escopo da revisão nova.

2.2 Como um cliente descobre a era do servidor

Ao contrário do que a remoção do handshake sugere, a spec define detecção de era pelo cliente — com mecânica específica por transporte:

TransporteSondaComo ler a resposta
stdioChamar server/discoverErro Modern reconhecível ⇒ servidor Modern (repetir com versão suportada). Qualquer outra coisa, ou timeout ⇒ servidor Legacy.
Streamable HTTPEmitir uma request Modern normalInspecionar o corpo do 400 Bad Request: com erro Modern reconhecível ⇒ servidor Modern; 4xx sem esse corpo ⇒ Legacy.
A era é propriedade do servidor, não da request. A spec manda o cliente cachear o resultado da sonda pelo tempo de vida do processo (stdio) ou da origem (HTTP), e permite persistir entre reinícios da mesma configuração, re-sondando se a suposição falhar depois. Ou seja: sondar não é custo por chamada.
O caso genuinamente perigoso não é a falha — é o silêncio. Na linha Modern → Legacy, a spec admite que o servidor pode processar um método ambíguo entre eras sob semântica antiga. Isso é pior que erro: a chamada "funciona" e faz outra coisa. É exatamente por isso que a sonda explícita em stdio é recomendada — falhar de forma determinística vale mais que dar sorte.
Cliente Legacy não tem como avançar. Não existe caminho para um cliente antigo falar com servidor novo: falta o initialize do lado do servidor e faltam os campos obrigatórios do lado da request. Por isso a spec recomenda que servidor só-Modern nomeie as versões que suporta no erro devolvido a um initialize — para o cliente antigo ao menos ter o que mostrar ao usuário. Se você opera clientes antigos, o servidor tem que ser dual-era.

Continua valendo que não há handshake de negociação: cada request é aceita ou rejeitada por si, e a versão viaja em toda chamada. O que existe é uma sonda opcional e um erro de versão não suportada que lista as versões aceitas — o que permite ao cliente repetir com uma versão comum.

Dois "FastMCP" continuam sendo coisas diferentes. A classe FastMCP vivia no SDK oficial 1.x e virou MCPServer no mcp 2.x. O npm fastmcp (4.22.1) é um terceiro projeto homônimo e independente. Tratamento completo da armadilha em Ferramentas, MCP & RAG §3.

6. Core stateless

A mudança estruturante, da qual quase todas as outras decorrem: o protocolo deixou de ter estado. Não existe mais um momento de abertura de conexão em que cliente e servidor se apresentam e negociam capabilities para o resto da vida da sessão.

É o mesmo erro de sempre — tratar identificação declarada pelo par como se fosse autenticação.

6.2 Estado explícito não é sugestão — é norma

A spec normatiza o handle explícito. Nas palavras dela: estado que precisa atravessar múltiplas requests DEVE ser referenciado por um identificador explícito que o cliente passa em cada request. E mais: o servidor NÃO PODE inferir contexto de requests anteriores na mesma conexão, nem tratar identidade de conexão ou de processo como se fosse continuidade de conversa. Uma conexão stdio aberta não é uma sessão — o cliente pode intercalar requests sem relação nenhuma no mesmo transporte.
Por que isso é bom, apesar do custo. Um protocolo sem estado é horizontalmente escalável por construção: qualquer réplica atende qualquer request, sem afinidade de sessão, sem replicação de estado entre nós, sem reconexão que precise reconstruir contexto. O custo é verbosidade — cada request repete o que antes era dito uma vez. É a troca clássica, e para servidores MCP atrás de balanceador ela compensa com folga.

7. O fim das sessões

Sessões saíram do protocolo. O header de identificação de sessão foi removido, e a spec é explícita: servidor na linha nova DEVE ignorá-lo se um cliente antigo o enviar.

Isso não é só limpeza — é correção de uma classe de vulnerabilidade. A identificação de sessão por header vinha sendo usada, na prática, como se fosse credencial: quem tivesse o identificador era tratado como o dono da sessão. Implementações reais do SDK já foram corrigidas por exatamente esse problema — servir requests de sessão sem verificar o principal autenticado. A revisão nova elimina o mecanismo em vez de tentar blindá-lo, e passa a exigir autenticação por request. Quando um padrão gera a mesma falha em várias implementações, o padrão é o defeito.

Se o seu servidor precisa de continuidade entre chamadas — um carrinho, um rascunho, um cursor de paginação —, o estado passa a ser explícito: um handle devolvido por uma tool e passado de volta como argumento de outra. Isso é melhor design mesmo na linha antiga, e é o conselho mais durável deste guia: handle explícito sobrevive às duas eras; sessão implícita não.

Handle explícito é dado que vem de fora — trate como tal. A spec diz o mesmo sobre o estado opaco que ela mesma define para o fluxo de múltiplas rodadas: o servidor DEVE assumir que está sob controle de um atacante. Assine, valide e escope o handle ao principal autenticado; nunca confie que ele voltou intacto só porque você o emitiu.

9. MRTR — requests de múltiplas rodadas

Num protocolo sem estado, o servidor não pode iniciar uma request para o cliente no meio de uma operação — não há canal aberto para isso. Tudo que dependia disso (pedir uma completação ao cliente, pedir input ao usuário, listar raízes de filesystem) foi reformulado sob um mecanismo único: Multi Round-Trip Requests.

O padrão inverte quem dirige a conversa:

  1. O cliente chama uma tool.
  2. Em vez de responder pronto, o servidor devolve um resultado do tipo input requerido, descrevendo o que precisa e carregando um estado opaco.
  3. O cliente obtém o que foi pedido — do usuário, do modelo, de onde for.
  4. O cliente repete a chamada, agora com as respostas e o estado opaco devolvido.
Quem controla o fluxo agora é o cliente. O servidor nunca "espera" — ele responde e sai. Isso é o que torna cada request independente e o servidor replicável. Também significa que o cliente precisa implementar o laço de retry: um cliente que trate input requerido como erro vai simplesmente falhar em toda tool que precise de interação.

9.1 Onde MRTR vale — e onde não vale

MRTR não é exclusivo de chamada de tool. O servidor pode devolver input requerido em exatamente três requests do cliente, e a spec fecha a lista com um NÃO PODE para todo o resto:

Request do clienteAceita input requerido?
prompts/getsim
resources/readsim
tools/callsim
qualquer outraNÃO PODE

9.2 As formas de wire

CampoOndeO que carrega

Detalhes fáceis de errar na implementação do cliente:
  • O id JSON-RPC DEVE ser diferente entre a request original e o retry — são requests independentes, não continuação.
  • Se veio requestState, o cliente DEVE ecoar o valor exato. Se não veio, o cliente NÃO PODE inventar um.
  • Sem inputRequests, o cliente PODE repetir imediatamente.
  • Esses campos valem só para o retry daquela request — nunca para outras chamadas em paralelo.
Do lado do servidor, duas regras que evitam laço quebrado: ele NÃO PODE pedir um tipo de input que o cliente não declarou em capabilities (pedir elicitation a quem não a suporta), e NÃO PODE assumir que o cliente vai atender ou repetir. Ele também DEVE incluir ao menos um entre inputRequests e requestState em toda resposta de input requerido.

9.3 Proteção do requestState

Este é o ponto de segurança da revisão. O estado trafega pelo cliente, então a spec obriga: o servidor DEVE tratá-lo como input controlado por atacante. Se ele influencia autorização, acesso a recurso ou lógica de negócio, o servidor DEVE proteger a integridade (HMAC ou AEAD) e DEVE rejeitar estado que falhe na verificação. A dispensa só vale quando adulterar não causa nada pior que a request falhar.

Contra replay, a spec manda incluir dentro do payload protegido e verificar na volta:

ItemO que impede
Principal autenticado — rejeitar estado apresentado por outroReuso entre usuários
Expiração curta (TTL) — rejeitar estado vencidoJanela de replay longa
Identificador da request de origem (método + digest dos parâmetros) — rejeitar em request que não bateReuso entre requests diferentes
Nada disso garante uso único. A própria spec avisa: essas medidas limitam a janela e impedem reuso entre usuários e entre requests, mas não garantem consumo único. Se o seu requestState representa algo que só pode ser resgatado uma vez — um pagamento, um cupom, uma aprovação —, você DEVE impor essa invariante do lado do servidor, com estado real. É a exceção onde "stateless" não te salva.

10.1 JSON Schema — duas regras novas, ambas de segurançaAtualizado · 2026-09-30

O dialeto padrão passa a ser JSON Schema 2020-12 quando o schema não declara $schema, e implementações DEVEM suportar ao menos esse dialeto. Junto vieram duas restrições que não são detalhe de tipagem — são defesa:

1. Não resolva $ref de rede automaticamente. JSON Schema permite $ref apontando para URI absoluta. A spec agora diz que implementações NÃO PODEM dereferenciar automaticamente $ref que resolva para URI de rede. Um modo opcional que busque PODE existir, mas DEVE vir desligado por padrão e DEVERIA impor allowlist de hosts — ou, no mínimo, rejeitar loopback, link-local e endereços de rede privada, aplicar timeout e limite de tamanho, e logar as URIs resolvidas. É a mesma família de SSRF que já assombra descoberta de metadados: um schema de tool vindo de servidor não confiável vira requisição para dentro da sua rede.

E o comportamento em falha importa: schema que não valida por $ref externo não resolvido DEVERIA ser rejeitado, não tratado como permissivo em silêncio.

Não é teoria: o GHSA-rwrf-2pqf-9j8j (medium, 2026-09-28) é exatamente um cliente do SDK Python que buscava um $ref escolhido pelo servidor ao validar outputSchema; corrigido em mcp 2.2.0 e 1.30.0.
2. Ponha limite nas palavras-chave de composição. anyOf, oneOf, allOf, if/then/else e $defs são expressivos e caros de validar. A spec recomenda limites — profundidade máxima, teto de subschemas, ou orçamento de tempo por validação — porque um schema malicioso vira vetor de negação de serviço contra o seu validador. Quem aceita schema de terceiro (marketplace de servidores MCP, registro público) precisa disso.
O que ficou mais permissivo: inputSchema e outputSchema aceitam qualquer palavra-chave do 2020-12, e structuredContent aceita qualquer valor JSON — não só objeto. Mais liberdade de modelagem, com as duas travas acima como contrapartida.

HTTP+SSE e os valores de includeContext já eram descritos como deprecados antes de existir política de ciclo de vida; a política nova apenas os reclassificou. Eles não ganham o relógio de 12 meses zerado. Quem ainda está em HTTP+SSE tem a migração mais urgente da lista.
Deprecado ainda funciona — e "elegível" não é "removido". A data marca quando o recurso fica elegível para remoção; a remoção em si é decisão dos mantenedores na preparação de uma release e pode acontecer depois. Implementações novas NÃO DEVERIAM adotar esses recursos; as existentes DEVERIAM migrar antes da data de elegibilidade. O registro oficial, que não lista nenhuma remoção até 2026-09-30, é a fonte viva: /specification/2026-07-28/deprecated.

Parte 3 — Extensões & auth

13. Framework de extensõesAtualizado · 2026-09-30

A revisão formaliza o que antes era zona cinzenta: recursos que não são núcleo do protocolo passam a ser extensões versionadas independentemente, declaradas nas capabilities e identificadas por um esquema de nome com prefixo de domínio reverso. Isso permite que o núcleo fique pequeno e estável enquanto funcionalidades opcionais evoluem no próprio ritmo.

"Extensão oficial" não quer dizer "núcleo", e é justamente essa a graça. Toda extensão oficial usa linguagem normativa (DEVE/DEVERIA/PODE) e passa por processo de proposta com implementação de referência obrigatória em algum SDK antes da revisão. Mas extensões são sempre desligadas por padrão e exigem opt-in explícito do desenvolvedor, e SDK nenhum é obrigado a implementá-las para estar em conformidade com o protocolo. Antes de depender de uma, confirme que o seu SDK a suporta.
Como a negociação acontece. O cliente anuncia extensões em clientCapabilities.extensions dentro do _meta de cada request; o servidor anuncia as dele na resposta do server/discover. É um mapa de identificador para objeto de configuração — objeto vazio significa "suporto, sem ajuste". Se um lado suporta e o outro não, quem suporta DEVE voltar ao comportamento do núcleo ou rejeitar com erro apropriado.
Extensões evoluem sozinhas — e isso tem um preço. Atualizações não passam por revisão dos mantenedores do núcleo. A orientação é preferir flags de capability ou versionamento dentro do objeto de configuração; quando a quebra é inevitável, cria-se um identificador novo (o padrão sugerido é sufixo -v2). Ou seja: o identificador da extensão é parte do seu contrato — trate mudança dele como quebra.
Não construa sobre proposta não normativa. "Em revisão" significa que a superfície pode mudar por inteiro. Extensão oficial tem contrato; proposta em revisão tem intenção.

14. O que mudou em auth

Menos do que o barulho sugere. A autorização não sofreu ruptura equivalente à do núcleo. Ela foi reorganizada em documentos versionados e ganhou alguns requisitos novos de hardening, quase todos endereçando ataques conhecidos de OAuth. Quem já seguia boa prática tem pouco a mudar.
Os subconjuntos de spec que a autorização MCP realmente implementa. A página normativa /basic/authorization lista as fontes externas de que é subconjunto: OAuth 2.1 IETF draft (draft-ietf-oauth-v2-1-13), RFC 6750 (Bearer Token), RFC 8414 (Authorization Server Metadata), RFC 7591 (Dynamic Client Registration), RFC 8707 (Resource Indicators), RFC 9728 (Protected Resource Metadata), RFC 9207 (Authorization Server Issuer Identification), o draft de Client ID Metadata Documents e OpenID Connect Discovery/Dynamic Registration. Autorização em si continua OPCIONAL para uma implementação MCP; quando suportada em transporte HTTP, DEVERIA seguir esta spec — stdio NÃO DEVERIA segui-la (credenciais vêm do ambiente).

14.1 Requisitos novos

RequisitoPor quê
Validar iss na resposta de autorização, antes de trocar o código, sem normalizar antes de compararDefesa contra ataques de confusão entre servidores de autorização (mix-up, RFC 9207 §1). A comparação do emissor é literal: diferença de caixa, porta ou codificação não deve ser normalizada.

MCP servers, do lado deles, NÃO DEVERIAM incluir offline_access nos escopos de WWW-Authenticate nem em Protected Resource Metadata — refresh token não é requisito de resource server.

14.2 Atribuição precisa — o que não é novidade

Dois pontos frequentemente contados errado:
  • A preferência por documento de metadados de cliente sobre registro dinâmico já existia desde a revisão 2025-11-25, como recomendação. A revisão nova não a introduziu — apenas moveu o registro dinâmico para o estado deprecado.
  • O registro dinâmico nunca foi obrigatório. Sempre foi opcional; agora é opcional e deprecado.
Errar essa atribuição faz parecer que há trabalho de migração onde não há.
Ordem de registro no fluxo atual. Use cliente pré-registrado quando houver; caso contrário, use Client ID Metadata Documents (CIMD) quando o authorization server anunciar client_id_metadata_document_supported; só então use registro dinâmico (DCR) como fallback de compatibilidade. O DCR foi formalmente marcado como deprecado em 2026-07-28, mas continua funcionando durante a janela de migração. Credenciais pré-registradas e de DCR devem permanecer vinculadas ao iss que as emitiu; CIMD não é autorização por si só. Fonte: mudanças oficiais de 2026-07-28.
Mudança de status que afeta citações — e ela é mais fina do que "virou tutorial". O documento antigo de boas práticas de segurança saiu do espaço normativo por inteiro e passou a ser material de tutorial (/docs/2026-07-28/tutorials/security/security_best_practices), sem linguagem DEVE/DEVERIA vinculante. Mas parte do conteúdo foi promovida, não só removida: existe agora uma página normativa própria dentro da spec de autorização — /basic/authorization/security-considerations — que usa MUST/SHOULD de verdade e cobre token audience binding, token theft, segurança de transporte (TLS obrigatório), proteção do código de autorização (PKCE), mix-up attacks, open redirection, segurança de CIMD, confused deputy (no sentido estreito de proxy OAuth) e restrição de privilégio do access token. O que ficou só tutorial — sem MUST vinculante, mas com valor prático alto — é o material mais novo e mais operacional: State Handle Hijacking, o detalhamento de SSRF (faixas de IP, DNS rebinding), Local MCP Server Compromise, validação de URL de autorização (XSS/RCE) e Scope Minimization — tratados em Ferramentas, MCP & RAG §11. Ao citar, confira qual das duas páginas você está apontando: a normativa ou a tutorial.

14.3 Seleção e step-up de escopo 2026-07-28

Escopo ganhou um fluxo formal de negociação, para o cliente pedir só o necessário e escalar sob demanda em vez de pedir tudo de uma vez.

PassoRegra
Seleção inicialCliente DEVERIA seguir esta prioridade: (1) o parâmetro scope do header WWW-Authenticate na resposta 401, se presente; (2) na ausência dele, todos os escopos de scopes_supported do Protected Resource Metadata.
Escopo insuficiente em runtimeServidor DEVERIA responder 403 Forbidden com WWW-Authenticate: Bearer error="insufficient_scope", scope="...", resource_metadata="...", reunindo todos os escopos daquela operação num único desafio — desafiar um de cada vez força múltiplas idas e voltas de autorização para uma única operação.
Step-up (reautorização)Cliente calcula a união entre os escopos já concedidos e os do desafio atual antes de reautorizar — isso preserva permissão já obtida em vez de perdê-la a cada desafio pontual (servidor não precisa repetir escopos já concedidos no desafio). Cliente agindo por um usuário DEVERIA tentar o step-up; cliente client_credentials PODE tentar ou abortar direto.
Hierarquia de escopoServidor DEVE considerar que um escopo mais amplo implica os mais estreitos (ex.: admin ⊇ read) ao decidir se um token já é suficiente.
Minimização de escopo é princípio operacional, não só protocolo. A orientação prática — modelo de escopo progressivo, nunca escopo wildcard/omnibus, log de eventos de elevação — está tratada junto com o resto do hardening de servidor em Ferramentas, MCP & RAG §11, para não duplicar a mesma tabela nos dois guias.

A terminologia também acompanhou o fim das sessões: o que se chamava sequestro de sessão passou a ser descrito em termos do handle de estado (State Handle Hijacking), coerente com o modelo novo — ver o controle operacional completo em Ferramentas, MCP & RAG §11.

Parte 4 — Projetar migrável

15. Contratos que sobrevivem

Esta é a parte mais durável do guia: prescrições válidas nas duas linhas. Seguir isto hoje não custa nada em uma integração Legacy e elimina retrabalho quando esse adapter puder usar a revisão atual.

FaçaPor quê
Estado como handle explícito, devolvido por uma tool e passado como argumento a outraFunciona nas duas linhas. Sessão implícita não existe mais na nova.
Assine e escope o handle ao principal autenticadoA spec nova exige tratar estado que passa pelo cliente como adulterável. A antiga já se beneficiava disso.
Autentique cada request, nunca a "sessão"Já era a orientação correta; agora é a única possível.
Use constantes nomeadas para códigos de erroA renumeração quebra comparação literal em silêncio.
Não construa sobre Roots, Sampling, Logging ou retomada de streamDeprecados ou removidos; têm relógio contando.
Operações longas por extensão oficial de tasks, com handle durávelÉ o caminho suportado; improviso com sessão não sobrevive.
Servidor que ignora identificador de sessão recebidoJá é comportamento obrigatório na linha nova; inofensivo na antiga.
O que é um servidor dual-era. Um servidor que atende as duas linhas a partir do mesmo processo: aceita requests no formato antigo (com handshake) e no novo (stateless por request). É o único ponto onde a compatibilidade pode existir, porque o cliente novo não tem como se adaptar. Os SDKs de referência que já falam a revisão nova oferecem esse modo — servir todas as revisões a partir do mesmo servidor.

16. A2A: ciclo de vida entre agentesAtualizado · 2026-09-30

MCP padroniza capabilities expostas a um host; A2A padroniza a interação entre um cliente e um agente remoto. Na fonte oficial atual, a specification wire é 1.0; o release v1.0.1 do repositório (28/05, "Latest" em 2026-09-30) é um patch — três correções de binding HTTP (prioriza application/a2a+json), erros de transcodificação e valores de TaskStatus — e não muda a versão wire Major.Minor.

SDK não é specification. O pacote Python instalável a2a-sdk 1.2.1 foi publicado em 30/09 (a 1.2.0, em 29/09); esse número identifica o SDK e não altera a specification wire 1.0 nem o patch do repositório v1.0.1. Confirme no binding e na suíte do seu cliente quais capacidades foram implementadas antes de afirmar interoperabilidade.
Contrato ao operar A2AAplicação
Versão por requestEnvie A2A-Version: 1.0 em cada request HTTP; o servidor processa a semântica Major.Minor pedida ou devolve VersionNotSupportedError.
Message → TaskUma Message inicia ou continua uma interação e recebe uma resposta direta ou uma Task. A Task carrega status, artifacts e histórico; resultados vivem em artifacts, não em Messages.
Atualização de TaskObtenha estado por polling, streaming ou push. O fluxo termina em TASK_STATE_COMPLETED, TASK_STATE_FAILED, TASK_STATE_CANCELED ou TASK_STATE_REJECTED; TASK_STATE_INPUT_REQUIRED e TASK_STATE_AUTH_REQUIRED pedem continuidade controlada.
Auth por requestO cliente envia credenciais declaradas pelo Agent Card em cada request; o servidor autentica cada request e autoriza pela identidade e política. taskId e contextId não substituem autorização.
Proteção do Agent CardValide binding, URL e requisitos de segurança antes de usar a descoberta. Quando houver assinatura, verifique JWS antes de confiar no card; detalhes estendidos só são obtidos após autenticação e sob controle de acesso.
Não trate descoberta como confiança. O Agent Card descreve capacidades e schemes de segurança; ele não concede privilégio. Proteja a versão estendida, não coloque segredos no card público e preserve autenticação/autorização em cada operação, inclusive nas etapas internas de uma Task.
