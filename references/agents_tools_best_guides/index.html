Guia Completo de Agentes — Portal

Porta de entrada única para construir sistemas de agentes de IA de forma portável entre provedores. O portal organiza um núcleo de orquestração agnóstico (arquitetura, estado, ferramentas, providers, operação), os guias de framework (OpenAI Agents SDK, LangGraph, Google ADK), as referências de provedor (OpenAI, Anthropic, Google) e os temas transversais — contexto, tokens, multimodal, paralelismo e Agent Skills. Para IA e humanos: prosa em PT-BR, identificadores e código em inglês. Agentes: entrem por llms.txt e pelo #para-agentes de cada guia.

Padrões vigentes

  • OpenAI: use a Responses API (client.responses.create) e a Conversations API para estado; o Agents SDK quando o loop roda no seu app. A Decisions API (POST /v1/decisions, só gpt-6-luna) é GA desde 2026-10-22.
  • OpenAI GPT-6: gpt-6-astra e gpt-6.1-sol aceitam reasoning.effort de low a max (sem none nem minimal); com effort diferente de none, não envie temperature, top_p nem top_logprobs. O modelo padrão do Agents SDK é gpt-5.6-luna, não GPT-6: passe model= e model_settings explícitos.
  • Gemini (superfície): use a Interactions API (client.interactions.create, GA desde junho de 2026) com google-genai (Interactions exige 2.3.0 ou superior; fixe <3.0.0) e previous_interaction_id para estado. generateContent só onde a Interactions ainda não cobre: Batch, AFC no SDK Python e cache explícito.
  • Gemini (modelos): gemini-3.8-flash é o padrão; thinking_level aceita low, medium e high (minimal retorna erro no 3.8 Flash). gemini-4-argon só gera texto, não tem Live API nem cache explícito e ignora temperature, top_p e top_k.
  • Anthropic (superfície): use a Messages API (client.messages.create). Sem SDK, envie anthropic-version: 2026-10-21 (os SDKs Python 2.x e TypeScript 1.x já enviam). Nessa versão temperature, top_p e top_k retornam 400 em qualquer modelo.
  • Anthropic (modelos): controle o raciocínio por output_config.effort; budget_tokens retorna 400 nos modelos atuais e o Sonnet 5.5 usa thinking: {"type":"between_tools"} no lugar de disabled. tool_choice any/tool retorna 400 em Fable 5.1, Opus 5.5 e Sonnet 5.5 (o Haiku 5.5 aceita).
  • MCP: implemente a especificação 2026-07-28; no Python fixe mcp>=2.2.0,<3 (frameworks que ainda limitam mcp<2 exigem mcp>=1.30.0,<2) e fastmcp>=4.1.2 (projeto distinto do SDK oficial mcp).
  • LangChain e LangGraph: from langchain.agents import create_agent; supervisor com subagentes expostos como @tool.

Sobre o portal

Este portal não repete o conteúdo dos guias: ele os relaciona. Cada tema profundo (modelos, streaming, thinking, multimodal, paralelismo, tokens, skills) tem um guia dedicado; o núcleo de orquestração define o vocabulário agnóstico (estado durável, projeções, capability registry, handoff vs agent-as-tool) e aponta para esses guias em vez de duplicá-los.

Como ler: agentes de IA começam pelo Resumo para agentes; humanos, por Por onde começar, para escolher uma trilha pelo seu perfil; use a Biblioteca (com busca) para localizar um guia específico; e consulte a Matriz de navegação para ir direto do tópico ao guia que o cobre.

Tese operacional: estado durável vs projeção vs execução

O segredo de um sistema de agentes portável é separar três coisas que os SDKs tendem a misturar:

  • Estado durável — um ledger canônico de itens tipados que você controla (mensagens, tool calls, resultados, reasoning, assets, decisões). É a fonte da verdade.
  • Projeção — o payload que cada provedor exige é uma visão derivada do ledger, não a verdade. Trocar de provedor = trocar a projeção, não perder o estado.
  • Execução — o loop de runtime (registrar → reduzir → projetar → chamar modelo/tool → reduzir de novo) é separado de ambos.
Por que importa: com essa separação, previous_response_id (OpenAI), thread/checkpointer (LangGraph) ou session/state (ADK) viram projeções intercambiáveis do mesmo ledger — e não três arquiteturas incompatíveis. O núcleo de estado detalha o contrato.

Os 4 planos que não devem ser misturados

Toda decisão de design cai em um destes planos. Misturá-los é a causa mais comum de acoplamento.

Beta, experimental e "a confirmar" status

Nem tudo que os provedores anunciam está estável. Esta seção separa o que é GA (estável, entra nos guias como fato) do que ainda é beta/experimental/preview/RC/alpha (documentado, mas com contrato que pode mudar e, às vezes, header de opt-in) e do que é "a confirmar" (não verificado em fonte primária — nunca tratado como fato).

O que "beta" significa aqui. Disponível na API, porém com contrato instável: pode exigir header/flag de opt-in (ex.: OpenAI-Beta: responses_multi_agent=v1), mudar sem aviso e não valer SLA. Documentamos rotulado com beta; use com feature flag e cubra com evals antes de produção. Distinto de GA (estável) e de a confirmar (sem verificação primária).

As 6 garantias do super-guia

  • ☑ Fonte oficial: todo fato perecível (modelos, parâmetros, versões) é verificado contra a doc oficial, com data de leitura; o que não foi confirmado fica marcado UNVERIFIED.
  • ☑ Só o estado vigente: cada guia descreve apenas a linha corrente de modelos, SDKs e APIs, sem histórico de versões; o git é o arquivo.
  • ☑ Agnóstico por padrão: o núcleo não hardcoda provedor; o específico de framework vive em guias próprios.
  • ☑ Sem duplicação: cada tema tem um dono; os demais guias fazem cross-link em vez de repetir.
  • ☑ Para IA e humanos: prosa PT-BR + referência consultável; identificadores e código em inglês.
  • ☑ Acessível e portável: tema claro/escuro, navegação por teclado, HTML auto-contido sem dependências externas.
