Resumo para agentes (verificado 2026-09-30) ¶Novo · 2026-09-30

Superfície atual

OpenAI = Responses API (input_image/input_file). Gemini = client.interactions (itens image/document/video/audio; saída em steps[], generateContent só para Batch, cache explícito, AFC Python e safety settings). Anthropic = Messages API (só imagem e PDF; sem áudio nem vídeo).

pip install "openai>=3,<4" "google-genai>=2.3,<3" "anthropic>=1,<2"   # atuais: 3.22.1 / 2.25.0 / 1.9.0 (2026-09-30)
# OpenAI
client.responses.create(model="gpt-6-astra", input=[{"role": "user", "content": [
    {"type": "input_text", "text": "Descreva"},
    {"type": "input_image", "image_url": f"data:image/png;base64,{b64}", "detail": "high"}]}])
# Gemini (texto antes da imagem; resolution é por item)
client.interactions.create(model="gemini-3.8-flash", input=[
    {"type": "text", "text": "Descreva"},
    {"type": "image", "data": b64, "mime_type": "image/png", "resolution": "high"}])
# Anthropic
client.messages.create(model="claude-opus-5-5", max_tokens=1500, messages=[{"role": "user", "content": [
    {"type": "image", "source": {"type": "base64", "media_type": "image/png", "data": b64}},
    {"type": "text", "text": "Descreva"}]}])

Faça / Não faça

  • Não use generate_content/inline_data/file_data para multimodal novo → use interactions.create com {type, data|uri, mime_type}.
  • Não use response_modalities/image_config/response_mime_type → use response_format ({"type":"audio"}, {"type":"image","aspect_ratio":...}).
  • Gemini: use "resolution" por item (ultra_high só imagem, só Gemini 3); não use generation_config.media_resolution global (UNVERIFIED).
  • Gemini vídeo: "processing":"agentic" só em 3.8/3.7/3.6 Flash e 3.5 Flash-Lite; use static (default, 1 FPS) para clips < 5 min ou precisão por frame. Requests longos: stream ou background.
  • Gemini: não envie temperature/top_p/top_k nem thinking_budget; minimal em thinking_level dá erro no 3.8 Flash.
  • OpenAI: não use Videos API/Sora (desligados em 2026-09-24, sem substituto) nem Assistants (2026-08-26); vídeo de entrada = extrair frames + gpt-transcribe.
  • OpenAI: não use gpt-4o-transcribe/whisper-1 em código novo (shutdown 2027-02-26); só eles fazem timestamps/diarização até lá. Chat Completions aceita só PDF como file.
  • Anthropic: não envie áudio nem vídeo; não use computer_20251124 (400 em Opus 5.5/Sonnet 5.5 → computer_toolset_20260801), tool_choice any/tool (400) nem thinking:{"type":"disabled"} em Opus 5.5. Files API é GA, sem header beta.
  • Não afirme um único número de tokens de mídia no Gemini: as páginas oficiais divergem (imagem 258 × 1.120; áudio 32 × 25 tok/s; vídeo 263/100/300 tok/s × 70 por frame) → meça com count_tokens e usage.

OpenAI GPT-6, GPT Image 2.5, gpt-transcribe

  • Flagship gpt-6-astra; gpt-6.1-sol lançado em 2026-09-29. Imagem de entrada por patches (multiplicador 1,2×) — §4.2.

Gemini Interactions API como superfície principal

  • Exemplos multimodais usam client.interactions.create com itens image/document/video/audio e steps[] na saída — §6.
  • gemini-3.8-flash GA (2026-09-02); gemini-3.5-transcribe GA (2026-08-26); gemini-omni-1.1-flash (vídeo 3–10 s) substitui gemini-omni-flash-preview.
  • Só generateContent: Batch, cache explícito, AFC em Python e safety settings — §5.2.
  • Desligamentos próximos: gemini-2.5-flash-image em 2026-10-02 e Veo 3.1 em 2026-10-22.

Anthropic Opus 5.5, Sonnet 5.5, Fable 5.1, Haiku 4.5

  • Modelos atuais: claude-opus-5-5 (recomendado), claude-sonnet-5-5, claude-fable-5-1 e claude-haiku-4-5 — §7.1.
  • Computer use GA via computer_toolset_20260801; computer_20251124 é rejeitado nos modelos atuais.
  • Files API e Skills sem beta header; code execution nas versões 20250825, 20260120 e 20260521.
  • Modelos aposentados e datas: Legado e migração.
Divergências oficiais registradas (2026-09-30). Tokens por mídia no Gemini: as páginas de image/audio/video e de tokens dizem 258 tokens por tile e 32 tokens/s de áudio; a página media-resolution dá 1.120 tokens por imagem em high, 25 tokens/s e 70/280 por frame de vídeo no Gemini 3 — use usage para custo real. Limite inline: 100 MB (50 MB para PDF) na tabela de métodos de entrada, 20 MB nas páginas de mídia. Nomes de eventos SSE divergem entre páginas da Interactions API. MCP remoto no Gemini 3: a overview diz que não é suportado, a página de function calling documenta mcp_server. gemini-omni-1.1-flash não consta da lista de modelos da overview. Em todos os casos o guia mostra os dois valores e a fonte.

3.11 Coding tool, ZDR e onde roda o Python — síntese de decisão ¶Atualizado · 2026-09-30

Esta subseção consolida 3.5 + 3.8 + 3.9 em um único quadro de decisão para três perguntas operacionais que aparecem juntas em quase todo projeto multimodal: "Para mandar um arquivo, preciso ativar coding tool? Isso é ZDR? Onde o Python realmente roda?". Cobre os quatro modos de entrega (inline, Files API, File Search/RAG, code execution), a posição por provider, ZDR cruzado, sandbox lado a lado, reupload por modo, fluxo recomendado para Excel e disponibilidade em clouds gerenciadas.

TL;DR em três linhas.
① Só quer ler/resumir/perguntar? Não precisa coding tool — inline, Files API ou File Search resolvem.
② Quer manipular de verdade? (joins, pivots, gerar arquivo, calcular margem, plotar) — precisa coding tool do provider ou Python no seu backend.
③ Compliance ZDR estrito? Faça o cálculo determinístico no seu backend e mande ao modelo só schema + amostra + erros + objetivo — evite Files API persistente, explicit cache e code execution server-side onde não for ZDR-elegível.

3.11.3 Isso é ZDR? — não confundir "API não treina com meus dados" com Zero Data Retention

"API não treina por padrão" e "Zero Data Retention" são coisas diferentes. Treinamento e logging operam em planos distintos; cada provider tem regras próprias de elegibilidade por endpoint/feature. Anthropic: matriz ZDR lida em 2026-09-30 (Files API e code execution: não elegíveis). OpenAI e Gemini: texto lido em 2026-05-23, não reverificado em 2026-09-30 UNVERIFIED (2026-09-30).

ProviderTreinamento por padrãoZDR com arquivo / código
OpenAI "data sent to the OpenAI API is not used to train or improve OpenAI models (unless you explicitly opt in to share data with us)". Por padrão, abuse-monitoring logs são gerados e retidos por até 30 dias. /v1/responses é ZDR-eligible com limitações: sob ZDR, store é tratado como false. /v1/files é "No" na tabela ZDR e mantém application state até deleção. Hosted Shell / Code Interpreter podem escrever estado temporário no filesystem do container enquanto ele estiver ativo; o estado é apagado quando o container expira ou é deletado. Pegadinha Background mode é aceito em projetos ZDR com store=false, mas retém temporariamente a resposta em disco por ~10 min para execução e polling; ZDR elegível não significa retenção física literal zero. MCP servers são third-party e ficam fora de ZDR; image/file inputs em /v1/responses passam por CSAM scan e podem ser retidos para revisão mesmo sob ZDR/MAM.
Gemini Para Paid Services: "Google does not use your prompts (including associated system instructions, cached content, and files such as images, videos, or documents) or responses to improve our products". Para ZDR real: prompts/responses podem ser logados por tempo limitado para abuse; ZDR precisa ser aprovado por projeto; Interactions API deve usar store=false; File API storage é INDEPENDENTE do ZDR logging — os arquivos ficam armazenados até expirar (48 h) ou serem deletados manualmente; explicit caching (cached_content) deve ser evitado para footprint zero absoluto. Pegadinha crítica Grounding com Google Search/Maps SEMPRE retém prompts/output por 30 dias, SEM opt-out. A documentação de implicit caching descreve um mecanismo automático e best-effort, mas não promete genericamente RAM, TTL de 24 h nem hit; confirme a postura de retenção no contrato de dados/ZDR aprovado para o projeto e observe hits pelos campos de usage.
Anthropic Dados retidos não são usados para treinamento sem permissão expressa. PDF support nativo é ZDR-elegível. Files API NÃO é ZDR-elegível — segue retenção padrão; arquivos persistem até deleção explícita. Code Execution NÃO é ZDR-elegível — dados do container (uploads, artefatos, outputs) retidos por até 30 dias. Message Batches também NÃO é ZDR-elegível. Uploads pelo usuário não podem ser baixados de volta via API; só arquivos criados por skills/code execution têm downloadable: true.
Arquitetura realmente ZDR / zero-footprint: evite Files API persistente, File Search store, caches explícitos e code execution server-side quando não forem elegíveis. Envie conteúdo inline quando couber, use store=false onde aplicável (Gemini Interactions API; OpenAI Responses sob ZDR já trata como false automaticamente), e faça processamento determinístico no seu backend para a parte sensível.

detail parameter — semantics per model family

detail controls the resolution at which the model processes the image. Allowed values: low, high, original (newer models), auto (default).

DetailBehavior
lowModel receives a low-resolution 512×512 version. Fast and cheap; lose fine detail.
highHigh-fidelity tokenization (still bounded by the model's patch budget or tile budget).
originalAvailable on gpt-5.4 and later. Largest patch budget; recommended for computer-use, click-accuracy, dense text, and spatially sensitive tasks.
autoDefault. auto equals original on gpt-6-astra, gpt-5.6-* and gpt-5.5; it equals high on gpt-5.4, -mini and -nano.

Fonte: guides/images-vision — lida em 2026-09-30. Para OCR, detecção de objetos pequenos e computer use, a doc recomenda "detail": "original" quando suportado.

Model sizing behavior (verificado 2026-09-30)

Model family Supported detail levels Sizing behavior
gpt-6-astra low, high, original, auto low cabe em 512×512. high → até 2.500 patches E 65.535 px de dimensão máxima (ambos valem). original preserva as dimensões (reduz só acima de 65.535 px). auto ≡ original.
gpt-5.6-sol, -terra, -luna low, high, original, auto low cabe em 512×512. high → 2048×2048 px e 2.500 patches. original preserva as dimensões (reduz só acima de 65.535 px). auto ≡ original.
gpt-5.5 low, high, original, auto low cabe em 512×512. high → 2.500 patches e 2048 px. original → 10.000 patches e 6000 px. auto ≡ original.
gpt-5.4, gpt-5.4-mini, gpt-5.4-nano low, high, original, auto low usa 2048 px e orçamento de 6.144 patches (pode custar mais tokens que high). high → 2.500 patches e 2048 px. original → 10.000 patches e 6000 px. auto ≡ high.
Teto de 30.000 patches por imagem. Em qualquer modelo e nível de detail, uma imagem que ainda precise de mais de 30.000 patches depois do redimensionamento é rejeitada, não reduzida. gpt-6-sol, gpt-6-luna e gpt-6.1-sol não constam na tabela de sizing oficial — UNVERIFIED se seguem as regras do Astra ou do gpt-5.6; confira com responses.input_tokens.count (§4.11). Fonte: guides/images-vision#model-sizing-behavior — lida 2026-09-30.

Token cost formulas

Os modelos atuais usam tokenização por patches de 32 × 32 px:

A. patch_count = ceil(width/32) * ceil(height/32)       (após o limite de pixels do detail)
B. se houver orçamento de patches e patch_count > orçamento, reduza a imagem proporcionalmente:
   shrink_factor = sqrt((32^2 * patch_budget) / (width * height))   (ajustado para pixels inteiros)
C. resized_patch_count = ceil(resized_width/32) * ceil(resized_height/32)
   > 30.000 → a API rejeita a request
D. billed_tokens = ceil(resized_patch_count * model_multiplier)

O multiplicador é 1,2 em gpt-6-astra, gpt-5.6-sol/-terra/-luna, gpt-5.5, gpt-5.4, gpt-5.4-mini, gpt-5.4-nano e gpt-5.2; aplica-se uma vez, só aos tokens da imagem. Exemplo oficial (gpt-6-astra, detail: high): 1024 × 1024 → 1024 patches → ceil(1024 × 1,2) = 1.229 tokens; 2048 × 2048 → reduzida a 1600 × 1600 (2.500 patches) → 3.000 tokens. Use a calculadora oficial para estimar uma imagem; o método por tiles só se aplica a modelos antigos (Legado).

Documented vision limitations (verbatim from the guide)

  • Medical images: Not suitable for CT scans, MRIs, or medical advice.
  • Non-English: May underperform on non-Latin scripts (e.g. Japanese, Korean).
  • Small text: Enlarge text within the image; use "detail": "original" if available.
  • Rotation: May misinterpret rotated/upside-down content.
  • Visual elements: Struggles with graphs where colors/styles (solid/dashed/dotted) vary.
  • Spatial reasoning: Struggles with precise spatial localization (e.g. chess positions).
  • Accuracy: May generate incorrect descriptions/captions in certain scenarios.
  • Image shape: Struggles with panoramic and fisheye images.
  • Metadata and resizing: Doesn't process original file names or EXIF; resizes per detail.
  • Counting: Approximate counts only.
  • CAPTCHAs: Submissions are blocked for safety.

4.3 PDF e documentos ¶Atualizado · 2026-09-30

PDF é o único tipo de arquivo para o qual a API extrai texto e imagens de página para o contexto — apenas em modelos com visão (a doc cita gpt-4o e posteriores; toda a família gpt-6, gpt-5.6-*, gpt-5.5 e gpt-5.4* entram). developers.openai.com/api/docs/guides/file-inputs — lida em 2026-09-30.

Three input modes

You can attach a PDF to Responses as input_file using:

  1. file_id returned from a client.files.create(..., purpose="user_data") upload.
  2. file_url pointing at an external PDF.
  3. file_data base64-encoded PDF bytes (with filename).

detail em input_file (PDF)

Todo item input_file de PDF na Responses API aceita o campo opcional detail (auto por padrão, low ou high), que controla o processamento das imagens de página (o texto extraído sempre entra). Use low para gastar menos tokens de input e high para gráficos densos, letra miúda ou diagramas. O default depende do modelo: de gpt-5.6 em diante (inclui a família gpt-6) auto usa high; em modelos anteriores usa low. 

{ "type": "input_file", "file_id": "file-abc123", "detail": "high" }

Fonte: guides/file-inputs#pdf-detail-levels — verificado 2026-09-30.

Size limits

  • Por arquivo: < 50 MB; o total de todos os arquivos de uma request também é limitado a 50 MB.
  • Teto de páginas: UNVERIFIED — reconfirmado 2026-09-30: a página file-inputs documenta só o limite de 50 MB. O número "100 páginas" citado por terceiros não aparece no texto oficial.
  • Para arquivos maiores que 50 MB ou PDFs de centenas de páginas, use File Search (vector store) em vez de input_file; vector stores criadas a partir de nov/2025 suportam até 100.000.000 arquivos.

How OpenAI tokenizes PDFs

"PDF parsing includes both extracted text and page images in context, which can increase token usage." — File-inputs guide.

The Token-counting guide also confirms that count_tokens supports file_id, file_url, or file_data "currently PDFs" and "reflects the model's full processed input."

The Responses API input_file mechanism accepts a wide list of file types beyond PDF, but the processing path differs depending on type.

4.5 Code Interpreter ¶

The Code Interpreter tool runs Python in a sandboxed container that the model controls. It is exposed in the Responses API.

"While we call this tool Code Interpreter, the model knows it as the 'python tool'." — Code Interpreter guide.

Tool definition

{
  "type": "code_interpreter",
  "container": { "type": "auto", "memory_limit": "4g" }
}

container may be:

  • {"type": "auto", "memory_limit": "...", "file_ids": ["..."]} — auto-create or reuse a recent container, optionally pre-attached files.
  • "cntr_..." — an explicit container ID created via POST /v1/containers.

memory_limit accepts "1g" (default), "4g", "16g", or "64g". Higher tiers are billed at the built-in-tools rate; the limit is fixed for the container's lifetime.

Container lifecycle

  • Expiration: A container expires if it is not used for 20 minutes. Any container operation (retrieve, add file, delete file) refreshes last_active_at.
  • Recovery: You cannot reanimate an expired container — files and in-memory Python state are gone. Always treat containers as ephemeral and download any files you care about while the container is alive.
  • Discovery: Auto-created containers are still reachable via GET /v1/containers/{id}.

Frame-extraction workflow (the working pattern)

import base64
import cv2
from openai import OpenAI

client = OpenAI()

def extract_frames(video_path, every_n_seconds=2, max_frames=24):
    cap = cv2.VideoCapture(video_path)
    fps = cap.get(cv2.CAP_PROP_FPS)
    frames_per_step = int(fps * every_n_seconds)
    frames = []
    idx = 0
    while cap.isOpened() and len(frames) < max_frames:
        ok, frame = cap.read()
        if not ok:
            break
        if idx % frames_per_step == 0:
            ok2, buf = cv2.imencode(".jpg", frame)
            if ok2:
                frames.append(base64.b64encode(buf.tobytes()).decode("utf-8"))
        idx += 1
    cap.release()
    return frames

# Transcrição da faixa de áudio (extraia o áudio antes, p. ex. com ffmpeg; limite de 25 MB)
with open("meeting.mp3", "rb") as audio:
    transcript = client.audio.transcriptions.create(model="gpt-transcribe", file=audio).text

frames = extract_frames("meeting.mp4", every_n_seconds=2, max_frames=24)
content = [{"type": "input_text", "text": "Summarize this meeting clip. Audio transcript:\n" + transcript}]
content += [
    {
        "type": "input_image",
        "image_url": f"data:image/jpeg;base64,{f}",
        "detail": "low",
    }
    for f in frames
]

resp = client.responses.create(
    model="gpt-6-astra",
    input=[{"role": "user", "content": content}],
)
print(resp.output_text)

Transcrição de arquivo — gpt-transcribe

gpt-transcribe é o modelo recomendado para gravações no idioma original. Aceita prompt (contexto livre), keywords (termos literais esperados) e languages (idiomas de entrada esperados), que substitui o language singular — não envie os dois. Cada keyword fica em uma linha, sem <, >, CR ou LF; a API rejeita a request inteira se encontrar esses caracteres ou se o prompt passar do limite. A resposta traz text e languages detectados ([] quando não há previsão confiável). Keywords são dicas, não saída obrigatória.

Streaming

  • Arquivo já gravado: stream=True com gpt-transcribe emite eventos transcript.text.delta e fecha com transcript.text.done (que inclui languages). Não exige sessão Realtime.
  • Áudio ao vivo: sessão Realtime com type: "transcription" e gpt-live-transcribe (WebSocket para pipelines de servidor, WebRTC para áudio de navegador); PCM 24 kHz; omita audio.input.turn_detection ou use null — o modelo não suporta server_vad nem semantic_vad. Aceita prompt, keywords e languages; não devolve timestamps por palavra, rótulos de falante, confiança nem idioma detectado.
Timestamps, legendas (srt/vtt), diarização e tradução para inglês não existem no gpt-transcribe. A doc oficial ainda indica whisper-1 e gpt-4o-transcribe-diarize para isso, mas ambos têm shutdown em 2027-02-26; o substituto oficial para essas funções UNVERIFIED (nenhum anunciado). Detalhes e exemplos em Legado e migração.

Áudio longo (> 25 MB)

Use um formato comprimido ou divida o arquivo em pedaços de até 25 MB, evitando cortar no meio de uma frase (ex.: PyDub), e carregue o contexto do pedaço anterior pelo prompt.

Realtime audio

Para áudio ao vivo (microfone, chamadas, media streams) use uma sessão Realtime:

  • Conecte por WebSocket ou WebRTC (gpt-realtime-2.1, gpt-realtime-translate, gpt-realtime-whisper); o GPT-Live (gpt-live-1, GA 2026-09-10) usa /v1/live/sessions.
  • Envie PCM16 com input_audio_buffer.append (cada chunk ≤ 15 MB) e use VAD do servidor (session.update) ou faça commit manual.
  • Receba response.output_audio.delta (PCM base64) e eventos conversation.item.input_audio_transcription.*.
  • Formatos: PCM16 (24 kHz, mono, little-endian), g711_ulaw, g711_alaw. Sem MP3 ou Opus.
  • Duração máxima de uma sessão Realtime: 60 minutos (realtime-conversations, lida 2026-09-30).

Text-to-speech

POST /v1/audio/speech com gpt-4o-mini-tts. O endpoint tem 13 vozes (alloy, ash, ballad, coral, echo, fable, nova, onyx, sage, shimmer, verse, marin, cedar); a OpenAI recomenda marin ou cedar e as vozes são otimizadas para inglês. 4.10 Limitações & gotchas ¶

Cross-cutting list to surface as "watch outs" in the comparative HTML guide.

Vision

  • Medical images: not for diagnosis.
  • Non-Latin scripts and small text are weaker — enlarge text, prefer detail: "original" on gpt-5.4+.
  • Images needing more than 30,000 patches are rejected, not resized.
  • Rotated content can be misread.
  • Graphs with dashed/dotted/colored variants: weak comprehension.
  • Spatial reasoning (chess, layout) is unreliable.
  • Panoramas and fisheye distortion: weak.
  • File metadata (EXIF, filename) is never read.
  • CAPTCHAs are blocked.
  • TPM accounting: every image counts.
  • Counting objects: approximate.

Files

  • input_file is per-request capped at 50 MB total (per file ≤ 50 MB).
  • Non-PDF docs lose embedded images/charts (text-only extraction). Convert to PDF if visuals matter.
  • Spreadsheet ingestion stops at the first 1,000 rows per sheet. Use Code Interpreter or Hosted Shell for larger sheets.
  • PDF parsing needs vision-capable models (família gpt-6, gpt-5.6, gpt-5.5, gpt-5.4). Older models won't see page images.
  • purpose matters: model-input use cases should use user_data.

Code Interpreter

  • Container expires after 20 minutes of idle.
  • All container files vanish at expiration — download what you need.
  • Filesystem is ephemeral block storage; no networking unless explicitly enabled.
  • memory_limit is fixed for life of container.
  • Rate limit: 100 RPM per org for the tool.

Audio

  • Transcription upload: 25 MB max, must be chunked for longer.
  • gpt-transcribe: no timestamps, no diarization, no subtitle formats, no translation; language (singular) is replaced by languages[].
  • gpt-live-transcribe: no word timestamps, speaker labels, confidence or detected language; no server_vad/semantic_vad.
  • Realtime sessions: 60-minute max; chunks ≤ 15 MB; PCM16/G.711 only; no MP3/Opus input.

Video

  • No native video input on Responses; use the frame-extraction + transcription pattern.
  • No video generation on OpenAI (see Legado).

Image-input billing cheatsheet

Gemini Interactions API — deep dive ¶Atualizado · 2026-09-30

A Interactions API é a superfície padrão deste guia para Gemini 3.x. Mantém estado server-side via previous_interaction_id, devolve uma timeline tipada de steps[] (em vez de candidates[].content.parts[]), roda tarefas longas em background (background=true), permite cancelamento explícito e retomada de SSE por last_event_id, e recebe a entrada em input[] com itens tipados (text, image, audio, video, document). Esta seção cobre cada modalidade, tool, parâmetro, tipo de step, limite e gotcha, com exemplos em Python e curl. Contratos reverificados em 2026-09-30 contra a overview oficial e as páginas por modalidade (imagem, documentos, vídeo, áudio, transcrição, fala, function calling).

Status (verificado em 2026-09-30): GA e recomendada para projetos novos desde junho/2026. steps[] é o único schema (o outputs[] antigo foi removido em 2026-06-08). Os quatro recursos que ainda só existem no generateContent estão em §5.2; o mapeamento de código antigo está em Legado e migração. A overview cobre o Gemini Developer API; a disponibilidade equivalente da Interactions no Vertex AI (hoje "Gemini Enterprise Agent Platform") UNVERIFIED (2026-09-30) — confirme na documentação do target antes de assumir.

6.1 API surface ¶

A Interactions API expõe um único recurso interactions sob https://generativelanguage.googleapis.com/v1beta/interactions (v1 também aceita Interactions; o default dos SDKs é v1beta, e Service Tier, Live API, Agents, Webhooks, cache, Computer Use e a tool MCP existem só em v1beta). O estado da conversa é persistido no servidor por padrão (store=true): os turnos seguintes referenciam previous_interaction_id em vez de reenviar o histórico. Autenticação pelo header x-goog-api-key: $GEMINI_API_KEY. steps[] é o único schema de resposta, com SDK Python/JS ≥ 2.3.0.

Geração e edição de imagem (model output)

Modelos de imagem (gemini-3.1-flash-image — Nano Banana 2, gemini-3.1-flash-lite-image — versão Lite e gemini-3-pro-image — Nano Banana Pro) devolvem blocos image dentro de steps[]. O formato de saída vai em response_format (type: "image", mime_type, aspect_ratio, image_size); ele substitui os antigos response_modalities e generation_config.image_config. Leia o resultado em interaction.output_image e edite no turno seguinte apontando previous_interaction_id.

import base64

interaction = client.interactions.create(
    model="gemini-3.1-flash-image",
    input="Gere uma ilustração de uma cidade futurista ao pôr do sol.",
    response_format={
        "type": "image",
        "mime_type": "image/jpeg",
        "aspect_ratio": "16:9",
        "image_size": "2K",
    },
)
with open("city.jpg", "wb") as f:
    f.write(base64.b64decode(interaction.output_image.data))

# Edição: mesmo modelo, turno seguinte encadeado
edit = client.interactions.create(
    model="gemini-3.1-flash-image",
    input="Troque o pôr do sol por amanhecer. Não mude mais nada.",
    previous_interaction_id=interaction.id,
    response_format={"type": "image", "mime_type": "image/jpeg", "aspect_ratio": "16:9"},
)

# Forma explícita: iterar os steps
for step in edit.steps:
    if step.type == "model_output":
        for c in step.content:
            if c.type == "image":
                print("mime:", c.mime_type, "bytes:", len(c.data))

6.3 PDF / documentos ¶

PDFs e outros documentos entram via items {type: "document"}. PDF é a modalidade de documento primária: o modelo recebe a representação visual de cada página em ~768×768 a 3072×3072 px e cobra 258 tokens por página (página de documentos). 6.4 Office / Excel / CSV ¶

A Interactions API não tem conversores nativos para .docx, .pptx, .xlsx, .csv. Há dois caminhos práticos:

  1. Pré-converter para PDF (LibreOffice headless, Aspose, scripts) e enviar como {type:"document", mime_type:"application/pdf"} — preserva layout, gráficos e tabelas com fidelidade visual.
  2. Usar a tool code_execution (ver §6.5) e deixar o sandbox Python ler o arquivo com openpyxl, pandas, python-docx, python-pptx. Útil para analytics e transformação tabular.

A página oficial de documentos (lida em 2026-09-30) afirma que só PDF é entendido visualmente; TXT, Markdown, HTML, XML e similares são extraídos como texto puro (tags, formatação e gráficos se perdem). .docx, .pptx e .xlsx não são citados como entrada nativa: siga os dois caminhos acima.

6.5 Code execution ¶

A tool {type: "code_execution"} habilita um sandbox Python que o modelo invoca autonomamente para analytics, plotting, parsing, ou validação determinística. No schema novo, os passos da execução são surfaceados como step.type dedicados:

step.typeConteúdoQuando
code_execution_callid, arguments.code (Python), arguments.language (python)Modelo emite código.
code_execution_resultcall_id (pareia com code_execution_call.id), is_error, result (string — stdout/stderr)Sandbox executa e devolve.

Exemplo Python — CSV analytics

csv_file = client.files.upload(file="transactions.csv")
interaction = client.interactions.create(
    model="gemini-3.8-flash",
    input=[
        {"type": "text", "text": "Qual o ticket médio por mês no CSV? Retorne uma tabela markdown."},
        {"type": "document", "uri": csv_file.uri, "mime_type": "text/csv"},
    ],
    tools=[{"type": "code_execution"}],
)

for step in interaction.steps:
    if step.type == "code_execution_call":
        print("--- código ---")
        print(step.arguments.code)
    elif step.type == "code_execution_result":
        print("--- resultado (is_error=", step.is_error, ") ---")
        print(step.result)
print(interaction.output_text)

Combine code_execution com outros tools — file_search para RAG, url_context para enriquecer dados, ou function para validar regras de negócio cliente-side.

6.6 Vídeo ¶

Vídeos entram como {type: "video"}. O campo processing do item escolhe como o vídeo vai ao contexto: "static" (default em todos os modelos: frames a 1 FPS, áudio a 1 Kbps mono, timestamps por segundo) ou "agentic" (o modelo navega pela linha do tempo e carrega só a transcrição, os frames e o áudio de que precisa; a doc cita até 88% menos tokens e ~7% mais qualidade em vídeo longo). O modo agentic está disponível em Gemini 3.8 Flash, 3.7 Flash, 3.6 Flash e 3.5 Flash-Lite. Comece por agentic em vídeos longos ou perguntas sobre momentos específicos; use static em clipes < 5 min sensíveis a latência ou quando precisar de precisão por frame. Recorte (start_offset/end_offset) e FPS customizado só existem em static. resolution (tokens por frame) e processing são independentes e combináveis.

Transcrição (STT) com gemini-3.5-transcribe

Para transcrição use o modelo dedicado gemini-3.5-transcribe (GA 2026-08-26): detecção automática de idioma (85+ locales, com code-switching), diarização, timestamps por palavra e vocabulário customizado. O comportamento fica em generation_config.transcription_config; o modo default é verbatim.

interaction = client.interactions.create(
    model="gemini-3.5-transcribe",
    input=[{"type": "audio", "uri": audio.uri, "mime_type": audio.mime_type}],
    generation_config={
        "transcription_config": {
            "language_codes": ["pt-BR"],          # opcional; vazio = detecção automática
            "mode": {
                "type": "verbatim",
                "diarization_mode": "speaker",     # spk_1, spk_2 ... (até 8 falantes)
                "timestamp_granularities": ["word"],
            },
        }
    },
)
print(interaction.output_text)
  • "mode": "smart" remove disfluências e formata o texto (parágrafos, listas, datas, valores), mas não combina com diarização nem com timestamps.
  • custom_vocabulary (até 1.000 termos; melhor com até 100) não combina com diarização nem com timestamps — a API rejeita a request.
  • Limites: 1 hora de áudio por request unária; 30 minutos quando diarização ou timestamps por palavra estão ligados. Timestamps por palavra podem reduzir a acurácia. Preço: US$ 0,003/min de áudio de entrada.

Fonte: transcribe e pricing, lidas em 2026-09-30.

Geração de áudio (TTS)

Os modelos gemini-3.8-flash-tts (GA 2026-09-22) e gemini-3.8-flash-lite-tts tratam o texto de entrada como transcrição literal: instruções de entrega (estilo, ritmo) e rótulos de falante vão em anotações speech_metadata, e eventos vocais pontuais ficam inline entre ângulos (<laugh>, <short pause>). O formato de saída vai em response_format={"type": "audio"} (substitui response_modalities) e voz/falantes em generation_config.speech_config.

import base64

interaction = client.interactions.create(
    model="gemini-3.8-flash-tts",
    input=[{
        "type": "user_input",
        "content": [{
            "type": "text",
            "text": "Boas-vindas ao nosso serviço!",
            "annotations": [{"type": "speech_metadata", "style": "cheerful and friendly"}],

    response_format={"type": "audio"},
    generation_config={"speech_config": [{"voice": "Kore"}]},
)
with open("saida.wav", "wb") as f:

  • Formato: resposta unária = WAV (audio/wav, 24 kHz mono 16-bit); em streaming, PCM bruto audio/l16. Em response_format também aceita audio/mulaw, audio/alaw e sample_rate (ex.: 24000, 16000, 8000).
  • Vozes: pré-construídas, biblioteca estendida (GET /v1beta/voices), voice design e voice replication (IDs voice_…).

6.9 Cache implícito ¶

Na Interactions API o caching é implícito: habilitado automaticamente e best-effort, tanto no modo stateful (com previous_interaction_id) quanto no stateless. O mínimo é de 4.096 tokens de prefixo idêntico nos Gemini 3.8/3.7/3.6/3.5 Flash e no 3.1 Pro (2.048 nos modelos 2.5). Em hits, os tokens cacheados aparecem em usage.total_cached_tokens e usage.cached_tokens_by_modality; ausência de hit é comportamento possível, não falha de contrato. O cache explícito (client.caches) não existe na Interactions: use o exemplo de §5.2. Fonte: caching, lida em 2026-09-30.

Exemplo Python — cache implícito via multi-turn

i1 = client.interactions.create(
    model="gemini-3.8-flash",
    input=[
        {"type": "text", "text": "Leia este edital."},
        {"type": "document", "uri": edital.uri, "mime_type": "application/pdf"},
    ],
)

# segundo turno: prefixo idêntico cacheado server-side

    model="gemini-3.8-flash",

Forking de conversas

Aponte previous_interaction_id para qualquer interaction.id anterior — não precisa ser o último turno. Isso permite ramificar a árvore de conversas sem perder o prefixo cacheado, útil para multi-tenant ou A/B em ramos diferentes.

6.11 Function calling & state machine ¶

Function calling client-side segue um ciclo claro em três passos: (1) modelo recebe input + tools e devolve status: "requires_action" com um step function_call; (2) cliente executa a função; (3) cliente cria nova interaction com previous_interaction_id e passa o resultado como step function_result, reenviando tools.

Em streaming: delta.type == "arguments"

Quando você usa stream=True, os argumentos da função chegam fragmentados via step.delta com delta.type == "arguments"; cada fragmento vem em delta.partial_arguments. Acumule os fragmentos e só faça json.loads() depois de receber o step.stop correspondente (ou no interaction.completed).

args_buffer = ""
for ev in stream:
    if ev.event_type == "step.delta" and ev.delta.type == "arguments":
        args_buffer += ev.delta.partial_arguments
    elif ev.event_type == "step.stop" and args_buffer:
        import json
        parsed = json.loads(args_buffer)   # agora é seguro
        args_buffer = ""

Auto function calling (Python) — não há

No generate_content o SDK Python executa callables automaticamente (AFC). Na Interactions API essa conveniência não existe: o roundtrip function_call → function_result é sempre um loop manual no cliente. Se você depende de AFC, veja a exceção em §5.2 (incluindo o aviso de fixar google-genai<3.0.0).

6.12 Streaming SSE ¶

Streaming é ativado com stream=True no SDK ou ?alt=sse + "stream": true no body REST. Os eventos do schema novo formam uma timeline tipada: interaction.created abre, vários step.start / step.delta / step.stop entremeiam, e ao final vem interaction.completed (com usage mas sem steps — você reconstrói via deltas acumulados) ou error, seguido do sentinel [DONE]. Transições intermediárias (incluindo requires_action) chegam como status dentro de interaction.status_update, não como evento próprio — o enum oficial de eventos SSE é apenas interaction.created, interaction.completed, interaction.status_update, error, step.start, step.delta, step.stop. A página de breaking changes usa outros nomes para as transições de status (interaction.in_progress, interaction.requires_action): divergência oficial em 2026-09-30 — trate eventos desconhecidos de forma tolerante.

Retomada via last_event_id (canônico)

Se o stream cair, cada chunk recebido carrega um event_id; mantenha o último em uma variável e reconecte via client.interactions.get(id=..., stream=True, last_event_id=...). Funciona apenas com stream=true. Padrão canônico conforme a documentação oficial de streaming (ai.google.dev/gemini-api/docs/interactions/streaming):

interaction_id = None
last_event_id  = None
done = False

def process(stream):
    global interaction_id, last_event_id, done
    for ev in stream:
        if ev.event_type == "interaction.created":
            interaction_id = ev.interaction.id
        if ev.event_id:
            last_event_id = ev.event_id
        if ev.event_type == "step.delta" and ev.delta.type == "text":
            print(ev.delta.text, end="", flush=True)
        elif ev.event_type in ("interaction.completed", "error"):
            done = True

stream = client.interactions.create(model="gemini-3.8-flash",

Uma interação usa model (modelo) ou agent (agent pré-construído) — nunca os dois. O endpoint é o mesmo POST /v1beta/interactions. A referência oficial (ai.google.dev/api/interactions-api, enum AgentOption) define três valores aceitos em agent: os dois Deep Research e o Antigravity (antigravity-preview-09-2026). 6.18 Limitações & gotchas ¶Atualizado · 2026-09-30

O que não está na Interactions API (oficial, 2026-09-30)

  • Batch API, cache explícito (client.caches), Automatic Function Calling (Python) e safety settings customizados: continuam no generateContent — ver §5.2. O único mecanismo de safety da Interactions é o safety_decision de runtime do Computer Use (ação regular/permitida ou require_confirmation).
  • Live API é superfície independente (WebSocket); Interactions é request/response com SSE.
  • Contagem de tokens: estime antes com client.models.count_tokens(...) (SDK > 2.0.0); o uso real vem em interaction.usage (em streaming, só no interaction.completed).

Limites quantitativos

  • Inline: 100 MB por request (PDF 50 MB) na página de métodos de entrada; as páginas de imagem, áudio e vídeo ainda citam 20 MB — divergência oficial não reconciliada.
  • Imagens: 3.600 por request. Áudio: 9,5 horas por prompt. PDF: 50 MB ou 1.000 páginas.
  • Vídeo: Files API até 20 GB (pago) / 2 GB (free); ~3 h em resolução baixa ou ~1 h em alta no contexto de 1M. STT dedicado: 1 h por request (30 min com diarização ou timestamps por palavra).
  • Files API: retenção 48h; 2 GB por arquivo, 20 GB por projeto.
  • Retenção de interaction.id: 55 dias (pago) / 1 dia (free).
  • Tokens por mídia: as páginas de imagem/áudio/vídeo/tokens (258 por tile, 32 tokens/s) divergem da página media-resolution (1.120 por imagem, 25 tokens/s, 70 por frame): confie em usage.

Edge cases e gotchas

  • store=false bloqueia previous_interaction_id e background=true — combinação impossível.
  • tools, system_instruction e generation_config são por interação: reenvie a cada turno, inclusive ao devolver function_result.
  • Em streaming, o interaction.completed traz usage mas não traz steps; reconstrua pelos deltas ou faça GET /interactions/{id}. Argumentos de function_call chegam em delta.partial_arguments (delta.type == "arguments"): acumule antes do json.loads().
  • thought_signature é opaco — não parseie. Em modo stateless devolva os steps de pensamento e de processing_* intactos.
  • Thinking: no gemini-3.8-flash minimal retorna erro; temperature/top_p/top_k são deprecados em Gemini 3.x.
  • MCP remoto em Gemini 3: a overview diz não suportado ("coming soon") e a página de function calling documenta mcp_server — divergência oficial; teste antes de usar.
  • Visualization em Deep Research só dispara se o prompt pedir explicitamente.
  • Regiões e data residency, e a política de retenção de prompt/saída do grounding com Google Search/Maps: não confirmados em fonte oficial lida em 2026-09-30 UNVERIFIED (2026-09-30).

ZDR (Zero Data Retention)

  • No Developer API, aproxime ZDR com store=false. Custo: perde previous_interaction_id e background; reanexe o histórico do cliente.
  • Files API e cache implícito seguem regras próprias — confira ai.google.dev/gemini-api/docs/zdr (página não relida em 2026-09-30, UNVERIFIED). ZDR formal é capability do Vertex AI.

Resolução nativa e tokenização

A página de vision expressa o tier hi-res por geração — "Claude 4.7 and later models" —, o que já cobre Fable 5.1, Opus 5.5 e Sonnet 5.5. A tokenização usa patches de 28×28 px (visual tokens). Fonte: vision#image-limits-and-costs — lida 2026-09-30.
  • Tier padrão (Haiku 4.5 e demais modelos fora do tier hi-res): nativo ≈ 1568 tokens por imagem, no máximo 1568 px no lado longo.
  • Tier hi-res ("Claude 4.7 e modelos posteriores" — inclui Opus 5.5, Sonnet 5.5 e Fable 5.1): nativo ≈ 4784 tokens por imagem, até 2576 px no lado longo. Automático — sem cabeçalho beta nem opt-in de cliente.

Inputs maiores são downscaled preservando aspect ratio até o limite do tier. Coordenadas que o modelo retorna (bounding boxes, pontos) referem-se à imagem já redimensionada — reescale no cliente antes de desenhar sobre o original.

Fórmula exata (patches de 28×28 px):

tokens = ⌈width / 28⌉ × ⌈height / 28⌉

Limitações de visão (verbatim do guia oficial)

  • Identificação de pessoas: Claude não nomeia pessoas em imagens e recusa fazê-lo (Acceptable Use Policy).
  • Precisão: alucinações/erros em imagens de baixa qualidade, rotacionadas ou abaixo de 200 px.
  • Raciocínio espacial limitado: relógios, posições de peças de xadrez, layouts finos.
  • Contagem: aproximada para grandes quantidades de objetos pequenos.
  • Detecção de imagem gerada por IA: Claude não detecta de forma confiável imagens sintéticas — não use como detector de fake.
  • Conteúdo impróprio é recusado por AUP.
  • Saúde: pode analisar imagens médicas gerais, mas não é ferramenta de diagnóstico para CT/MRI; jamais substitua aconselhamento médico.
  • Metadados: Claude não lê EXIF nem metadados de imagem.
  • Persistência: uploads via base64/URL são efêmeros, descartados após a request; imagens via Files API persistem até serem deletadas.
  • Geração/edição: Claude é image-understanding only. Não gera nem edita imagens — use OpenAI gpt-image-2.5-flare/-sunburst, Gemini gemini-3.1-flash-image, Stability etc.

Workaround recomendado — frame extraction

Sub-amostre o vídeo em frames estáticos (tipicamente 0.5–2 FPS dependendo do movimento) e envie como sequência de blocos image. Com Opus 5.5 cabem até 600 imagens por request (modelos de 200k: 100), o que cobre alguns minutos de footage em uma chamada se os frames forem modestos.

frames = sorted(glob.glob("frames/frame_*.jpg"))[:60]  # 60 frames

content = [{"type": "text",
            "text": "These are frames at 1 FPS from a short clip. Summarize what happens."}]
for i, path in enumerate(frames, 1):
    with open(path, "rb") as f:

    content.append({"type": "text", "text": f"Frame {i}:"})
    content.append({"type": "image", "source": {
        "type": "base64", "media_type": "image/jpeg", "data": b64,
    }})

msg = client.messages.create(
    model="claude-opus-5-5",
    max_tokens=2048,
    messages=[{"role": "user", "content": content}],

7.9 Prompt caching com imagens / PDFs ¶Atualizado · 2026-09-30

O prompt caching da Anthropic permite marcar conteúdo de prefixo caro (system prompt, imagens grandes, PDFs grandes) com cache_control para que requests subsequentes que baterem no mesmo prefixo paguem uma tarifa reduzida de cache-read.

Uso

Anexe cache_control: { type: "ephemeral", ttl: "5m" | "1h" } em um bloco image, document, text, definição de tool, ou tool result. Ordem importa — a Anthropic cacheia prefixos, então coloque conteúdo estável (system → tools → docs grandes → imagens) antes do turno dinâmico do usuário. 

msg = client.messages.create(
    model="claude-opus-5-5",
    max_tokens=1024,
    messages=[{
        "role": "user",
        "content": [
            {"type": "document",
             "source": {"type": "base64", "media_type": "application/pdf", "data": pdf_b64},
             "cache_control": {"type": "ephemeral", "ttl": "1h"}},
            {"type": "text", "text": "Which model has the highest win rate?"},
        ],
    }],
)
# Inspect: msg.usage.cache_creation_input_tokens / cache_read_input_tokens

Constraints

  • Até 4 breakpoints cache_control por request.
  • TTL: "5m" (default) ou "1h".
  • Cache é chaveado por prefixo: qualquer mudança mais cedo no prefixo invalida tudo o que vem depois.
  • Tamanho mínimo cacheável (verificado em 2026-09-30): 512 tokens em Fable 5.1, Opus 5.5 e Sonnet 5.5 (e em Mythos 5.1, Opus 5, Fable 5, Mythos 5); 4.096 tokens em Haiku 4.5. Abaixo disso o cache não é criado, nenhum erro é retornado e você paga input cheio. Com 512 tokens, um screenshot único ou um PDF de 1–2 páginas já podem ser cacheados. Modelos legados têm mínimos de 1.024 a 4.096 (Legado). Fonte: prompt-caching#cache-limitations.
  • Multiplicadores: write 5m = 1,25× o input base; write 1h = 2×; read = 0,1×, exceto 0,05× no Opus 5.5 e 0,025× no Fable 5.1. Opus 5.5 ($4/MTok): write 5m $5 · write 1h $8 · read $0,20. Sonnet 5.5 ($2/MTok): read $0,20. Fontes: pricing e models/overview — lidas 2026-09-30.
  • Image caching: bytes da imagem + representação tokenizada são cacheados — modelos hi-res (Opus 5.5, Sonnet 5.5, Fable 5.1) são quem mais ganha.
  • PDF caching: cada página é cacheada como image + text tokens — economia escala linearmente com o doc.

Quando compensa

  • Mesmo PDF, muitas perguntas (Q&A estilo analista).
  • Mesmo screenshot, muitos prompts diagnósticos.
  • Documento de referência grande sendo chunked em muitos turnos.
  • Loops de tool use repetidos onde o schema do tool é grande.

7.11 Limitações & gotchas ¶Atualizado · 2026-09-30

Visão

  • Sem identificação de pessoas, sem conteúdo que viola AUP, sem diagnóstico CT/MRI.
  • Artefatos de compressão lossy podem quebrar OCR — verifique seu downscaler.
  • Coordenadas retornadas pelo modelo referem-se à imagem pós-resize e pós-pad. Reescale antes de desenhar no original.
  • Imagens via base64/URL são efêmeras; descartadas após a response. Para "lembrar" entre turnos, use Files API com o mesmo file_id.
  • Animações: apenas o primeiro frame de GIF/WebP.

PDF

  • Sem PDFs com senha/encriptados.
  • Teto de 600 páginas em modelos 1M ctx, 100 em 200k ctx — mas request size (32 MB) e context window podem bater antes.
  • Cada página é texto + imagem; PDFs de 100 páginas podem consumir 200k+ tokens facilmente.
  • Análise visual via Amazon Bedrock Converse exige citations.enabled=true, ou você perde silenciosamente entendimento de gráficos/diagramas.

Code Execution

  • Sem rede outbound. Qualquer pip install ou urllib.request.urlopen falha. Pré-instaladas cobrem a maior parte; para o resto, stage wheels via container_upload.
  • Container expira em 30 dias; container_id serve para workflows curtos, não storage durável.
  • Sessões concorrentes são cobradas por container — 10 containers paralelos × 10 min = 10 × min(5 min, real).
  • Bash output_file_too_large trip em stdout multi-MB (ex.: imprimir DataFrames inteiros). Pipe para arquivo e baixe.
  • Code Execution não é ZDR-elegível.

Files API

  • 500 MB por arquivo, 1 TB por org. No teto de org os uploads retornam 403.
  • Rate limit aproximado de 500 RPM. Não é bus de ingestão high-volume.
  • Arquivos enviados não podem ser baixados. Apenas arquivos que Claude produziu (skills ou Code Execution) têm downloadable: true.
  • Arquivos persistem até serem deletados — limpe periodicamente ou veja o storage encher.
  • Escopo de workspace: qualquer API key do mesmo workspace pode usar/deletar qualquer arquivo. Trate como compartilhado.

Geral

  • Blocos multimodais contam para o mesmo limite de 32 MB por request; muitas imagens grandes → Files API.
  • Blocos image e document só existem dentro de mensagens com role: "user".
  • O chain-of-thought do modelo (quando thinking está habilitado) não faz streaming da imagem. Não espere "ver" Claude olhando a imagem passo-a-passo em adaptive thinking.
  • Bedrock e Vertex AI são subsets limitados — sources somente base64, sem Code Execution, Bedrock Converse exige citations para PDF visual.
  • tool_choice forçado: any/tool devolve 400 em Opus 5.5, Sonnet 5.5 e Fable 5.1; use auto com strict: true ou structured outputs. Nada disso afeta os blocos image/document.

R1 — Q&A em PDF longo com citações por trecho

Problema: usuário sobe um PDF de centenas de páginas e quer respostas com o trecho exato citado. Apenas a Anthropic tem primitiva de citação nativa no bloco do documento; a OpenAI usa as annotations do File Search; no Gemini a citação vem do prompt.

OpenAI File Search + Responses (annotations)

resp = client.responses.create(
    model="gpt-6-astra",
    tools=[{"type": "file_search", "vector_store_ids": [vs.id]}],
    include=["file_search_call.results"],
    input="Quais cláusulas tratam de rescisão? Cite o trecho.",
)
for item in resp.output:
    for part in getattr(item, "content", None) or []:
        for ann in getattr(part, "annotations", None) or []:
            if ann.type == "file_citation":
                print(ann.file_id, ann.filename)
