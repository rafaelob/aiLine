Paralelismo de tools em frameworks de agentes: OpenAI, Anthropic e Gemini

Análise ampliada para desenho de um framework multi-provider que usa OpenAI Responses API e Agents SDK, Messages API da Anthropic e a Interactions API do Gemini (google-genai). O foco é separar emissão de tool calls pelo modelo, execução client-side, ferramentas hosted/server-side, serialização por dependência, latência, segurança, custo, observabilidade e política por ferramenta.

Superfície atual

OpenAI = Responses API (parallel_tool_calls, padrão ligado). Anthropic = Messages API (vários tool_use por turno; disable_parallel_tool_use dentro de tool_choice auto). Gemini = client.interactions (vários steps function_call por resposta; sem boolean de paralelismo). Nenhum provider tem política paralelo/serial por tool: o scheduler e o teto de concorrência são seus.

Faça / Não faça

  • Não trate parallel_tool_calls como política por tool: ele só controla a emissão pelo modelo → limite a execução no seu runtime (§7, §24).
  • OpenAI: built-in tools não entram no batch paralelo de function calls; com mutações, separe em fases (§3.3). A ordem entre built-in e function calls no mesmo output não é especificada.
  • OpenAI: não use Chat Completions com tools em gpt-6-astra/gpt-6.1-sol → use Responses. Não use Assistants (encerrada em 2026-08-26).
  • OpenAI async:true (GPT-6 Astra e posteriores): devolva a saída tardia com o call_id original e previous_response_id; não combine com tools hosted, programmatic tool calling nem, em multi-agent, com parallel tool calls.
  • Agents SDK: não confunda ModelSettings.parallel_tool_calls (emissão) com max_function_tool_concurrency (execução local).
  • Anthropic: não envie tool_choice any/tool em Opus 5.5, Sonnet 5.5, Fable 5.1 ou Mythos 5.1 (400, também no count_tokens) → use auto + strict:true ou structured outputs (§4.6). disable_parallel_tool_use dentro de auto segue válido.
  • Anthropic: devolva todos os tool_result em uma única mensagem user imediatamente após o assistant, antes de qualquer texto; se não executar uma chamada, devolva tool_result com is_error:true.
  • Anthropic: não use thinking:{"type":"disabled"} nem budget_tokens em Opus 5.5 (400); Sonnet 5.5 usa {"type":"between_tools"}. Devolva o assistant turn verbatim (thinking e server_tool_use inclusos); blocos de thinking são presos a modelo, conversa e conta.
  • Anthropic: server tools não entram no seu scheduler (web_search_20260318, web_fetch_20260318, code_execution_20260521); trate pause_turn reenviando a resposta como está; computer_20251124 dá 400 → computer_toolset_20260801.
  • Gemini: não use generateContent/AFC quando o scheduler precisa controlar a execução; na Interactions o loop é seu. Responda TODO step function_call (call_id = step.id, name igual) e reenvie tools/system_instruction/generation_config a cada turno.
  • Gemini stateless (store=False): devolva os steps thought intactos e na ordem; store=False não combina com background=True. Streaming: acumule arguments_delta e execute só após step.stop.
  • Gemini: não assuma que any limita a uma só chamada; valide len(calls). Mantenha 10–20 tools ativas.

0. Tese executivaAtualizado · 2026-09-30

Ponto mais importante: não trate parallel_tools=True como uma flag universal. Ela mistura pelo menos três decisões diferentes: se o modelo pode emitir várias tool calls, se o seu runtime vai executá-las em paralelo e se a ferramenta é executada por você ou pelo provedor.

OpenAI

parallel_tool_calls (ligado por padrão desde o GPT-5) controla a emissão de function calls, mas não é uma política per-tool nem torna hosted tools client-side. Com built-ins disponíveis, function calls podem ser paralelas; a built-in é que não entra no batch paralelo. [S1]

Agents

No OpenAI Agents SDK, parallel_tool_calls controla emissão pelo modelo; max_function_tool_concurrency controla execução local de function tools. São knobs diferentes. [S7] [S8]

Claude

Claude pode emitir múltiplas client tools por padrão; disable_parallel_tool_use=true limita isso. Server tools da Anthropic não entram no seu executor client-side. Em Fable 5.1, Mythos 5.1, Opus 5.5 e Sonnet 5.5, tool_choice forçado (any/tool) retorna 400 — só auto/none; use auto+strict:true. [S13] [S34]

Gemini

Na Interactions API (GA desde junho de 2026), chamadas paralelas chegam como vários steps function_call numa só resposta e todas devem ser respondidas por function_result. O modo de chamada vai em generation_config.tool_choice. [S18] [S23]

Conclusão de arquitetura

Seu framework deve ter pelo menos estes controles, não apenas uma flag:

@dataclass
class AgentToolPolicy:
    # O modelo pode emitir várias chamadas no mesmo turno?
    allow_model_parallel_tool_calls: bool = True

    # Quantas tools client-side rodam simultaneamente no seu runtime?
    max_client_tool_concurrency: int | None = 4

    # Como lidar com built-ins/server tools?
    hosted_tool_strategy: Literal["same_turn", "separate_phase", "disabled"] = "separate_phase"

    # Como lidar com mutações, side effects, pagamentos, envios, deleções?
    mutation_policy: Literal["forbid_parallel", "lock_by_resource", "allow"] = "forbid_parallel"

    # Controle de exposição de tools por fase.
    expose_only_phase_tools: bool = True

    # Limites e retry são enforcement do runtime, não do provider.
    max_fanout_per_scope: dict[str, int] = field(default_factory=lambda: {"request": 4, "tenant": 20, "provider": 100})
    retry_only_if_transient_and_idempotent: bool = True
    circuit_breaker: bool = True
    require_typed_subagent_io: bool = True

O desenho robusto é: built-ins/server-side são uma trilha; function tools/client-side são outra trilha; e a sua camada de orquestração decide o scheduler real.

Em APIs modernas, “tool” pode significar uma função sua, uma busca web hospedada, um interpretador de código remoto, um MCP server, um browser/computer tool, um subagente, uma operação local no shell ou uma capacidade server-side. Essas categorias têm propriedades completamente diferentes.

3. OpenAI em profundidadeAtualizado · 2026-09-30

Eixo ortogonal a parallel_tool_calls (verificado em 2026-09-30): async:true por tool deixa 1 call lenta sem bloquear o turno, com entrega tardia pelo mesmo call_id (function_call_output/custom_tool_call_output num request de continuação com previous_response_id). Suportado pela família GPT-6 (Astra e posteriores). Não usar com tools hosted, programmatic tool calling ou, em multi-agent, combinado com parallel tool calls. Fonte: async-tool-calling.

Na OpenAI, a recomendação central é separar function tools client-side de built-in/hosted tools. A Responses API oferece function calling, built-in tools, MCP e tool search. [S2] A família vigente é GPT-6: gpt-6-astra (flagship, GA 2026-09-03), gpt-6.1-sol (GA 2026-09-29, equilíbrio entre velocidade, custo e inteligência), gpt-6-sol (anterior da linha Sol) e gpt-6-luna (volume). gpt-5.6 segue servido, sem data de retirada. O parâmetro reasoning.effort aceita none só em gpt-6-sol e gpt-6-luna; Astra o rejeita (400) e gpt-6.1-sol não o suporta (nem minimal). Detalhes de modelo e preço no guia OpenAI.

3.1 O que parallel_tool_calls faz de fato

parallel_tool_calls controla se o modelo pode emitir múltiplas chamadas no mesmo turno; vem ligado por padrão nos modelos a partir do GPT-5. Quando configurado como false, a doc garante exatamente zero ou uma tool call. [S1]

Bom caso: só function tools externas, todas read-only e independentes. Exemplo: consultar CRM, billing e tickets para o mesmo cliente. O modelo pode emitir três function calls no mesmo output, e você executa as três em paralelo.

response = client.responses.create(
    model="gpt-6.1-sol",
    input="Consulte CRM, billing e tickets do cliente 123.",
    tools=[crm_lookup_tool, billing_lookup_tool, ticket_lookup_tool],
    parallel_tool_calls=True,
)

# Se response.output contiver 3 function_call items independentes:
results = await asyncio.gather(
    dispatch(crm_call),
    dispatch(billing_call),
    dispatch(ticket_call),
)

3.2 O que parallel_tool_calls não faz

Não fazImplicação
Não força o modelo a chamar múltiplas toolsMesmo com a flag ligada, o modelo pode chamar só uma ou nenhuma.
Não executa suas funções por vocêNa Responses API direta, você precisa extrair calls, executar, montar outputs e reenviar.
Não dá política por toolNão há um campo nativo geral “esta tool pode paralelizar, esta não”.
Não transforma built-ins em tasks client-sideWeb search/file search/code interpreter hospedados são executados pela OpenAI, não pelo seu scheduler.
Não resolve dependências lógicasReasoning models podem precisar de chamadas em série quando uma depende da outra. [S6]

Programmatic Tool Calling (GPT-5.6, Responses API) — caminho ortogonal ao parallel_tool_calls. Em vez de o modelo emitir N function calls para o seu cliente executar, o GPT-5.6 pode escrever JavaScript num runtime V8 isolado e efêmero (sem Node, FS, rede, subprocessos ou estado persistente) que orquestra várias tool calls — com loops e condições — e reduz saídas intermediárias grandes a um resultado estruturado antes de voltar ao modelo. Ative com a tool {"type":"programmatic_tool_calling"} e habilite cada ferramenta elegível com allowed_callers:["programmatic"]; a execução emite os itens program/program_output. Bom quando o fluxo é determinístico e redutível (fan-out de reads + agregação); menos indicado quando cada passo exige julgamento do modelo ou aprovação humana. tools-programmatic-tool-calling

3.3 Built-in tool e function tools no mesmo request

O que a doc diz (verificado em 2026-09-30): “On supported models beginning with GPT-5, functions can be called in parallel when built-in tools are also available. Built-in tools cannot be included in a parallel function-call batch.” [S1] Ou seja: ter uma built-in na lista de tools não impede function calls paralelas; o que a doc exclui é a própria built-in do batch paralelo de funções.

A built-in é executada dentro do fluxo hospedado da OpenAI: seu código não recebe uma pausa controlada no meio do reasoning para iniciar suas functions em paralelo a ela, e só controla a execução quando a API devolve function calls ao cliente. File Search, por exemplo, é uma hosted tool gerenciada pela OpenAI, chamada automaticamente quando o modelo decide usá-la. [S3]

A doc não especifica a ordem nem se o modelo mistura built-in e function calls no mesmo output. Decisão de engenharia (não contrato do provedor): use hosted_tool_strategy="separate_phase" quando alguma function for mutação, porque o scheduler não desfaz uma built-in já executada; para functions todas read-only, same_turn é aceitável e você valida o resultado no runtime.

# Só reads: built-in + functions no mesmo request; o scheduler paraleliza apenas as function calls.
response = client.responses.create(
    model="gpt-6.1-sol",
    input="Pesquise notícias da empresa X e consulte CRM, billing e tickets.",
    tools=[
        {"type": "web_search"},
        crm_lookup_tool,
        billing_lookup_tool,
        ticket_lookup_tool,
    ],
    parallel_tool_calls=True,
)

3.4 Arquiteturas para OpenAI built-ins + externas

Opção A — Duas fases técnicas

Fase 1 com built-in hosted; fase 2 com function tools externas e parallel_tool_calls=True. É o padrão mais claro quando há mutações.

Request 1: web_search/file_search/code_interpreter ↓ resultado/contexto Request 2: CRM + Billing + Tickets com parallel_tool_calls=True ↓ resultados paralelos Request 3 ou continuação: síntese final

Opção B — Transformar built-in em function sua

Crie external_web_search() como function tool client-side. Assim ela entra no seu scheduler junto com CRM e billing. Você ganha controle, mas perde parte da integração hosted.

Opção C — Prefetch pelo orquestrador

Seu framework inicia CRM/billing/tickets em paralelo com a chamada OpenAI que usa web search. Reduz latência quando você sabe que esses dados serão necessários.

Opção D — Agentes separados

Use um ResearchAgent com built-ins e um OpsAgent com function tools. O agente orquestrador combina os resultados e mantém política de fase.

# Fase 1: hosted tool OpenAI
research = client.responses.create(
    model="gpt-6.1-sol",
    input="Pesquise informações recentes sobre a empresa X.",
    tools=[{"type": "web_search"}],
)

# Fase 2: apenas function tools externas, paralelizáveis
ops = client.responses.create(
    model="gpt-6.1-sol",
    previous_response_id=research.id,
    input="Cruze agora com CRM, billing e tickets do cliente 123.",
    tools=[crm_lookup_tool, billing_lookup_tool, ticket_lookup_tool],
    parallel_tool_calls=True,
)

3.5 OpenAI reasoning models e loops de tools

Reasoning models podem pensar antes e entre tool calls, e a documentação recomenda preservar reasoning items em workflows de function calling, seja por previous_response_id ou repassando output items relevantes. [S5] O Cookbook da OpenAI chama atenção para o caso em que modelos que suportam parallel tool calls ainda podem precisar de chamadas em série quando há dependência entre etapas. [S6]

Loop robusto com reasoning: while True: response = call_model(context, tools) calls = extract_client_function_calls(response) if not calls: return final_message(response) groups = scheduler.partition(calls) # paralelo/serial/locks/aprovação outputs = execute_groups(groups) context = preserve_reasoning_items_and_append_tool_outputs(response, outputs)

Isso importa porque “paralelo” não é um estado global do agente. É uma propriedade de um conjunto específico de calls independentes em um step específico.

O Agents SDK é útil quando você quer loop de agente, tracing, handoffs, guardrails, agents-as-tools e execução de function tools com menos boilerplate. A documentação do SDK lista categorias como hosted OpenAI tools, local/runtime tools, function calling, agents as tools e Codex tool. 5.1 Function calls paralelas em steps

Você declara a tool como {"type":"function","name","description","parameters"} em tools. Quando o modelo chama funções, a resposta traz steps function_call com id, name e arguments. Chamadas independentes chegam como vários steps function_call na mesma resposta, e todas devem ser respondidas: você devolve um item function_result por chamada, com call_id igual ao id do step, junto de previous_interaction_id — e reenvia tools, porque tools, system_instruction e generation_config são por interação. [S18]

import json
from concurrent.futures import ThreadPoolExecutor
from google import genai

client = genai.Client()
tools = [crm_tool, billing_tool, ticket_tool]  # {"type": "function", "name": ..., "parameters": ...}

interaction = client.interactions.create(
    model="gemini-3.8-flash",
    input="Consulte CRM, billing e tickets do cliente 123.",
    tools=tools,
)

while True:
    calls = [s for s in interaction.steps if s.type == "function_call"]
    if not calls:
        break
    # Seu scheduler decide paralelo/serial; aqui, pool com teto de concorrência.
    with ThreadPoolExecutor(max_workers=3) as pool:
        results = list(pool.map(dispatch, calls))
    interaction = client.interactions.create(
        model="gemini-3.8-flash",
        input=[
            {
                "type": "function_result",
                "name": call.name,
                "call_id": call.id,
                "result": [{"type": "text", "text": json.dumps(result)}],
            }
            for call, result in zip(calls, results)
        ],
        tools=tools,
        previous_interaction_id=interaction.id,
    )

print(interaction.output_text)

A estrutura de function_call/function_result e o uso de previous_interaction_id seguem o exemplo oficial; o laço paralelo e o pool são nossos. Mantenha 10–20 tools ativas por request. O SDK Python não executa funções por você na Interactions: o loop é sempre seu, o que é o que um scheduler per-tool precisa (a execução automática do generateContent está em #legado).

5.5 Streaming de chamadas

No stream SSE, o step function_call chega como step.start (com o nome) seguido de step.delta com arguments_delta (JSON parcial a acumular) e step.stop; a interação termina em interaction.completed (com usage). Recomendação nossa: execute a tool só depois do step.stop do step. A doc de streaming ainda lista interaction.status_update, enquanto a página de breaking changes lista interaction.in_progress e interaction.requires_action: trate eventos desconhecidos com segurança.

6.2 O que instruções resolvem — e o que não resolvem

Instruções ao agente ajudam muito para orientar o modelo:

Use tools em paralelo apenas quando forem read-only, idempotentes e independentes.
Nunca chame em paralelo tools que criam, atualizam, deletam, enviam mensagens,
cobram pagamentos, reservam estoque ou modificam estado externo.
Para dependências, chame uma tool, aguarde o resultado e só então chame a próxima.

Mas isso é controle probabilístico. Para invariantes de negócio, use hard controls: não exponha a tool naquele turno, desabilite paralelismo, aplique locks, exija aprovação, use idempotency keys e valide o plano antes de executar.

7. Scheduler recomendado para seu framework

O scheduler deve agir como uma camada de segurança e eficiência entre o modelo e o mundo externo. Ele não deve simplesmente executar tudo que o modelo emitiu.

7.1 Pipeline de execução

1. Provider adapter extrai tool calls brutas e identifica route/capabilities 2. Normalizador converte para NormalizedToolCall (I/O tipado + call id) 3. Registry adiciona ToolSpec e loss declaration 4. Policy validator autentica/autoriza e classifica: permitido, rejeitado, aprovação, serial, paralelo 5. Planner constrói batches/DAG dentro de fan-out e budgets por escopo 6. Scheduler executa com fila, backpressure, semaphores, locks, timeouts, retries e circuit breakers 7. Formatter monta tool outputs no formato da rota, sem vazar dados 8. Próximo call preserva apenas histórico/IDs/reasoning/signatures suportados pela rota

7.3 Validação antes de executar

def validate_calls(calls: list[NormalizedToolCall], registry: ToolRegistry, policy: AgentToolPolicy):
    decisions = []
    if len(calls) > policy.max_fanout_per_scope["request"]:
        return [(call, "blocked_fanout_limit") for call in calls]
    for call in calls:
        spec = registry.get(call.name)
        if spec is None or not validate_schema(call.args, spec.input_schema):
            decisions.append((call, "blocked_invalid_input"))
            continue
        if not policy.authorize(call.name, spec.authorization_scope):
            decisions.append((call, "blocked_unauthorized"))
            continue

        if spec.runtime_kind.endswith("hosted") or spec.runtime_kind.endswith("builtin"):
            decisions.append((call, "provider_executed"))
            continue

        if spec.requires_approval:
            decisions.append((call, "needs_approval"))
            continue

        if spec.side_effect and policy.mutation_policy == "forbid_parallel":
            decisions.append((call, "serial"))
            continue

        if spec.parallel_safe and spec.read_only:
            decisions.append((call, "parallel"))
        else:
            decisions.append((call, "serial"))

    return decisions

Autorização é decidida por claims/tenant no runtime e revalidada no executor; texto do modelo, tool description ou resultado de outra tool nunca aumenta o scope. Schema de entrada e saída são validados antes e depois da chamada; falha de validação é blocked, não retry.

7.4 Locks por recurso

Algumas tools podem ser paralelas em recursos diferentes, mas não no mesmo recurso. Exemplo: atualizar cliente 123 e cliente 456 em paralelo pode ser aceitável; duas atualizações no cliente 123 devem ser serializadas.

async def execute_with_resource_locks(calls, registry, lock_manager):
    async def run_one(call):
        spec = registry[call.name]
        key = render_resource_key(spec.resource_key_template, call.args)

    # gather não autoriza nem faz retry; erros retornam status explícito.

7.5 Batches com semáforo

async def run_parallel_batch(calls, max_concurrency: int):
    sem = asyncio.Semaphore(max_concurrency)

    async def guarded(call):
        async with sem:
            if circuit_breaker.is_open(call.spec.circuit_breaker_key):
                return blocked(call, reason="circuit_open")
            return await run_with_timeout_and_retries(
                call,
                retry_if=lambda error: is_transient(error) and call.spec.idempotent,
                idempotency_key=runtime_idempotency_key(call),
                max_attempts=call.spec.max_retries + 1,
                on_unknown="do_not_repeat",

    return await asyncio.gather(*(guarded(c) for c in calls), return_exceptions=False)

7.6 DAG de dependências

Quando você consegue inferir dependências, use uma DAG. Dependências vêm de três lugares: steps diferentes emitidos pelo modelo, outputs que alimentam argumentos futuros e conflitos de recurso/side effect.

Exemplo: get_customer(customer_id=123) ─┬─► create_invoice(customer.id) └─► get_contract(customer.id) billing_get_balance(customer_id=123) ───────────────┘ Batch 1 paralelo: get_customer, billing_get_balance Batch 2 serial/dependente: get_contract, create_invoice conforme resultado

8.3 Custo de schemas e histórico

Tools aumentam tokens. Anthropic documenta que custos de tool use incluem schemas enviados no parâmetro tools, blocos tool_use, blocos tool_result e possíveis cobranças adicionais para server-side tools. [S14] OpenAI MCP também recomenda preservar itens como mcp_list_tools para evitar relistar tools e reduzir latência. [S10] Gemini tool combination conta parts intermediários de toolCall/toolResponse no histórico de requests. [S19]

Práticas recomendadas:

  • Não exponha todo o catálogo de tools em todo turno.
  • Use fases, namespaces, tool search ou allowed tools.
  • Minimize schemas profundos demais.
  • Retorne resultados enxutos, estruturados e sem payloads gigantes.
  • Use cache para lookups read-only e resultados de busca quando compatível com freshness.

8.4 Throughput e rate limits

Paralelismo reduz latência individual, mas pode aumentar QPS e carga no banco. Uma execução paralela com 10 tools por usuário e 100 usuários simultâneos vira 1.000 chamadas externas simultâneas. O scheduler precisa de:

  • semaphore global por provider;
  • semaphore por tool ou rate-limit bucket;
  • timeouts curtos e diferenciados por tool;
  • circuit breaker para serviços degradados;
  • retry com backoff só para operações idempotentes;
  • limite de fan-out por request, agente, tenant e provider, com fila e backpressure;
  • budget de contexto/tokens e compactação com retenção de fatos críticos;
  • fallback para resultados parciais quando o produto permitir.

8.5 Latência de hosted tools é menos controlável

Built-ins podem ser excelentes por integração, mas a latência é opaca. OpenAI web search, por exemplo, pode ser usado como tool na Responses API, e o modelo decide se pesquisa ou não; em cenários agentic/reasoning, uma busca pode envolver mais deliberação e passos internos. [S4] Code interpreter também pode iterar código até resolver o problema, o que é poderoso mas menos previsível em latência. [S2]

9. Padrões arquiteturais recomendados

Padrão 1 — Fases read/write

Primeiro exponha apenas tools read-only e paralelizáveis. Depois, em fase separada, exponha tools de mutação com paralelismo desligado.

Phase A: read-only parallel CRM, billing, tickets, docs Phase B: reasoning/synthesis Phase C: mutation serial create_invoice, send_email, charge_card

Padrão 2 — Composite tool para transações

Para fluxos críticos, encapsule a sequência em uma única tool procedural que controla locks, transação, retry e idempotência.

@tool
async def checkout_order(cart_id, payment_method_id, idempotency_key):
    async with lock(f"cart:{cart_id}"):
        inventory = await reserve_inventory(cart_id)
        charge = await charge_card(payment_method_id, inventory.amount, idempotency_key)
        order = await create_order(cart_id, charge.id)
        return {"order_id": order.id, "status": "confirmed"}

Padrão 3 — Batch tool

Em vez de permitir 30 chamadas da mesma tool, exponha uma batch tool que aceita lista. Reduz overhead, melhora rate limit e simplifica retorno.

@tool
async def batch_get_weather(cities: list[str]) -> dict[str, Weather]:
    return await weather_client.batch(cities)

Padrão 4 — Hosted phase + client phase

Ideal para OpenAI quando precisa de built-ins e function tools externas. Use hosted em fase própria, depois client functions em paralelo.

OpenAI hosted search → external client tools parallel → final answer

Padrão 5 — Orchestrator prefetch

Quando dados internos são quase sempre necessários, busque-os antes ou em paralelo à chamada do modelo. Troca overfetch por latência menor.

Padrão 6 — Agent-as-tool controlado

Use subagentes para encapsular capacidades, mas trate cada subagente como uma tool com timeout, budget e política de side effects.

14. Protocolo nativo de tool loop por provedorAtualizado · 2026-09-30

Esta seção desce do nível conceitual para o formato operacional. Em um framework multi-provider, você deve esconder as diferenças por trás de adaptadores, mas não deve apagá-las mentalmente. Cada provedor tem um jeito diferente de representar chamadas, resultados, IDs, histórico e estado de reasoning.

14.1 OpenAI Responses API — loop manual de function tools

Na Responses API direta, o loop típico é: chamar a rota explicitamente escolhida, procurar output items de function call, executar suas funções, devolver output items de função e repetir até a mensagem final. Em reasoning models, preserve reasoning items ou use previous_response_id para manter continuidade; conversation é uma alternativa de recurso stateful e não deve ser combinada com esse encadeamento na mesma chamada. [S5] [S6] [S22]

async def run_openai_function_loop(client, *, model, input_, tools, policy):
    previous_response_id = None
    pending_input = input_

    while True:
        response = client.responses.create(
            model=model,
            input=pending_input,
            tools=tools,
            previous_response_id=previous_response_id,
            parallel_tool_calls=policy.allow_model_parallel_tool_calls,
        )

        calls = extract_openai_function_calls(response)
        if not calls:
            return extract_final_text(response)

        # Normalizar, validar, agrupar e executar com seu scheduler.
        normalized = normalize_openai_calls(calls, response=response)
        results = await scheduler.execute(normalized, policy=policy)

        # Montar outputs no formato esperado pela Responses API.
        pending_input = [
            {
                "type": "function_call_output",
                "call_id": result.call_id,
                "output": json.dumps(result.content if result.ok else {"error": result.error}),
            }
            for result in results
        ]
        previous_response_id = response.id  # ou ledger/conversation, escolha uma rota

Detalhe de produção: se você usa store=false, zero data retention ou histórico manual, precisa cuidar de reasoning/encrypted reasoning items conforme a documentação; não simplifique isso para “só devolver tool outputs”. [S5]

14.2 OpenAI com built-ins — loop hospedado vs loop client-side

Quando há built-ins OpenAI, o loop tem uma parte invisível para você: a tool hospedada roda no servidor do provedor e não entra no batch paralelo de function calls. Seu framework pode observar outputs/eventos, mas não executa aquela tool. Por isso, para built-ins + externas com mutações, o protocolo recomendado é duas fases técnicas:

async def run_openai_hosted_then_client(client, query, customer_id):
    # 1) Fase hosted: OpenAI executa web/file/code tool.
    research = client.responses.create(
        model="<validated-model-id>",
        input=query,
        tools=[{"type": "web_search"}],
        parallel_tool_calls=False,
    )

    # 2) Fase client-side: apenas suas functions, agora paralelizáveis.
    ops = await run_openai_function_loop(
        client,
        model="<validated-model-id>",
        input_="Use o contexto anterior e consulte dados internos do cliente.",
        tools=[crm_lookup_tool, billing_lookup_tool, ticket_lookup_tool],
        policy=AgentToolPolicy(
            allow_model_parallel_tool_calls=True,
            max_client_tool_concurrency=3,
        ),
        previous_response_id=research.id,  # escolha esta continuidade ou conversation, nunca ambas
    )

    return ops

14.3 Anthropic Messages API — loop manual de client toolsAtualizado · 2026-09-30

Claude retorna blocos tool_use; você executa e devolve blocos tool_result. Para paralelismo, a regra crítica é agrupar os resultados em uma única mensagem de usuário, logo depois da mensagem do assistant com as calls. [S13]

async def run_anthropic_tool_loop(client, *, model, messages, tools, policy):
    while True:
        response = client.messages.create(
            model=model,

            messages=messages,

        tool_uses = [b for b in response.content if b.type == "tool_use"]
        if not tool_uses:

        # Acrescentar a mensagem do assistant exatamente como retornada.
        messages.append({"role": "assistant", "content": response.content})

        normalized = normalize_anthropic_tool_uses(tool_uses)

        # Importante: uma única mensagem user com todos os tool_result.
        messages.append({
            "role": "user",
            "content": [

                    "type": "tool_result",

                    "content": json.dumps(r.content if r.ok else {"error": r.error}),

                for r in results
            ],
        })

async def run_interactions_loop(client, *, model, user_input, tools, policy, previous_id=None):
    request = {
        "model": model,
        "input": user_input,
        "tools": tools,

    interaction = client.interactions.create(**request)
    while True:
        # Só steps function_call entram no scheduler; built-ins ficam como observação.
        calls = normalize_function_call_steps(interaction.steps)
        if not calls:
            return interaction.output_text
        results = await scheduler.execute(calls, policy=policy)
        interaction = client.interactions.create(
            model=model,
            input=[
                {
                    "type": "function_result",
                    "name": r.name,
                    "call_id": r.call_id,  # = id do step function_call

                }
                for r in results

            system_instruction=policy.system_instruction,
            generation_config=policy.generation_config,
            store=policy.store_interactions,
            previous_interaction_id=interaction.id,
        )

16. Validação pós-modelo: o modelo sugere, o framework decide

Mesmo quando a API permite chamadas paralelas, o framework deve validar se elas são aceitáveis. Isso é especialmente importante quando o modelo emite várias chamadas no mesmo turno, porque “mesmo turno” não significa “seguro executar junto”.

16.1 Algoritmo de decisão

def classify_execution(calls, registry, policy):
    provider_executed = []
    needs_approval = []
    serial = []
    parallel_candidates = []

    for call in calls:
        spec = registry[call.name]

        if spec.runtime_kind in {"openai_hosted", "anthropic_server", "gemini_builtin"}:
            provider_executed.append(call)
            continue

        if spec.requires_approval or spec.irreversible:
            needs_approval.append(call)
            continue

        if spec.side_effect:
            serial.append(call)
            continue

        if spec.parallel_safe and spec.read_only:
            parallel_candidates.append(call)
        else:
            serial.append(call)

    # Depois, dividir candidatos paralelos por locks/rate limit buckets.
    parallel_batches = split_by_resource_conflicts(parallel_candidates, registry)
    return ExecutionPlan(provider_executed, needs_approval, serial, parallel_batches)

17. Contratos de prompt e descrição de tools

Instruções não substituem enforcement, mas melhoram o comportamento do modelo e reduzem violações. O ideal é ter um contrato de prompt por fase e uma descrição de tool com semântica operacional.

17.1 Contrato de fase paralela

Você está na FASE DE LEITURA.
Objetivo: coletar dados independentes e read-only.
Pode chamar várias tools no mesmo turno somente se forem read-only e independentes.
Não chame tools de criação, atualização, deleção, envio, cobrança ou reserva.
Não invente dependências: se uma chamada precisar do resultado de outra, chame apenas a primeira.
Ao receber resultados parciais, sintetize explicitando lacunas.

17.2 Contrato de fase sequencial/mutação

Você está na FASE DE AÇÃO CONTROLADA.
Só execute uma ação por vez.
Antes de ações irreversíveis, confirme que o usuário aprovou explicitamente.
Se faltar approval, peça confirmação; não chame a tool.
Não chame duas tools de mutação no mesmo turno.
Use idempotency_key quando disponível.

20. Análise final da pergunta central: OpenAI built-in → externas paralelasAtualizado · 2026-09-30

[S1] O resto é a distinção entre o que a doc garante e o que o seu runtime precisa impor.

24. Per-tool: paralelo / serial — desenho do schedulerAtualizado · 2026-09-30

Esta seção responde à pergunta de design que os providers não resolvem nativamente: como, dentro do mesmo agent loop, fazer com que algumas tools sejam SEMPRE paralelas (reads independentes) e outras SEMPRE sequenciais (mutações, pagamento, deleção, envio de email), de forma portável entre OpenAI, Anthropic e Gemini?

24.1 Pergunta enquadrada

Nenhum provider tem flag nativa per-tool que diga “esta tool sempre paralela, aquela sempre serial”. OpenAI tem parallel_tool_calls request-wide; Anthropic tem disable_parallel_tool_use request-wide; Gemini tem generation_config.tool_choice (auto, any, none, validated, allowed_tools). Nenhum é per-tool, e nenhum dos modos de “forçar chamada” promete limitar a uma só. Portanto, a política per-tool tem que viver no scheduler client-side. O provider serve como dica e redução de emissões ruins, não como fronteira de enforcement.

24.2 Princípios de design

#PrincípioConsequência
1Tools provider-executed (built-ins, server tools) já rodaram quando você vê o resultado; o scheduler não as desfaz.Visibilidade por fase é obrigatória; nunca exponha provider-executed lado a lado com mutações críticas, salvo opt-in explícito (allow_provider_executed_with_mutations).
2Comportamento de emissão varia por família de modelo e muda entre versões.A arquitetura falha fechado por padrão.
3parallel_tool_calls=false e disable_parallel_tool_use são request-wide.Não expressam “reads paralelos, mutações seriais” no mesmo conjunto visível, e não retroagem a built-ins.
4Distinguir tool_use client de server_tool_use (e steps de built-in no Gemini) no normalizer.Marque provider_executed; o scheduler trata como observação, não como agendável.
5Modos de tool choice (any, allowed_tools, allowed_function_names) não são scheduler.Use-os só para visibilidade; não expressam locks, approval, idempotency ou conflict groups.
6Quando o scheduler precisa controlar a execução, desabilite execução automática de tools do SDK (por exemplo, o Agents SDK só é o chokepoint se ele for o scheduler).O loop de function calls da Interactions já é manual; no Agents SDK, use max_function_tool_concurrency e guardrails.
7Tool composta só serve para sequência de negócio real (charge_then_send_receipt).Use COMPOSITE_SEQUENCE como tipo declarado e raro.
8Resource locks e tool-group locks precisam de linguagem declarativa.ConcurrencyPolicy.SERIAL_BY_RESOURCE (key template) e SERIAL_BY_TOOL_GROUP (conflict groups).
9Prompts e descrições são dica, não enforcement: o modelo pode emitir chamadas em paralelo mesmo instruído a não fazê-lo.Política como código no scheduler.

24.6 Tradução por provider

def adapter_config(provider, phase, tools: list[ToolSpec], policy: AgentToolPolicy):
    visible    = [t for t in tools if phase in t.visibility_phases]
    all_reads  = all(not t.is_mutation() for t in visible)
    has_mut    = any(t.is_mutation() for t in visible)

    if provider == "openai_responses":
        return {"tools": ..., "tool_choice": "auto",
                "parallel_tool_calls": bool(all_reads)}

    if provider == "anthropic":
        return {"tools": ..., "tool_choice": {"type": "auto",
                                              "disable_parallel_tool_use": bool(has_mut)}}

    if provider == "gemini_interactions":
        # tools já filtradas por fase; a visibilidade é o controle, não o modo
        return {"tools": ...,
                "generation_config": {"tool_choice": "auto"}}

O que não dá para empurrar para nenhum provider e tem que ficar no scheduler: per-resource locks; “esta tool é serial, aquela é paralela” no mesmo turno; “reads agora, mutations depois nesta ordem”; “charge_card e send_email mutuamente exclusivos”; idempotency key reuse em retry; rejeitar só a mutação preservando o read; não misturar provider-executed com mutação client-side.

24.7 Conclusão

Per-tool parallel/serial só é robusto quando o scheduler é o chokepoint de execução, é alimentado por ToolSpec declarativos com ConcurrencyPolicy + locks + approval + idempotency, e o provider serve como hint para reduzir emissões ruins — não como fronteira de enforcement. As três APIs convergem nesse modelo via adapters finos.

Próximos passos sugeridos: queue_after em vez de block em conflitos de lock, TTL de approval, observabilidade OTel para o scheduler e o cenário composite (charge_then_send_receipt).
