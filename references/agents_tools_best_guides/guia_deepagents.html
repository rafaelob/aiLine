def get_weather(city: str) -> str:
    """Get weather for a given city."""
    return f"It's always sunny in {city}!"

agent = create_deep_agent(
    model="anthropic:claude-sonnet-5-5",          # "provider:model" ou instância de chat model; não omita (None depreciado)
    tools=[get_weather], system_prompt="You are a helpful assistant",
    interrupt_on={"get_weather": True}, checkpointer=MemorySaver(),   # HITL exige checkpointer
)
agent.invoke({"messages": [{"role": "user", "content": "weather in sf"}]}, config={"configurable": {"thread_id": "t1"}})

3. Faça / Não faça

  • Não use deepagents-cli/deepagents init|dev|deploy/deepagents.toml (depreciados; libs/cli removido na 0.7.9) → mda init|dev|deploy (§21.1) ou langgraph deploy (§26). deepagents-code é outro pacote e está ativo.
  • Desde a 0.7.0 (2026-07-29) write_todos não vem por padrão: passe middleware=[TodoListMiddleware()] (no agente e em cada subagente que planeja). Constantes de prompt removidas; BASE_AGENT_PROMPT deprecated (remoção na 0.9.0) → use system_prompt= próprio.
  • FilesystemBackend/LocalShellBackend têm virtual_mode=True por padrão (0.7.0+) e não servem para produção; backend= recebe instância concreta, não factory (§9).
  • A tool task rejeita chaves de argumento desconhecidas (0.7.18+); o modo de subagente handoff agora é isolated (0.7.13+). Não existe async_create_deep_agent: use ainvoke/astream (§7).
  • Subagente: system_prompt, middleware e skills não herdam do pai; tools e permissions definidos substituem os herdados. CompiledSubAgent.runnable precisa de state key messages; em create_agent use system_prompt=, não prompt=.
  • OpenAI: a string "openai:*" já usa a Responses API no create_deep_agent (ProviderProfile); uma instância ChatOpenAI não: configure use_responses_api=True. Não existe integração com a Gemini Interactions API.
  • HITL (interrupt_on) e threads duráveis exigem checkpointer; StoreBackend exige store= (§4, §15).
  • MCP em Python: langchain.mcp.MCPAdapter (pip install "langchain[mcp]"), não langchain-mcp-adapters (arquivado); resources/prompts MCP só existem no pacote arquivado (§28).
  • Não atribua resultados da eval suite oficial (§22.2) a GPT-6, Claude 5.5 ou Gemini 3.8: a tabela não os cobre. Para Gemini 3.x não fixe temperature/top_p/top_k.

Parte A — Conceitos

Vinte e quatro capítulos cobrindo o Deep Agents na ordem de leitura recomendada da documentação oficial.

1. Visão geral · os quatro pilares

O Deep Agents é um harness construído sobre langchain.agents.create_agent e LangGraph. Sua proposta — segundo o post de Harrison Chase (2025-07-30) — é elevar agentes "shallow" (chamar tool em loop) para a categoria deep: capazes de planejar, delegar e manter contexto em horizontes longos.

PilarMecânicaImplementação
1. System prompt configurável Default lean/vazio; a aplicação adiciona somente as instruções necessárias system_prompt= + prompts próprios dos middlewares ativos. BASE_AGENT_PROMPT é compatibilidade 0.6 depreciada; HarnessProfile.system_prompt_suffix continua opcional.
2. Planning tool To-do list como "context engineering strategy" para manter o agente no rumo Opt-in na 0.7: middleware=[TodoListMiddleware()] injeta write_todos; status pending / in_progress / completed
3. Sub-agents Dividir tarefas e isolar contexto Tool task(...) injetada por SubAgentMiddleware; subagent general-purpose default; tipos SubAgent / CompiledSubAgent / AsyncSubAgent
4. Sistema de arquivos virtual Workspace compartilhado funcionando como memória de longo prazo Tools ls / read_file / write_file / edit_file / glob / grep injetadas por FilesystemMiddleware; BackendProtocol pluggable
Fontes: blog, overview.
Nota (docs oficiais, verificado 2026-06-29): a documentação oficial enquadra as quatro capacidades como: (1) Execution environment — tools, filesystem virtual, sandbox opcional e REPL; (2) Context management — skills, memória, sumarização e caching de prompt; (3) Delegation — subagents e planejamento de tarefas; (4) Steering — HITL e interrupts. Mapeamento com os pilares acima: System prompt detalhado ≈ Execution environment + Context management; Planning tool e Sub-agents ≈ Delegation; Sistema de arquivos virtual ≈ Execution environment.

# pip install deepagents tavily-python
import os
from typing import Literal
from tavily import TavilyClient
from deepagents import create_deep_agent

tavily_client = TavilyClient(api_key=os.environ["TAVILY_API_KEY"])

def internet_search(
    query: str,
    max_results: int = 5,
    topic: Literal["general", "news", "finance"] = "general",
    include_raw_content: bool = False,
):
    """Run a web search"""
    return tavily_client.search(
        query,
        max_results=max_results,
        include_raw_content=include_raw_content,
        topic=topic,
    )

agent = create_deep_agent(
    model="anthropic:claude-sonnet-5-5",
    tools=[internet_search],
    system_prompt="You are an expert researcher...",
)

agent.invoke({
    "messages": [{"role": "user", "content": "Research LangGraph and write a summary"}]
})

Ordem do stack de middleware

Base stack (sempre presente, exceto excluído). Na 0.7, TodoListMiddleware não faz parte dele; adicione-o em middleware=[TodoListMiddleware()] quando quiser planejamento explícito:

  1. SkillsMiddleware (só se skills= for fornecido)
  2. FilesystemMiddleware
  3. SubAgentMiddleware (só se houver subagent síncrono — incluindo o general-purpose default)
  4. AsyncSubAgentMiddleware (só se houver AsyncSubAgent)
  5. SummarizationMiddleware
  6. PatchToolCallsMiddleware

User middleware é inserido aqui.

Tail stack:

  • HarnessProfile.extra_middleware
  • _ToolExclusionMiddleware (só se profile tem excluded_tools)
  • AnthropicPromptCachingMiddleware (no-op em modelos não-Anthropic)
  • MemoryMiddleware (só se memory=)
  • HumanInTheLoopMiddleware (só se interrupt_on=)
Não existe um símbolo separado async_create_deep_agent. Use o mesmo create_deep_agent e chame await agent.ainvoke(...), agent.astream(...) e middleware com hooks async (abefore_agent, awrap_model_call, awrap_tool_call, astream). Para sub-agents em background, use AsyncSubAgent.

5.1 read_file multimodal

Quando read_file lê um arquivo não-texto (imagem, vídeo, áudio ou documento), o conteúdo retorna como content blocks multimodais — não como texto. Extensões oficialmente suportadas:

TipoExtensões

A estrutura exata do content block não é detalhada na página do harness — ela aponta para a documentação de mensagens multimodais do LangChain (langchain/messages, seção #multimodal). As tools de FS built-in são ls, read_file, write_file, edit_file, delete, glob, grep e execute (este só em backends sandbox).

5.2 Caveat multimodal na summarization

A tool read_file pode retornar content blocks multimodais (imagem, áudio, vídeo — ver 5.1). Isso importa para a compactação de histórico: quando essas mensagens acabam sendo alvo de SummarizationMiddleware, a mídia não sobrevive ao resumo.

Summarization é text-only — mídia é descartada, não resumida. A doc de multimodal é explícita: "Summarization compacts older messages into a text-only summary" e "Image, audio, video, and file blocks in that range are not carried forward" — o modelo só enxerga o que o summarizer escreveu sobre elas. A conversa original completa continua gravada no filesystem virtual como texto ("The original conversation is still written to the filesystem as text"), mas os blocos de mídia em si somem do contexto do modelo após a compactação. Mensagens recentes abaixo do keep threshold permanecem inalteradas.

Offloading é diferente: ele mede só tokens de texto ("Offloading measures text tokens only") e preserva blocos não-texto nas mensagens de substituição em vez de comprimi-los ("Non-text blocks (including images) are preserved in replacement messages rather than compressed") — uma mensagem que só contém uma imagem não é descartada por offloading com base no tamanho da imagem.

Boas práticas recomendadas pela doc oficial (a compressão embutida é "primarily text-oriented"):
  • Guardar mídia grande em um backend/object store externo e passar apenas referências ("store large media in a backend and pass references when possible"), em vez de blocos base64 inline ("Prefer references over base64-encoded image blocks in long-running conversations").
  • Tools que produzem imagens/binários devem salvar o artefato no backend e retornar uma descrição textual curta + path/URL ("save the artifact to a backend and return a concise text description plus a path or URL"), não o conteúdo bruto.
  • Usar subagents para inspeção pesada de imagem ("Use subagents for image-heavy inspection so the main agent receives a compact text result") — context quarantine, ver seção 7.
  • Ajustar os thresholds de summarization ou fornecer um token counter customizado quando o provedor cobra muitos tokens por imagem ("Tune summarization thresholds or provide a custom token counter when your provider charges many tokens for images").

12.1 Reload de skills em meio de thread

Skills carregam uma vez por thread e ficam guardadas em SkillsState.skills_metadata — uma thread longa, por padrão, nunca via skill adicionada, editada ou removida depois do primeiro run. Desde deepagents 0.7.16 (2026-09-21), resetar esse campo para None faz a próxima chamada de modelo reler todas as fontes e substituir a lista carregada: 

# Dentro de um node/tool com acesso ao Runtime, para forçar reload no próximo turno:
def invalidate_skills(state, runtime):
    return {"skills_metadata": None}   # próxima chamada de modelo recarrega as skills

Uma thread cujas fontes não continham nenhuma skill também conta como "carregada" — ela para de listar o backend a cada run; threads checkpointadas por versões anteriores à 0.7.16 guardam [] nesse caso e precisam de um None explícito para recarregar. Se você escreve um SKILL.md novo durante o próprio run (ex.: com StateBackend), o reload enxerga os files escritos naquele run. Um fork herda uma invalidação pendente (se o pai setou None no mesmo passo do fork), mas recarrega das suas próprias fontes — não herda a última lista carregada do pai. Porta JS/TS: 1.14.0 espelha o comportamento — resetar skillsMetadata para null; o carregamento migrou de beforeAgent para beforeModel nessa versão.

17.1 Programmatic Tool Calling (PTC)

Com PTC, o modelo invoca suas tools de dentro do código JS, em vez de pelo caminho normal de tool calling. Declare a allowlist com ptc=[...] (lista de nomes de tools liberadas). Dentro do interpretador QuickJS, as tools ficam disponíveis sob o namespace tools. em camelCase e devem ser aguardadas com await (ex.: a tool web_search vira tools.webSearch(...)). 

from deepagents import create_deep_agent
from langchain_quickjs import CodeInterpreterMiddleware

agent = create_deep_agent(
    model="openai:gpt-6.1-sol",
    middleware=[CodeInterpreterMiddleware(ptc=["task"])],   # allowlist PTC
)
// Dentro do código executado no interpretador (camelCase + await)
const result = await tools.webSearch({ query: "deepagents interpreters" });
Gotcha de segurança (citação oficial): "PTC calls currently execute through the interpreter bridge and do not go through the normal tool calling path. As a result, interrupt_on approval workflows are not enforced per PTC-invoked tool call." Ou seja, tools aprovadas via HITL (interrupt_on) não são interrompidas quando chamadas por PTC — não inclua na allowlist tools que exijam aprovação humana.

18. Context engineering

Citando a doc oficial: context engineering = configuração de contexto que maximiza a probabilidade do comportamento desejado. O Deep Agents implementa as três técnicas long-horizon do paper da Anthropic:

TécnicaQuando aplicarNo Deep Agents
CompactionContinuidade conversacionalSummarizationMiddleware (auto em 85% / 170k) + SummarizationToolMiddleware (manual via compact_conversation)
Note-taking estruturadoTrabalho iterativo com milestoneswrite_file / edit_file no FS virtual + MemoryMiddleware (AGENTS.md)
Sub-agent architecturesExploração paralela / pesquisa complexaSubAgent / AsyncSubAgent + tool task; subagent devolve sumário de ~1–2k tokens ao lead

Específicos da summarization

  • Trigger: 85% de max_input_tokens. Mantém 10% como recent context.
  • Fallback (profile do modelo não disponível): trigger em 170 000 tokens, 6 mensagens mantidas.
  • Dois outputs: sumário estruturado in-context (intent / artifacts / next steps) substitui o histórico; mensagens originais são escritas em disco para recuperação.
  • Thresholds de offload: inputs > 20k tokens ⇒ tool calls de file-write truncados a pointers de disco em 85% de uso de janela. Resultados > 20k ⇒ offload imediato com path + 10 primeiras linhas.
  • Diretórios de offload no backend: resultados grandes vão para /large_tool_results/ e o histórico compactado para /conversation_history/. Ambos são escritos no backend de arquivos.
  • Filtro em stream: if metadata.get("lc_source") == "summarization": continue.
Isolamento dos arquivos do sistema: como o harness escreve em /large_tool_results/ e /conversation_history/, envolva o FilesystemBackend (ou o backend de projeto) em um CompositeBackend para que esses diretórios de offload não se misturem com os arquivos do projeto:

19.1 Event streaming: stream.subagents

A doc oficial de event streaming do Deep Agents descreve uma projeção de subagents construída sobre o event streaming version="v3": stream.subagents entrega um handle de stream por chamada da tool task — ou seja, um handle por delegação a um subagent. Citando a doc: “Use stream.subagents when you want one stream handle per delegated task call.” O name de cada handle é o nome configurado do subagent — o subagent_type que o coordenador passa naquela chamada de task. A projeção é lightweight (verbatim): “it discovers subagent tasks first, and message, tool-call, and value streams are opened only when you access them on a subagent handle.” Ou seja, os streams individuais de cada subagent (mensagens, tool calls, valores, subagents aninhados) só são abertos quando você os acessa no handle, evitando decodificar eventos que a UI não vai exibir.

O stream é aberto com agent.stream_events(input, version="v3") (síncrono) ou await agent.astream_events(input, version="v3") (assíncrono). Todos os exemplos abaixo assumem esse handle stream.

Campos do handle de subagent

CampoDescrição
nameNome do subagent — o subagent_type escolhido pelo coordenador na chamada de task.
messagesMensagens emitidas pelo subagent.
subagentsInvocações de subagents aninhados (recursivo).
outputEstado final do subagent, ou sinal de conclusão da tarefa delegada.
pathCaminho de namespace do stream do subagent.
statusStatus de ciclo de vida (a doc lista como exemplos, não como enum fechado): started, completed, failed, interrupted.
tool_callsTool calls escopadas ao subagent.

Em Python os nomes de projeção usam snake_case (verbatim: “Python uses snake_case projection names such as tool_calls”). Além dos campos da tabela, a doc menciona que cada stream de subagent também pode expor .values (estado incremental do subagent), junto de .messages, .tool_calls, .subagents e .output.

Ciclo de vida e leitura de status

O padrão da doc para acompanhar o ciclo de vida itera stream.subagents e trata o acesso a subagent.output como o sinal de conclusão: ler output dentro de um try/except diferencia completed (leitura bem-sucedida) de failed (exceção). 

running = 0
completed = 0
failed = 0

for subagent in stream.subagents:
    running += 1
    print(f"{subagent.name}: started")

    try:
        _ = subagent.output
        running -= 1
        completed += 1
        print(f"{subagent.name}: completed")
    except Exception:
        running -= 1
        failed += 1
        print(f"{subagent.name}: failed")

Tool calls e output_deltas

Tool calls são expostas tanto no nível do coordenador (stream.tool_calls) quanto no nível de cada subagent (subagent.tool_calls). Cada objeto de tool call expõe tool_name, input, completed, error, output_deltas e output. O output_deltas transmite a saída da tool de forma incremental (iterado com for delta in call.output_deltas), permitindo renderizar o resultado da tool conforme ele chega; o output traz o resultado final quando completed é verdadeiro e error é None. 

for call in stream.tool_calls:
    print("[coordinator tool]", call.tool_name, call.input)
    print(call.completed, call.error)

for subagent in stream.subagents:
    for call in subagent.tool_calls:
        print(f"[{subagent.name} tool]", call.tool_name, call.input)
        for delta in call.output_deltas:
            print(delta, end="", flush=True)

        if call.completed and call.error is None:
            print(call.output)
        elif call.error is not None:
            print(call.error)

Subagents aninhados (recursão)

Como um subagent pode por sua vez delegar trabalho a outros subagents, o campo subagents de cada handle é recursivo: iterar subagent.subagents alcança as invocações aninhadas, cada uma com seus próprios name, status e tool_calls — o mesmo formato do handle de nível superior, aplicado em profundidade. 

for subagent in stream.subagents:
    print(f"subagent {subagent.name}: {subagent.status}")

    for tool_call in subagent.tool_calls:
        print(f"{tool_call.tool_name}({tool_call.input})")
        for delta in tool_call.output_deltas:
            print(delta, end="", flush=True)

    for nested in subagent.subagents:
        print(f"nested subagent {nested.name}: {nested.status}")

Consumo concorrente

Três estratégias da doc para consumir coordenador e subagents ao mesmo tempo:

  • Async com asyncio.gather: abra o stream com await agent.astream_events(input, version="v3") e rode duas corrotinas em paralelo (async for sobre stream.messages e sobre stream.subagents), unidas por await asyncio.gather(consume_coordinator(), consume_subagents()).
  • Interleaving síncrono: stream.interleave("messages", "subagents") itera as duas projeções juntas, entregando tuplas (name, item) na ordem em que os eventos chegam — aqui name é o nome da projeção ("messages" ou "subagents"), não o nome do subagent. Útil para uma UI que renderiza um único feed combinado em vez de duas listas.
  • Ordenação exata por namespace: para controle fino sobre a ordem, itere os eventos brutos do protocolo (for event in stream), filtre por event.get("method") == "messages", extraia o payload de event["params"]["data"][0] e teste payload.get("event") == "content-block-delta" com delta do tipo text-delta. A origem vem de event["params"]["namespace"]: se truthy, o evento é de um "subagent"; caso contrário, do "coordinator". 
import asyncio

stream = await agent.astream_events(input, version="v3")

async def consume_coordinator():
    async for message in stream.messages:
        print("[coordinator]", await message.text)

async def consume_subagents():
    async for subagent in stream.subagents:
        async for message in subagent.messages:
            print(f"[{subagent.name}]", await message.text)

await asyncio.gather(consume_coordinator(), consume_subagents())
stream.subagents vs. stream.subgraphs: a doc oficial é direta — “stream.subgraphs shows graph execution structure. stream.subagents shows product-level Deep Agents task delegations.” Para UI voltada ao usuário final, prefira stream.subagents: ele esconde nós internos do grafo e expõe apenas as delegações de tarefa que fazem sentido em nível de produto (qual subagent está rodando, o que ele disse, quais tools chamou).
Fonte: deepagents/event-streaming

28.1 Consumir servidores MCP — langchain.mcp.MCPAdapter (embutido, beta)

Desde langchain 1.4.0 (2026-09-03), Python ganhou o namespace embutido langchain.mcp — sem pacote separado, mas exige o extra FastMCP: pip install "langchain[mcp]" (puxa fastmcp>=4.0.1,<5.0.0). A classe é MCPAdapter: ela usa FastMCP para negociação/conexão e adapta as tools MCP descobertas em tools LangChain assíncronas. 

from deepagents import create_deep_agent
from langchain.mcp import MCPAdapter

# target aceita URL http(s), Path (script local via stdio), um cliente/servidor FastMCP
# já construído, ClientGroup ou MCPConfig. Uma string PRECISA ser URL http(s).
async with MCPAdapter("https://example.com/mcp") as adapter:
    tools = await adapter.list_tools()      # cache_mode="use" (default) | "refresh" | "bypass"
    agent = create_deep_agent(
        model="anthropic:claude-sonnet-5-5",
        tools=tools,                        # mistura com built-ins via FilesystemMiddleware
        system_prompt="You help users automate tasks across our stack.",
    )
    result = await agent.ainvoke({"messages": [{"role": "user", "content": "What is 2 + 2?"}]})
Beta. Importar de langchain.mcp dispara LangChainBetaWarning uma vez por processo. Uma target em str que não seja URL http/https levanta ValueError por padrão (protege contra ler uma string de origem externa como caminho de arquivo local executável); para servidor local use Path("server.py"), um transporte fastmcp explícito ou MCPConfig. Elicitation (servidor pedindo input a meio da chamada) é resolvida por padrão via interrupt() do LangGraph — funciona dentro do fluxo HITL do create_deep_agent como qualquer outro interrupt. O MCPAdapter do langchain 1.4.3 expõe list_tools(); resources e prompts MCP não fazem parte dele (ver Legado). Detalhe completo em guia_langgraph.html §2. Fonte: langchain/mcp/adapter.py do wheel langchain 1.4.3 · docs · langchain/mcp — lidos em 2026-09-30.

28.3 Servir um deep agent como servidor MCP

Não existe função langchain_to_mcp_server(...) no langchain.mcp nem no SDK deepagents para "transformar um agente em servidor MCP". Expor um deep agent por MCP é um recurso de deployment, não de biblioteca.

Um LangSmith Deployment tradicional pode expor seu agente via MCP ou A2A "out of the box". Citação oficial: "A traditional LangSmith Deployment ... can expose your agent via MCP or A2A." 28.4 A2A — Agent-to-Agent Protocol

Enquanto o MCP conecta o agente a tools, o A2A expõe o próprio deep agent para que outros agentes o consumam. Um Agent Server publica o endpoint /a2a/{assistant_id} e um agent card em /.well-known/agent-card.json?assistant_id={assistant_id}. Métodos JSON-RPC suportados: message/send, message/stream e tasks/get.

O A2A vem habilitado por padrão; para desligá-lo, adicione disable_a2a ao bloco http do langgraph.json: 

{
  "$schema": "https://langgra.ph/schema.json",
  "http": {
    "disable_a2a": true
  }
}
Dependência mínima: langgraph-api >= 0.4.21. O contextId do A2A mapeia para o thread_id do LangGraph; esse thread_id viaja no metadata de nível superior do JSON-RPC (não dentro de params). Para compatibilidade de text-part, o estado do agente DEVE conter a chave messages.
A página de A2A do Deep Agents redireciona para a documentação operacional do LangSmith Server A2A. Confirme a versão do Agent Server e a configuração de autenticação antes de publicar o endpoint; um create_deep_agent in-process não o expõe automaticamente.

R5. Receita · Ralph mode (loop)

Origem: examples/ralph_mode. O agent fica em loop persistente, lê fila de tarefas, executa cada uma e marca como done — pattern de "agente residente".

from deepagents import create_deep_agent
from time import sleep

agent = create_deep_agent(
    model="anthropic:claude-opus-5-5",
    tools=[fetch_next_task, mark_done, notify_slack],
    system_prompt=(
        "Você é Ralph. Faça um loop:\n"
        "1) chame fetch_next_task; se vazio, espere.\n"
        "2) execute a tarefa.\n"
        "3) chame mark_done(task_id) e, em falha, notify_slack(reason).\n"
        "4) Repita indefinidamente."
    ),
)

state = {"messages": [{"role":"user","content":"start"}]}
while True:
    state = agent.invoke(state)
    if state.get("done"): break
    sleep(1)
